# Оптимизация Three.js

## Текущий шаг

**Шаг 0 завершён — харнесс и baseline зафиксированы; следующий шаг 1: диагностика.**
Ветка: `perf/optimization`, создана из текущего `master` без потери рабочих изменений.
До начала задачи в дереве были многочисленные правки рендера, UI, протокола и тестов,
а также удаления документов. Они остаются пользовательскими изменениями: коммиты этой
задачи включают только её собственные дельты. Baseline измеряет фактические текущие исходники,
а не старый `HEAD`; в JSON сохраняются хеши исходников и окружение.

## Как будет устроен харнесс

1. Отдельная страница и Node runner в `bench/`, команда `npm run bench`.
   Production bundle собирается из текущего TypeScript через установленный esbuild,
   без изменения алгоритмов рендера. Runner сам поднимает временный loopback HTTP-сервер
   и headless Chrome через Puppeteer, затем закрывает только свои процессы.
2. Использовать реальные пути `WorldRenderer3D`, `Terrain`, `Visuals`, `AnimatedModel`,
   `ModelBuild` и `TextureLoad`, локальные модели/текстуры/тайлы текущего клиента.
   Уже существуют `BenchmarkReplay`, публичные методы диагностики `WorldRenderer3D`
   и `lab/CharacterLab.ts`, позволяющие работать без аккаунта/worldserver.
   Предыдущие `.runtime/qa-*` пробы полезны как пример, но не заменяют новый baseline.
3. Зафиксировать seed, 1280×720, DPR/pixelRatio 1, настройки графики, время суток,
   маршрут и длительность 20 секунд. Прогрев описывается явно и исключается из выборки.
   Передвижение должно проходить через границу тайлов и упражнять настоящий streaming;
   стресс-профили — 10, 50 и 200 анимированных персонажей. Не подменять их кубами.
4. Для каждого кадра сохранять интервал RAF, CPU время работы и renderer.info;
   JSON: средний FPS, 1% low (1000 / среднее худшего 1% интервалов), p99 ms,
   кадры >30 ms, calls/triangles/programs/geometries/textures, пик JS heap.
   Указывать GPU/ANGLE и доступность GPU timer queries. Не называть CPU submit GPU time.
5. `bench/results/<timestamp>.json` содержит условия, сырые выборки и сводку.
   Скриншоты одинаковых позиций/моментов сохраняются вне измеряемого участка.
   Локальные клиентские ресурсы и тяжёлые артефакты не публикуются в Git.
   Baseline JSON и его идентификатор фиксируются после успешного полного запуска.
6. Шаг 1: отдельный запуск с `page.tracing`, анализ длинных кадров и CPU/GPU;
   tracing не включается в сравнительные измерения, чтобы не смешивать overhead.

### Реализация и проверка шага 0

- `bench/run.mjs`, `bench/config.json`, `bench/metrics.mjs`, `src/browser/bench/Harness.ts`;
  закреплены Puppeteer Core 25.11.0 и esbuild 0.25.12. Полная проверка типов проходит,
  обе проверки формул метрик проходят. Код игрового рендера не изменён.
- Реальный GPU подтверждён: RTX 5070 Ti, ANGLE D3D11, Chrome 153, pixelRatio 1.
  В sandbox Chrome не стартовал; разрешённый запуск бенчмарка вне sandbox работает.
- В игровом рендерере обнаружен существующий `UNIT_BUDGET=64`.
  Поэтому movement использует настоящий мир и 10 персонажей, а stress — отдельную
  лабораторную сцену ровно с 10/50/200 реальными HumanMale через shipping-код построения
  и анимаций. Лимит мира не изменялся. Stress не подтверждает игровой FPS с HUD/сервером.
- Существующий локальный клиент даёт 228 костей и 6454 треугольника на HumanMale;
  у 10 моделей проверены 40 calls и 64540 triangles. Ключевые скриншоты мира и толпы
  просмотрены: реальные текстуры и геометрия присутствуют.
- Исправлены дефекты подготовки харнесса: отсутствующий proxy-маршрут `terrain-layer`,
  конкурирующая запись одинакового blob несколькими URL, подготовка промежуточных точек
  маршрута. Первый полный прогон `2026-09-20T09-37-03-072Z` **отклонён**:
  9 ресурсов впервые загрузились во время измерения. Его цифры не являются baseline.
- Повтор `2026-09-20T09-40-35-287Z` тоже отклонён из-за одного нового ресурса на границе
  видимости. Добавлена автоматическая подготовка/повтор только при cache miss;
  выбор по FPS запрещён. 200 моделей подтвердили постоянные 800 calls / 1290800 triangles.
