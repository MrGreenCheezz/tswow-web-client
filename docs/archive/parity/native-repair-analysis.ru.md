Дата: 2026-09-23. Анализ статический, оригинальный клиент не запускался.

## Таблица Lua API

В `.data` по смещениям файла `0x6CCD00..0x6CCDA7` лежит 21 запись по 8 байт: `{uint32 nameVA, uint32 functionVA}`. Первый указатель ведёт к завершаемой нулём ASCII-строке имени, второй — в `.text`. После таблицы, по `0x6CCDA8`, стоит пара `{0xFFFFFFFF, 0x00000000}`. Следующая таблица начинается по `0x6CCDB0`. Примеры:

| Смещение записи | Имя | VA функции |
| --- | --- | --- |
| `0x6CCD60` | `CanMerchantRepair` | `0x5849F0` |
| `0x6CCD30` | `GetBuybackItemLink` | `0x5852C0` |
| `0x6CCD88` | `InRepairMode` | `0x5843B0` |
| `0x6CCD90` | `GetRepairAllCost` | `0x585990` |
| `0x6CCD98` | `RepairAllItems` | `0x585C90` |

Для автоматического извлечения имён: разобрать секции PE и преобразование VA→смещение файла; пройти выровненные по 4 байта позиции в сырой `.data`; собрать непрерывные группы записей, где `nameVA` указывает на корректный ASCII-идентификатор в `.rdata`/`.data`, а `functionVA` — в `.text`. Порог в три записи отсеивает часть случайных совпадений. У других таблиц завершающая пара отличается, поэтому фиксированный sentinel для всего бинарника неприменим. Такой проход дал 97 кандидатов и 2859 записей; среди них есть методы UI-объектов, так что подсчёт не равен числу глобальных Lua API.

### Повторяемая сверка таблицы продавца с WebClient

`tools/audit-native-merchant-api.mjs` читает только указанную выше таблицу из выбранного `Wow.exe`. Он проверяет полный SHA-256 файла, разбирает секции PE32 для перевода VA в файловые смещения и сверяет имена с `FRAMEXML_SEAM_NAMES` текущих TypeScript-исходников. Диапазон `0x6CCD00..0x6CCDA7` относится **только** к бинарнику с указанным SHA-256; для другого билда требуется отдельное исследование. В отчёт попадают только имена и счётчики, без байтов бинарника.

```powershell
# Node.js 22.15+; запуск из корня WebClient. Source hook исключает устаревший dist.
node --import ./tools/register-test-sources.mjs tools/audit-native-merchant-api.mjs 'F:\Circle\Wow.exe'
```

**Это сверка регистраций, а не функциональная проверка.** `registered` означает только, что имя есть в `FRAMEXML_SEAM_NAMES`: например, зарегистрированный `CanMerchantRepair` сейчас возвращает `false` в `LiveWorldSeam`, а `GetRepairAllCost` — `[0, false]`. `missing` означает отсутствие имени в этом seam **среди 21 записи только таблицы продавца**, а не отсутствие API во всём бинарнике или действия во всём WebClient. Действие может выполняться другим слоем либо нативным UI. Для каждого кандидата нужна отдельная проверка пользовательского сценария и серверного результата.

На текущих исходниках сверка дала 21 имя: 16 зарегистрированы в seam, 5 не зарегистрированы — `ShowMerchantSellCursor`, `ShowBuybackSellCursor`, `ShowRepairCursor`, `HideRepairCursor`, `RepairAllItems`. Это пять пробелов регистрации в данном seam, которые нужно проверить по рабочему сценарию.

## Подтверждённое поведение

- `CanMerchantRepair` (`0x5849F0`) проверяет наличие текущего NPC и бит `0x1000` в его флагах. В выбранном TrinityCore это `UNIT_NPC_FLAG_REPAIR` (`src/server/game/Entities/Unit/UnitDefines.h:249`).
- `GetBuybackItemLink` (`0x5852C0`) принимает номер ячейки с единицы, переводит его в индекс с нуля, проверяет число доступных buyback-предметов (`0xBFA3F4`), разрешает индекс через таблицу ячеек (`0xBF90F8`) и строит ссылку из найденного экземпляра предмета. Для пустой/недоступной ячейки возвращает ноль значений Lua. В отличие от него `GetMerchantItemLink` (`0x584200`) строит ссылку из записи товара и шаблона предмета.
- `InRepairMode` (`0x5843B0`) возвращает истинное значение, когда внутренний режим курсора равен `0x11`; иных условий в функции нет.
- `GetRepairAllCost` (`0x585990`) обходит слоты экипировки `0..0x12`, слоты инвентаря `0x17..0x26` и содержимое сумок `0x13..0x16`. Для повреждённых предметов суммирует результат общего helper `0x584B20`. Возвращает два значения Lua: сумму и признак наличия хотя бы одного повреждённого предмета. При отсутствии пригодного NPC возвращает нулевую сумму.
- `RepairAllItems` (`0x585C90`) обходит те же предметы. Для ремонта за деньги игрока сравнивает рассчитанную сумму с текущими деньгами и при нехватке завершает обработку без отправки пакета. Ветка ремонта за счёт гильдии обходится без этой локальной проверки. Передаёт серверу opcode `0x2A8`, GUID NPC, нулевой GUID предмета и один байт выбора денег гильдии; вызов отправки находится по `0x585F08`.
- Общий helper (`0x584B20`) получает базовую стоимость от `0x708540`, затем применяет скидку репутации с NPC. При отсутствии скидки коэффициент `1`; функция скидки `0x7279A0` содержит значения `0.05`, `0.10`, `0.15`, `0.20`, которые helper вычитает из единицы.
- Базовый расчёт (`0x708540`) проверяет текущую и максимальную прочность, ищет коэффициенты по уровню предмета, классу/подклассу и качеству, умножает их на потерянную прочность, округляет и обеспечивает минимум `1` при положительной стоимости. Связь двух таблиц с `DBFilesClient\DurabilityCosts.dbc` и `DBFilesClient\DurabilityQuality.dbc` прослежена по их соседним объектам и виртуальным методам загрузки (`0x63DBB0`→`0x8AED30`, `0x63DE00`→`0x8AEDB0`).

`src/generated/protocol-data/opcodes.ts:684` подтверждает `CMSG_REPAIR_ITEM: 0x2A8`. Выбранный TrinityCore (`src/server/game/Handlers/NPCHandler.cpp:758..790`) читает `npcGUID`, `itemGUID`, `guildBank`; нулевой `itemGUID` выбирает ремонт всех предметов. Расчёт сервера в `src/server/game/Entities/Item/Item.cpp:753..797` использует те же две DBC-таблицы. Сервер также применяет свои настройки стоимости и расширяемую скидку, поэтому результат и списание денег остаются за ним.

## Границы вывода

Проверены указанные участки кода и данные PE, без живого сравнения в игре. Нажатие отдельного предмета курсором ремонта и его пакетная ветка пока не разобраны. Для функциональной проверки реализации понадобятся NPC с флагом ремонта, повреждённый предмет, варианты оплаты игроком и гильдией и наблюдение серверного изменения прочности/денег.
