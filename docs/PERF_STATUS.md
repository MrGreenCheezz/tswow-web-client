## Шаг 20 — 27.09: фризы живой игры, которых стенд не видел

**Жалоба владельца.** После шагов 16–19 и Electron на P-ядрах в игре остаются фризы при движении
(город, открытый мир, маунт/полёт) и в толпе; включён оригинальный интерфейс FrameXML. Стенд тем
временем показывает город 97 FPS, движение 155 FPS, худший кадр маршрута 18 мс.

**Почему стенд их не видел.** `src/browser/bench/Harness.ts` гоняет только `WorldRenderer3D`: нет
игрового цикла `game/Loop.ts` (физика и коллизии, миникарта, звук), нет сети и пакетов, нет FrameXML
(он идёт в своём `requestAnimationFrame`, вне `cpuMs` и вне кольца `webclientHitches()`), а сценарии
толпы строят всех юнитов до замера — цена первого появления юнита не измерялась никогда. Живая
запись (`O` → «Записать фризы») видела только RAF-колбэк игры и LoAF без стеков.

### Инструменты

- **Запись фризов v2** (`game/PerformanceCapture.ts`, `FrameCapture.ts`, новый `world/CaptureProbe.ts`):
  выборки стеков JS Self-Profiling API за всю минуту (и между кадрами), шаги и внешние проходы
  FrameXML дольше 4 мс (`FrameXmlWorldPerf`), время обработчиков пакетов по опкодам/секундам и
  отдельные пакеты дольше 4 мс (`WorldClient.#deliver`), куча JS в checkpoints, расширенные LoAF
  (позиция точки входа, invoker). Переполненные журналы хранят самые долгие записи.
  Профилировщику нужен `Document-Policy: js-profiling`: `vite.config.mjs` (`WEB_JS_PROFILING=0`),

  (Chrome 153 и Electron 40 / Chromium 144) выборка раз в 16 мс; маркеров GC API не даёт.
- **Цена заголовка — нет** (`.runtime/perf-step20/series-js-profiling.*`, строго, 4 пары ABBA,
  `bench/run.mjs --js-profiling`): город 92.8 → 94.3 FPS (пары +4.6%, −1.2%), движение 151.4 → 154.2
  (+3.3%, +0.4%) — в пределах шума.
- **Карты исходников**: `vite build` пишет `sourcemap: "hidden"`, плагин уносит карты из `dist/web` в
  `dist/sourcemaps` (в Electron-сборку и приложение игрока не попадают).
  `bench/analyze-live-profile.mjs` разбирает запись: окна длинных интервалов, функции по
  собственному/включающему времени через карты, точки входа LoAF, пакеты, шаги FrameXML, куча.
- **Сценарий `city-arrival`**: площадь Штормграда без толпы при подготовке, затем 8 юнитов в секунду
  во время замера. Первый прогон (`2026-09-27T07-16-10-889Z`): 87.2 FPS, **1% low 14.5 FPS**,

### Исправления

Шесть правок с раздельными файлами, у каждой — тесты с проверкой мутаций (намеренная поломка
кода должна ронять новый тест) и замер до/после. Скрипты замеров — в scratchpad сессии.

1. **Коллизия по группам** (`game/CollisionSource.ts`, `game/Collision.ts`, `CollisionClient.ts`).
   Единица работы — размещённая группа (spawn + трансформация + индекс группы): трансформируется и
   получает свою сетку один раз, лежит в кеше (64 МБ, вытесняется давно ненужное, стоящее в мире —
   никогда). Шаг по улице только вставляет/вынимает готовые группы; гистерезис 90 → 120 ярдов;
   новые группы строятся ближние первыми с бюджетом 4 мс/кадр, ближе 12 ярдов — сразу; `isReady`
   закрыт, пока всё нужное не построено. Дедупликация — числами, с кешем по набору тайлов. Имя
   модели свёрнуто к написанию vmtile (`STORMWIND.WMO` и `Stormwind.wmo` — одна загрузка), посадка
   модели, которую коллизия не ждала (водный зонд рендера), пересборку не вызывает. Реальные vmaps,
   настоящие классы, fetch — энкодерами gateway: проход 379 ярдов по Штормграду, `refresh()` за кадр:

   | Проход | До: всего / макс / кадров >16 мс / major GC | После |
   | --- | --- | --- |
   | 7 ярд/с, первый | 4320 мс / 104 мс / 59 / 12 | 143 мс / 6.5 мс / 0 / 0 |
   | 7 ярд/с, обратно | 2651 / 114 / 36 / 6 | 32 / 2.1 / 0 / 0 |
   | 14 ярд/с (маунт), первый | 4527 / 113 / 60 / 12 | 139 / 5.2 / 0 / 0 |

  неподписанным звеном) → материал не делится. `signMaterialCompileHook` вызывают установщики:

  ветер, фейд травы, fantasy glow, влажность не подписаны → их материалы не делятся.

  идентичности) и возвращает изменённые на месте. `detachMaterial` — единственная копия-на-запись
  (хук как есть, ключ программы один раз); через неё теперь `cloneMaterialFaded`.

  сразу, `ownedTextures` содержит только выжившие; группы, порядок и `materialSlots` не меняются.
  Закреплены: материалы движущихся батчей (свои часы) и проходы сабмеша, рисуемого больше одного
  раза (глубина равна — решает порядок, а три сортирует opaque по id материала).
- `WorldRenderer3D.ts`: реестр, опция только для `cache === this.#builtUnits`,
  `sharedMaterialDiagnostics()`; `Harness.ts --diagnostic`: `drawsByBranch[].renderStates` и
  `sharedMaterials` (счётчики + живой аудит).

**Порядок отрисовки.** three r185: opaque — `groupOrder → renderOrder → material.id →
materialVariant → z`, программы не сортируются; transparent — `… → z → id`, материал не участвует.
Общий материал сам делает группы соседними; прозрачный порядок не меняется. Меняется только

поэтому слоёные проходы закреплены (в 17 городских сборках и display 49 таких сабмешей 0).
`renderOrder`/id не трогались.

**Освобождение.** Общий материал — элемент `built.materials` одной сборки; существующий
`disposeEvictedBuiltModels` освобождает объект один раз, когда его не держит ни одна оставшаяся
сборка; реестр забывает его по `dispose`.

### Устройство (`PoseEngine.ts`, `PoseEngineCore.ts`, `PoseEngine.worker.ts`)

- Главный поток оставляет себе дешёвое и наблюдаемое: часы миксера, время/вес/фейды действий и их
  события (код `FastPoseState.advance` до накопления без изменений), выбор пути. На каждый позируемый
  юнит он пишет в общий `SharedArrayBuffer` (64 МБ, фиксированный: WebGL отказывается грузить из
  растущего) маленькое задание — клипы/время/веса (≤8), матрицы корня и камеры, часы глобальных
  последовательностей — и публикует его сразу, так что воркер считает первый юнит, пока главный поток
  идёт ко второму.
- Воркер делает дорогое: интерполянты треков вычисляемых костей, `PropertyMixer.accumulate/apply`,
  глобальные последовательности, иерархию, билборды и палитру — прямо в данные текстуры костей
  (текстура скелета живёт в арене; `RigSkeleton.computeBoneTexture`). Клипы, программы, bind-матрицы,
  таблицы глобальных каналов регистрируются в арене один раз (ключ — объект; освобождение через
  `FinalizationRegistry` в безопасной точке кадра).
- Всё, что читает риг (крепление в проходе сцены, эмиттер, заклинание, загрузка палитры), сначала
  завершает его задание: готово — берётся; воркер не дошёл — страница считает сама тем же кодом по той
  же памяти; воркер считает прямо сейчас — ждёт до 0.3 мс, потом забирает. Результат пишется в область
  своей роли (3 области local, 2 области model), поэтому опоздавший воркер не портит результат
  страницы. Кадр никогда не показывает позу другого кадра — задержки на кадр нет по построению, это же
  проверяет тест паритета (сравнение в том же кадре). Безопасные точки: перед обходом юнитов и после
  отправки кадра (`endFrame` доделывает непрочитанные задания и ждёт простоя воркеров).
- На главном потоке остаётся всё, что `FastPose` и раньше отдавал обычному пути (чужое чтение кости,
  аддитивный слой, стрейф ног, кадр портрета), и пара всадник+маунт (её `FastPoseState`). Переход
  между позой воркера и `FastPoseState` переносит local-состояние (`adopt`).
- Без изоляции / SharedArrayBuffer / Worker `pagePoseEngine()` = undefined — прежний путь без
  изменений. `?poseworker=0` выключает воркер в игре, `?poseworkers=N` — 1–4 потока. Сбой воркера
  (исключение, `onerror`, зависание >200 мс) выключает движок, риги возвращаются на `FastPoseState`.
- Одно приближение, в пределах float32: активная привязка, которую в этом шаге не ведёт ни одно
  действие, в Three смешивается с устаревшим аккумулятором с весом 0 (`stale*0 + original`); здесь
  пишется original — разница только в знаке нуля или ulp нормировки кватерниона (в тесте на этот
  случай разошлось 0 чисел).

### Толпа

1. **`RenderBone` снова в быстром режиме V8.** Ленивый Euler шага 14 переопределял `rotation`
   через `Object.defineProperty` на экземпляре — это переводит каждую кость в словарный режим
   (`%HasFastProperties` = false), и любое чтение `position/quaternion/matrix` становится
   хеш-поиском. Офлайн, 64 реальные городские модели, полная частота: обычный путь 9.3 → 6.0 мс.
   Тест проверяет, что свойства кости остаются data-свойствами.
2. **Плоская поза (`FastPose.ts`) для толпы.** Те же часы, интерполянты и `PropertyMixer.accumulate`
   Three, но только для костей, которые рисуются или читаются (палитра + крепления + эмиттеры
   и их предки: стражник 148 из 228), без записи в `Object3D` и без обхода сцены; иерархия
   компонуется во Float64Array в порядке родителей, как `calculateBoneMatrices` в

   активных привязок или после обычного пути. Уход на обычный путь: чужое чтение кости вне
   программы (навсегда для этой модели), аддитивный слой, поворот ног при стрейфе, кадр портрета.

## Как будет устроен харнесс

1. Отдельная страница и Node runner в `bench/`, команда `npm run bench`.
   Production bundle собирается из текущего TypeScript через установленный esbuild,
   без изменения алгоритмов рендера. Runner сам поднимает временный loopback HTTP-сервер
   и headless Chrome через Puppeteer, затем закрывает только свои процессы.
2. Использовать реальные пути `WorldRenderer3D`, `Terrain`, `Visuals`, `AnimatedModel`,
   `ModelBuild` и `TextureLoad`, локальные модели/текстуры/тайлы текущего клиента.
   Уже существуют `BenchmarkReplay`, публичные методы диагностики `WorldRenderer3D`
   и `lab/CharacterLab.ts`, позволяющие работать без аккаунта/worldserver.
   Предыдущие `.runtime/qa-*` пробы полезны как пример, но не заменяют новый baseline.
3. Зафиксировать seed, 1280×720, DPR/pixelRatio 1, настройки графики, время суток,
   маршрут и длительность 20 секунд. Прогрев описывается явно и исключается из выборки.
   Передвижение должно проходить через границу тайлов и упражнять настоящий streaming;
   стресс-профили — 10, 50 и 200 анимированных персонажей. Не подменять их кубами.
4. Для каждого кадра сохранять интервал RAF, CPU время работы и renderer.info;
   JSON: средний FPS, 1% low (1000 / среднее худшего 1% интервалов), p99 ms,
   кадры >30 ms, calls/triangles/programs/geometries/textures, пик JS heap.
   Указывать GPU/ANGLE и доступность GPU timer queries. Не называть CPU submit GPU time.
5. `bench/results/<timestamp>.json` содержит условия, сырые выборки и сводку.
   Скриншоты одинаковых позиций/моментов сохраняются вне измеряемого участка.
   Локальные клиентские ресурсы и тяжёлые артефакты не публикуются в Git.
   Baseline JSON и его идентификатор фиксируются после успешного полного запуска.
6. Шаг 1: отдельный запуск с `page.tracing`, анализ длинных кадров и CPU/GPU;
   tracing не включается в сравнительные измерения, чтобы не смешивать overhead.
