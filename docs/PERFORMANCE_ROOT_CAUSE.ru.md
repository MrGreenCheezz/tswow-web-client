# Пересмотр причин производительности — 22 сентября 2026

**Проблема состоит из нескольких разных ограничений.** Последний instancing-прототип
уменьшал GPU submissions, сохраняя дорогую обработку скелетов на CPU. Подгрузка содержит
крупные синхронные операции вне бюджетов сборки сцены. При этом автономная толпа не
воспроизводит состав последней живой сцены с эффектами. Это объясняет, почему локальное
ускорение отдельных функций не даёт ожидаемого результата всей игры.

Это аудит и диагностические эксперименты. Production-код и настройки не менялись.
Исправление текущего живого FPS и достижение 120 FPS здесь не заявляются.

## 1. Что объясняет результат instancing

В предыдущей прогретой паре полного WorldRenderer:

| Среднее время / количество | Исходный вариант | Instancing |
| --- | ---: | ---: |
| CPU всего render callback | 14,631 мс | 14,774 мс |
| Обработка units | 4,242 мс | 4,276 мс |
| Submission | 8,203 мс | 8,302 мс |
| GPU query envelope | 3,104 мс | 2,275 мс |
| Draw calls | 483 | 192 |

Источник: [сохранённый полный эксперимент](.runtime/qa-fps120-20260922/world-instanced/v2-dynamic/FINDINGS.ru.md).
Небольшое различие CPU не доказывает регрессию: повторов мало и порядок последовательный.

Причина ограничения видна в коде: Three делает `scene.updateMatrixWorld()` до
`scene.onBeforeRender()`. Прототип начинает объединять модели только во втором hook.
К этому моменту исходные кости уже обойдены. Затем он обновляет индивидуальные скелеты
и копирует их палитры в общий буфер. AnimationMixer также сохраняется для каждого экземпляра.
Сокращаются draws, но основная работа с позой и матрицами остаётся, добавляются проверки
совместимости и упаковка.

Проверенные места: `node_modules/three/src/renderers/WebGLRenderer.js:1635–1650`,
`.runtime/qa-fps120-20260922/world-instanced/v2-dynamic/kernel/WorldIntegration.ts:39–59`,
`DynamicInstancedSkinning.ts:322–339` в том же каталоге kernel.

Проверка инструментария не обнаружила скрытых 6–8 мс overhead, которыми можно было бы
объяснить этот результат: сумма эксклюзивных фаз покрывает 14,575 из 14,631 мс baseline.
Подробный WorldSubmissionCapture в обычных runs выключен. Все 73 исходника `src/` в
замороженном baseline совпадают с текущими; bundle и source-map SHA проверены.

## 2. Подгрузка может блокировать поток вне кадрового бюджета

`Terrain.ts:1303` синхронно разбирает весь WVA после загрузки ответа; `:1310` публикует
результат через `#storeAnimations`, где `:1900` синхронно обходится decoded payload для
учёта памяти. Кадровые бюджеты WMO/terrain-сборки этот путь не ограничивают.

Проверка текущего декодера на настоящих локальных ресурсах, Node, 8 повторов на ресурс,
без дискового чтения внутри замера:

| Ресурс | Размер ответа | Decode + учёт памяти |
| --- | ---: | ---: |
| Archibald, 262 animation clips | 15,98 MB | 36,10–69,75 мс |
| TrollMale, 170 animation clips | 13,30 MB | 28,62–47,74 мс |
| DragonHawk, WVM9 | 2,72 MB | 8,12–27,45 мс |

Ресурсы укладываются в существующие лимиты размера. Это подтверждает наличие крупной
неразбиваемой работы, но не доказывает, что именно эти файлы вызвали текущий игровой рывок.
Node-время нельзя выдавать за длительность браузерного кадра.

FullFrameClock измеряет синхронный RAF callback (`RenderStats.ts:315–327`), а эти
continuations могут выполняться между callbacks. Поэтому интервал кадров может резко
расти при умеренных значениях render/fullFrame. Нужна связь cadence с decode, сборкой
атласа и загрузкой текстур, а не только поиск самой дорогой render-фазы.

Аналогичные места для проверки: синхронная сборка CharacterAtlas после Promise.all,
копирование TerrainSplat и canvas readback. Их вклад этим аудитом не измерен.
Предварительный shader warmup тоже не гарантирует готовность до первого показа:
новый compile запускается в том же кадре перед render. Это отдельная гипотеза,
которую нужно проверять по первому использованию программы.

[32 сырых измерения](.runtime/root-cause-20260922/streaming-decode-results.json),
[воспроизводимый probe](.runtime/root-cause-20260922/streaming-decode-probe.mjs),
[команды и ограничения](.runtime/root-cause-20260922/streaming-checks.md).

## 3. Текущий стенд не описывает всю живую нагрузку

Последняя сохранённая живая запись от 20 сентября: 20,44 FPS, CPU mean 46,66 мс,
1920×919, lightingQuality=2, 64 юнита, 39 эффектов. В sampled submission медиана —
119 обновлений скелетов, 16 773 обновлённые кости, 1333 main draws, из них 639 skinned.
Владелец draw/скелета не записан: это могут быть персонажи, маунты, заклинания и окружение.
Средняя измеренная часть main draws — 14,35 из 30,53 мс world submission.

Автономный world-crowd-200 использует одинаковых HumanMale, допускает 64 из популяции 200,
рисует около 480 calls при 1280×720 и lightingQuality=1, без полного UI и живого сервера.
Он полезен для сравнения конкретной замены, но не доказывает ускорение сцены с другим
набором материалов/эффектов. Число NPC не является достаточным описанием нагрузки.

Источник: [live-crowd-20260920.json](../bench/live-crowd-20260920.json).
Старая запись не является baseline нынешних исходников и не доказывает текущий FPS.

Особенно стоит проверить повторные обходы spell/effect rigs: `WorldRenderer3D.ts:5736`,
`:5838`, `:7170`, затем обычный обход сцены и вычисление палитры. Unit emitter path
`:6943` не ограничен тем же admission guard, что environment/gameobject emitters.
Это кандидат лишней работы, не готовое исправление: скрытый персонаж и видимый след
эффекта имеют разную семантику. Простое отключение всех hidden effects может испортить картинку.

## 4. Дополнительная несогласованность автоматического качества

AutoQuality реагирует на CPU full-frame p95 (`game/Loop.ts:617`), а меняет только
разрешение рендера. При основной стоимости анимации/матриц это может снижать чёткость
без заметного ускорения. Кроме того, ladder и UI допускают 40%, а
`WorldRenderer3D.setRenderScale` ограничивает фактический минимум 50%.

Это подтверждённая несогласованность кода, но не причина приведённого live capture:
там `autoQuality=false`. Исправлять её следует отдельно от диагноза CPU/streaming.

## Решение по дальнейшей работе

1. Для толпы и эффектов измерять стоимость по владельцам: units, mounts, spells,
   animated environment; число bone passes, скелетов и material draws. Следующий
   кандидат должен сокращать повторную подготовку позы/матриц, а не только calls.
2. Для движения связать длинный межкадровый интервал с выполнением decode/atlas/upload.
   Изолированный перенос подтверждённого CPU decode в Worker или разбивка работы должны
   сохранять отмену устаревших заданий и ограниченную публикацию результата в основной поток.
3. Проверять полный кадр на том же маршруте и при одинаковом содержимом, качестве,
   размере canvas и внешней нагрузке. Выигрыш микротеста не считать выигрышем игры.

Оснований переписывать всё приложение пока нет. Есть конкретные границы работы,
которые прежние оптимизации не устраняют, и конкретные пробелы в измерениях.

## Новая контрольная серия: отключение отдельных этапов

Проведены 11 последовательных браузерных runs по 20 секунд: обычный baseline между
каждыми двумя вмешательствами. Текущие исходники, полный WorldRenderer, прогретый
offline Elwynn, 64 допущенных HumanMale, 1280×720, DPR=1, Chrome 153 / RTX 5070 Ti.
Каждый временный hook восстановлен; последний run снова обычный.

| Временное отключение | CPU mean baseline до | С отключением | Baseline после |
| --- | ---: | ---: | ---: |
| GPU timer | 26,01 мс | 26,76 мс | 26,91 мс |
| AnimationMixer.update | 26,91 мс | 23,75 мс | 27,95 мс |
| Обычный обход дерева RenderBone | 27,95 мс | 20,97 мс | 27,78 мс |
| RigSkeleton.update и обновление bone texture | 27,78 мс | 21,98 мс | 27,51 мс |
| renderBufferDirect всех проходов | 27,51 мс | 23,27 мс | 26,37 мс |

Большой эффект дерева костей сохраняется и на последних 10 секундах маршрута:
28,34 / 20,82 / 28,43 мс. Для palette — 28,43 / 21,99 / 27,21 мс.
GPU timer не показывает устойчивого выигрыша относительно обоих соседних контролей.
Это согласуется с тем, что оставленная обработка скелетов ограничивает пользу instancing.

**Эти отключения портят результат рендеринга и не являются оптимизациями.**
Пропуск дерева затрагивает descendants/attachments; явные `updateWorldMatrix`
продолжают работать. Пропуск palette убирает и вычисления, и обновление текстуры.
Пропуск draws относится ко всем проходам, а не только персонажам. Эффекты пересекаются;
дельты нельзя складывать или выдавать за достижимое ускорение без изменения картинки.
Числа не переводятся в обещание игрового FPS.

Во время работы запущена Diablo IV; отдельные замеры до/после серии показали заметную
и меняющуюся внешнюю загрузку. Поэтому абсолютные времена и небольшие различия
не подходят для приёмки производительности. Также возможны JIT/order effects из-за
смены методов между runs. Все сырые кадры сохранены; ничего не отфильтровано из записи.
Сводка отдельно считает весь маршрут и хвосты после 5/10 секунд.

Во всех 11 runs: readiness pending/errors=0, cache errors=0, routeHeightMissing=0,
stand-in=0. Консоль браузера без warnings/errors. Последний обычный кадр просмотрен.
Strict TypeScript проверка всего проекта с диагностическими controls, добавленными
только в памяти, прошла. Дополнительно прошли 42 существующих source-теста decoder,
budget, residency и warmup. Сборка игры, автономный пакет и живая серверная сцена
в этом аудите не проверялись.
При завершении локальные 5173/8090/3724/8085 не принимали подключения.
Временный QA-сервер 4204 остановлен, созданная вкладка закрыта.

## Реализованные исправления после аудита, 22 сентября 2026

По следующему запросу пользователя внесены две ограниченные правки без изменения
качества картинки или частоты обновления анимаций:

1. `EnvironmentClient` разбирает WVA-анимации и считает их память в ленивом Web Worker.
   Входные и выходные ArrayBuffer передаются с передачей владения. Один Worker выполняет
   одно задание, ещё одно может ждать; сетевой слот занят до окончания декодирования.
   Сохранены лимиты, preflight, обработка неверного rig, отмена, dispose и повторные попытки.
   Ошибка данных разрешает cache reload; инфраструктурная ошибка Worker не сбрасывает HTTP-кеш.
   Node-инструменты сохраняют прежний декодер. Штатный esbuild benchmark также собирает,
   раздаёт и включает Worker в fingerprint исходников.
2. В `WorldRenderer3D` убраны ранний полный обход костей spell visual до размещения
   и дополнительный обход после billboard. Полная подготовка остаётся перед чтением
   матриц эмиттерами или отправкой сцены в рендерер.

### Подтверждённый результат

В браузере проверены реальные WVA размером 15,98 и 13,30 МБ, по три пары на файл.
Все значения анимаций, буферы и учёт памяти совпали точно. Максимальный интервал
контрольного таймера в отдельных парных измерениях снизился с **35–76 до 15–33 мс**.
Полное ожидание Worker составило **67–157 мс** против **35–74 мс** синхронного вызова:
результат приходит позже, зато браузер обрабатывает события во время декодирования.
Отправка задания занимает до 0,8 мс, но это **не** вся стоимость основного потока:
получение и восстановление объектов результата всё ещё создаёт заметную паузу.
Отмена активного запроса, продолжение очереди, неверный payload и dispose проверены
и в браузере. Исходные файлы и побайтовое сравнение находятся вне интервала замера.

Проверка реальных методов spell visuals на синтетических skinned rigs прошла девять
сценариев: position/flight/root/bone placement, global sequences, billboards,
частицы, ribbons, скрытие и повторное появление. На **48 непустых GPU-кадрах** различий
пикселей нет; матрицы и состояния эффектов совпали. Число посещений контрольного листа
при полных обходах до submit уменьшилось с **1685 до 670** за 720 кадров теста.
Это подтверждает устранение повторной работы; размер fixture не позволяет пересчитать
результат в игровой FPS.

Полный WorldRenderer до/после прошёл загрузку и 20-секундный offline-маршрут Elwynn
с 64 допущенными персонажами. Pending/errors, stand-ins, отсутствующие высоты и ошибки
кеша — ноль. Контрольные кадры 1280×720 побитно совпали; итоговый кадр просмотрен,
консоль без warnings/errors. Все 82 входа текущего browser bundle сверены с исходниками.
Прогретый маршрут не содержит активных spell visuals и новых WVA-загрузок во время
замера, поэтому его времена используются только как проверка интеграции.

Проверки: строгий `tsc --noEmit`, **141/141** выбранных source-тестов и production Vite
build прошли. Worker присутствует отдельным артефактом production-сборки. Сборка
выполнена в изолированном `.runtime` без копирования public assets и без генерации данных.
После уточнения проверки безопасного удаления временного каталога тест сборки
benchmark повторён отдельно и прошёл. Предупреждения сборки о крупных chunks,
двух UI-изображениях и browser-external Lua imports остаются.

### Граница результата

Устранены две конкретные причины лишней работы и длительной блокировки браузера.
Основная стоимость анимации и скелетов обычных персонажей при постоянной толпе
этими правками не устранена. Внешняя нагрузка CPU/GPU не контролировалась;
ускорение живого города, целевой FPS и автономный установленный пакет не проверены.
Живые gateway/auth/world при выполнении задачи были недоступны. Рабочие сервисы,
БД и установленные клиентские ресурсы не изменялись.
