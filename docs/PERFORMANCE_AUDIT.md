### 2.2 UI/DOM каждый кадр (`ui/Widgets,Spellbook,Auras,ActionBar,CastBar,MirrorTimers,Minimap,HeadOverlay`)
Статус: **проблема подтверждена → исправлено, требуется runtime-проверка**.
Причина: `setCooldown/setUsable/Bar.set/textContent/classList/hidden` писались 60 раз/с на
кнопку/ауру/бар без проверки изменений; `Minimap.drawBlips` — два полных скана
`state.objects` + аллокации; `HeadOverlay` — `getBoundingClientRect` каждый кадр;
`CastBar` — `getElementById` каждый кадр; `Minimap` часы/зона — форматирование каждый кадр.
Исправление: сравнение перед записью, один проход по объектам, кеш bounds 250 мс, кеш
фокус-маунта, кеш текстов. Поведение не менялось (финальный DOM тот же).
Проверка: tsc + widget/spellbook/aura/minimap/corpse-target тесты зелёные.
Ограничение: эффект на baseline требует runtime-замера игроком.

### 2.3 2D-оверлей сцены (`SimpleScene.ts:draw`)
Статус: **проблема подтверждена → исправлено, требуется runtime-проверка**.
Причина: проход по всем объектам был `spread/filter/map/filter/sort` (4 промежуточных
массива + двойной `squaredDistance`) каждый кадр поверх WebGL.
Исправление: один цикл, тот же набор и порядок. Тесты scene/nameplate/corpse зелёные.

### 2.4 Террейн (`WorldRenderer3D #updateTerrain/#buildTerrain/#rebuildTerrainGeometry`, `Terrain.ts`)
Статус: **проблема подтверждена (фриз 65 мс) → исправлено, требуется runtime-проверка**.
Причина: пересечение границы = до 5 новых тайлов + каскад ребилдов соседей синхронно
(129×129 heights/normals/water-скан каждый).
Исправление: `TERRAIN_BUILD_BUDGET=1`, `TERRAIN_REBUILD_BUDGET=2`, свой тайл вне бюджета,
отложенное хранит старую ревизию; убран `get(key)!`.
Проверка: tsc + terrain-* / submission тесты + новый тест стаггера. Швы/топология не тронуты.

### 2.5 Submit/GL (`WorldRenderer3D draw: submit-фаза`, текстуры, шейдеры)
Статус: **проблема подтверждена (фриз 69 мс в submit), причина уточняется**.
Факт: JS-билд в норме (env 3.4 мс), spike внутри двух `renderer.render`.
Инструмент: `drawSubmitStats` (дельты шейдеров/текстур/геометрии за сабмит) + `detail` в
записи фриза. Ожидается строка вида `[сабмит: шейдеры +2, текстуры +14, геометрия +9]`.
Гипотезы по исходу: шейдеры>0 → предкомпиляция на загрузке; только текстуры → дозирование
допуска/аплоадов; нули → CPU-сабмишен/каллинг/сортировка.
Рендерер создаётся с `antialias:true`, `high-performance`, pixelRatio≤2; тени — по
`lightingQuality` (`sun.castShadow`, `PCFShadowMap`). Влияние теней/AA/свечения на baseline —
гипотеза, предложен эксперимент с настройками (свечение, трава, lightingQuality).

### 2.6 Окружение/admission (`RenderAdmission`, `#updateEnvironment`, бюджеты 16/6/48)
Статус: **есть гипотеза**. Реселект каждые 4 ярда (замер в коде: 1.26 мс в Штормграде, 42k
плейсментов); допуск `selectEnvironmentAdmission` — КАЖДЫЙ кадр (3 прохода + frustum +
heap-sort). Среднее `render.env 1.9` подтверждает постоянную цену. Кандидат P1: кеширование
допуска / частота по требованиям.
`ENVIRONMENT_BUILD_BUDGET=16`, `WMO_GROUP_BUILD_BUDGET=6`, hysteresis и warm-бюджеты уже
стоят — проверено чтением, не трогать без замера.

### 2.7 Трава/ground cover (`GroundCover`, `#updateGroundCover`, 23–24k инстансов)
Статус: **есть гипотеза**. Селекция каждый кадр поверх десятков тысяч; Phase `ground` в
среднем не в топ-5 — ниже 0.6 мс? Уточнить строкой `среднее` (порог показа 0.05 мс).

### 2.8 Юниты/анимации (`AnimatedModel`, `#updateUnits`, `#poseUnit`, эффекты)

### 2.9 Физика/коллизии (`Physics`, `Movement`, `Collision`, `CameraRig`, `CollisionSource`)

### 2.10 Сеть/состояние (`WorldClient #readWorld`, inflate, `WorldState`, `WorldStore`, `WorldView`)

### 2.11 Аудио (`Sound`, `SoundClient`, `Zone/Combat/GameSounds`)
Статус: **частично исправлено (заходы 3, 15)**. Устранено: `disconnect` one-shot нод,

### 2.12 Вход/загрузка/выход (`EnterWorld`, `LoadingScreen`, `AssetWarmup`, `CollisionSource`, `Context`)
Статус: **есть гипотеза**. Факты: handshake сериализован до создания клиентов (теряется
перекрытие RTT); барьер = terrain+collision (до 9 vmtile + модели, потолок 20 с); много
fire-and-forget после handshake (хорошо); warmup-приоритеты есть; модель персонажа вне
барьера (возможна капсула). Утечки: `CollisionSource` без dispose (висячие fetch-таймеры),
terrain-семья чистится несимметрично, телепорт хранит чужие тайлы/таймеры, двойные подписки
на store — гипотеза по `detach`.
Кандидаты выполнены: dispose коллизии + чистка чужих тайлов (заход 3); остаток P2:
параллельный handshake-warmup (выигрыш — перекрытие RTT, нужен замер входа).

### 2.13 Сборка/старт (Vite, чанки, `main.ts`)
Статус: **проверено, проблема не обнаружена (критичной)**. Факты: ~2.4 МБ JS (main 1030КБ +

### 2.14 Память/жизненный цикл
Статус: **не проверено** (нужна продолжительная сессия + heap-снимки). Кандидаты из чтения:
аудио-PCM без лимита, таймеры коллизии, фоновые fetch отцепленных клиентов, `frontDoor`
lease. Повторные входы/выходы (сценарий J) — прогнать с игроком.

### 2.15 Портреты/миникарта/превью (доп. render targets, readback)
Статус: **проверено, проблема не обнаружена**. Портреты — только dirty (тест пинит),

2. `AnimatedModel.boneChainQuaternion`: переиспользуемый scratch вместо массива на вызов.
3. `WorldRenderer3D.#drawUnit`: scratch-`Color` вместо `new THREE.Color` на юнита в кадре.
4. `WorldRenderer3D.#updateUnits`: `inRange` собирается в том же проходе (убран `.map`-массив).
5. `RenderAdmission.stableBoundedTopK`: дешёвый путь при n≤k (предподсчёт скоров +

6. `WorldRenderer3D.#pruneWarmEnvironment`: вместо скана всех retained каждый кадр —

### Заход 28 — private-виды pending-текстур без варнингов (исправлено, требуется runtime-проверка)
Причина варнингов доказана по исходникам three: `setTexture2D` предупреждает при
`version > 0 && image === null`, а `Texture.copy()` ставит `needsUpdate = true`.

пикселей (схлопнутые консолью 8/5 — это сотни вызовов; сам спам тоже стоит времени входа).

через `ModelTextureLoader`, чей `#applyCompletion` — единая точка терминального состояния.

с пустым каноникалом на версии 0 (нечего аплоадить — не о чем предупреждать),

контрактами: shared source с рождения сохранён (`strictEqual` в R2.4), `clone()` зовётся
ровно один раз, `source.version`-наблюдаемость после onLoad — та же; эвикция pending
невозможна (pending защищён от вытеснения — `pinnedCount`), stale-комплишены принадлежат

### Заход 31 — предпрогрев программ в точке сборки (исправлено, требуется runtime-проверка)
Причина подтверждена по исходникам three 0.185.1: программа материала создаётся и
линкуется при первом сабмите (`getProgram` → `acquireProgram` → `gl.linkProgram`), а
униформы/локации — при первом использовании (`getUniforms`), то есть внутри `render.submit`.
Новый модуль `ProgramWarmup` переносит это раньше:
1. `registerObject` — из каждого места сборки (M2-нода и WMO-группа, skinned-инстансы
   юнитов/маунтов/аттачментов/дрессировки/геймобъектов/визуалов, инстансы окружения,
   ground cover, эмиттеры, террейн, splat-вариант, вода, погода). Stand-in повторяет
   ровно те параметры three читает с объекта: общая геометрия, класс (Mesh/SkinnedMesh/
   InstancedMesh) и `instanceColor`; дедуп — по паре «материал + `customProgramCacheKey()`»,
   поэтому смена профиля (splat, wind, tint) — новый вариант, а не пропущенный.
2. `tick` (в кадре, после всех контентных фаз, до сабмита) копирует в приватную сцену
   `fog`/`environment` мира и вызывает `renderer.compile(stand-ins, camera, worldScene)`:
   свет и тени берутся из мирового таргета, значит ключ программы тот же, что у реального
   draw. Батч — 4 программы на кадр, остальное ждёт следующие кадры.
3. Программы, которые драйвер ещё линкует, опрашиваются по `isReady()`
   (`KHR_parallel_shader_compile`, неблокирующе); готовые получают `getUniforms()`, то есть
   вторую половину цены первого draw. Контекст без расширения определяется при
   создании рендера одной строкой в консоли; тогда прогрев только переносит цену.
4. Диагностика: фаза `render.warm` в разбивке кадра и хвост `· прогрев: N прогр./M униф.`
   в строке фриза — следующий лог сам покажет, работает ли перенос.
5. Безопасность: stand-ins никогда не рендерятся, `reset()` при `clearWorldResources`,
   `isReady`/`getUniforms`/`compile` в try-catch со счётчиком `failures` (цепочка шейдера,
   которая падает, остаётся делом реального draw), `resetReplayEpoch` не тронут.
Проверки: tsc чисто; новый `tests/program-warmup.test.mjs` (4 теста: классы прокси,
единичный compile против мирового таргета с зеркалом тумана, батч/неблокирующий линк/
поздние униформы, отказ `customProgramCacheKey`) + полный прогон 3464/3490 — те же 6
предсуществующих падений, новых нет.

### 9.4. Измерения до/после

**Измеренное ускорение — только synthetic shader lifetime.** `tools/performance-warmup-scenario.ts`
использует настоящий Three/WebGL и текущий ProgramWarmup; 8 пачек по 24 уже удалённых объекта,
8 вызовов tick на пачку, видимая сфера не меняется. У материалов намеренно разные shader defines.
Это воспроизведение lifetime-дефекта, не имитация достоверной игровой толпы.

| Метрика, одинаковый workload | До | После |
|---|---|---|
| Компилируемые материалы уже удалённых объектов, каждый из 3 прогонов | 192 | 0 |
| Заявки после удаления каждой пачки | 24 | 0 |
| WebGL programs после обработки пачки, включая 1 видимую | 25 | 1 |
| CPU всего queue lifecycle (регистрация + dispose + 8 tick), финальные три пары, мс | 124.3 / 100.1 / 138.3 | 2.4 / 1.5 / 1.4 |
| CPU регистрации, три прогона, мс | 1.7 / 0.7 / 0.8 | 1.4 / 1.0 / 0.7 |
| CPU dispose, три прогона, мс | 0.1 / 0.0 / 0.2 | 1.0 / 0.5 / 0.7 |
| Видимая геометрия / draw calls | 720 / 1 | 720 / 1 |
| GPU time / VRAM bytes | недоступно / недоступно | недоступно / недоступно |

Нулевая измеренная длительность значит ниже разрешения performance.now(), а не отсутствие CPU.
Медиана всей работы очереди в финальных трёх парах: **124.3 → 1.5 мс**. Первичная серия
до завершающих исправлений дала 122.7 → 1.5 мс; меньшие различия серий не интерпретируются.
Проверка всего lifecycle показывает, что выигрыш не перенесён целиком в dispose: его цена выросла
на доли миллисекунды, удалённая компиляция занимала десятки/сотни. После каждой пачки исходный
сценарий делает дополнительный dispose **только для собственной уборки**: в игре второго dispose
у уже удалённого владельца не было, поэтому ошибочно воссозданные программы могли задерживаться.

Отдельная кнопка **Dispose compiled program before settling** компилирует один материал,
удаляет его до следующего tick и считает обращения к настоящему Three `isReady`.
Handle уничтожен в обеих версиях, но исходная очередь вызывает метод 4 раза и сохраняет запись;
исправленная не вызывает его и удаляет запись. Это подтверждение устранённого дефекта,
численное ускорение CPU для этого маленького сценария не заявляется.

**Без измеренного ускорения:** 20 сессионных циклов metadata — 40 → 0 подписок; OUT_OF_RANGE
и NEW_WORLD очищают лишние данные по тестам. Численное ускорение реального мира не заявляется.

Лаборатория до изменений (3×10 с): RAF p50 **6.9 / 6.9 / 6.9** мс,
p95 **7.0 / 7.0 / 7.0**, p99 **7.1 / 7.1 / 7.1**; CPU callbacks p95 **0.8 / 0.8 / 0.7**,
p99 **0.9 / 1.0 / 0.9**; >50 мс **0 / 0 / 0**. JS heap после окон наблюдения
17.3 / 15.5 / 15.0 MB — это отдельные snapshots, не доказательство плато всей игры.
Лаборатория после изменений (3×10 с): RAF p50 **6.9 / 6.9 / 6.9** мс,
p95 **7.0 / 7.0 / 7.0**, p99 **7.1 / 7.1 / 7.1**; CPU callbacks p95 **0.7 / 0.7 / 0.9**,
p99 **0.9 / 0.9 / 1.2**; >50 мс **0 / 0 / 0**, Long Tasks **0 / 0 / 0**.
JS heap после окон — **19.2 / 19.8 / 18.9 MB**. Уменьшение heap не доказано: GC не
принудительный, страницы живут разное время, окно короткое. Интервалы совпадают, разница CPU
мала и не считается ускорением. Тяжёлые сборки/тесты во время этих контрольных записей не шли.
DCL/load одной навигации: до **67.4/68.8**, после **67.5/69.8 мс**; единичные значения,
не время готовности модели и не основание для вывода об ускорении/регрессии загрузки.

### 10.2. Подтверждённая причина и исправление

В `WorldRenderer3D.#applyUnitOpacity` изменение коэффициента появления каждый кадр
вызывало `returnBorrowedMaterials` → `dispose` всех прозрачных копий → новое клонирование.
Когда удалялся последний материал-владелец программы, Three.js удалял и программу.
Следующий submit заново компилировал **тот же ключ**. У game objects та же проблема
возникала на каждом из шести шагов прозрачности. Прогрев исходного непрозрачного материала
не мог удержать отдельную прозрачную программу.

Теперь private materials сохраняются до окончания fade или смены состава body/equipment.
`updateBorrowedMaterials` обновляет значения через `fadeMaterial(..., source)` от исходного
материала: opacity, alphaTest и цвет для additive blend. Это предотвращает накопительное
затемнение и позволяет восстановить цвет после нулевого коэффициента. Общие материалы
не изменяются, shader hooks сохраняются, при возврате полной непрозрачности восстанавливается
исходный массив материалов и освобождаются копии. Новые копии также регистрируются в прогреве.
Текущие 400 мс появления и шесть шагов для game objects сохранены.

Изменённые файлы: `src/browser/WorldRenderer3D.ts`, `src/browser/ModelBuild.ts`.

### 12.2. Причина и исправление травы

Размер каждого кустика включал дистанционный smoothstep, рассчитанный при scatter.
Scatter выполняется после перемещения на четыре игровых ярда, поэтому между пересборками
граница оставалась неподвижной, затем скачком менялась. Кроме того, прежний cutoff по
`drawRadius` удалял экземпляры из четырёхъярдового запаса ещё до того, как они могли
войти в видимую область. Этот механизм присутствовал до последних правок анимаций/текстур;
момент, когда пользователь начал замечать дефект, по записи определить нельзя.

Добавлен `GroundCoverFade.ts`: прежняя кривая плавного масштаба в полосе 20 ярдов теперь
вычисляется в vertex shader из текущей позиции игрока и корня каждого экземпляра.
Применение после деформации ветра сохраняет прежний силуэт. За радиусом трава имеет
нулевой размер. Каждый кадр меняются только общие uniforms; пересчёта тысяч матриц
или новых загрузок instance buffer между шагами нет.

`GroundCover.ts` сохраняет полный исходный масштаб и запас за видимой границей в режиме
`deferDistanceFade`; остальные callers сохраняют прежний контракт. `ModelBuild.ts`
устанавливает shader hook только по явной опции. `WorldRenderer3D.ts` передаёт состояние
fade и использует отдельный ключ кеша, чтобы обычная размещённая копия того же M2
не получила ограничение дальности травы. Живые built models остаются закреплены в кеше.
Плотность и видимый радиус не уменьшены. Счётчик отправленных экземпляров теперь включает
невидимый запас за границей; он может немного вырасти при прежних настройках.

### 13.2. Воспроизведённые ошибки прогрева

В `ProgramWarmup.ts` исправлены два независимых пропуска:

1. Подсказка дедупликации учитывала материал и класс объекта, но не параметры геометрии.
