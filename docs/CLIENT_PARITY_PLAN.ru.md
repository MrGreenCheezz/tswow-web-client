Текущий результат и неудачные проверки: [журнал выполнения](parity/parity-execution.ru.md) и [блокеры](parity/parity-blockers.ru.md). Матрицы: [P0](parity/parity-p0-matrix.ru.md), [P1](parity/parity-p1-matrix.ru.md).

**Все открытые пункты одним списком — [единый план работ](WORK_PLAN.ru.md)** (253 пункта по этапам, с 28.09.2026; звук и чат вне плана по решению владельца 29.09). Доказательства к ним — в [аудите 28.09](parity/audit-2026-09-28.ru.md); детали производительности — в [каталоге оптимизаций](OPTIMIZATION_CATALOG.ru.md). Начальный анализ выполнен по рабочим исходникам без запуска оригинального клиента и новых FPS-замеров; позднее состоялся вход в локальный realm через WebClient и первый браузерный проход. В дереве уже много незакоммиченных изменений; исторические результаты из `bench/` и документов не являются baseline нынешнего дерева.

## 1. Что считать эталоном

Целевой профиль: оригинальный клиент **WoW 3.3.5a build 12340**, данные и локаль `ruRU` из выбранного клиентского комплекта, совместимый TSWoW/TrinityCore из конфигурации WebClient. Для каждого сравнения фиксировать хеш исходников WebClient, ревизию ядра, fingerprint dataset и клиентских ресурсов, realm, разрешение и DPR, UI scale, настройки графики, персонажа и снаряжение. Пароли, ключи сессии и содержимое `.env` в артефакты не включать.

Эталон имеет три источника:

1. **Оригинальный клиент** — вид, звук, управление, расположение интерфейса, порядок пользовательских действий.
2. **Выбранное ядро TrinityCore/TSWoW** — направления и форматы пакетов, авторитетный исход игровых действий, доступность функций именно этого realm.
3. **Исходные MPQ/DBC/FrameXML** — модели, текстуры, анимации, таблицы, Lua/XML и их порядок загрузки.

Для парной съёмки нужен закреплённый профиль «3.3.5a». По умолчанию `src/browser/ui/SettingsModel.ts` включает несколько `faithful-plus` эффектов и множитель травы 2; эти настройки не подходят для некалиброванного сравнения с оригиналом. Первый контрольный профиль уже добавлен в окно настроек: он ставит render scale 100%, выключает автоизменение качества и дополнительные эффекты, возвращает множитель травы 1. Он пока **не откалиброван** по свету, камере и реальным кадрам оригинала. Сомнительные интерпретации таблиц, например плотность травы, разрешать сравнением с эталоном, а не подбором красивой картинки.

Для живых сценариев использовать выделенный тестовый realm или согласованный снимок состояния. Рабочую БД не считать одноразовой фикстурой. Рандомные исходы проверять по допустимым правилам и состоянию сервера, а детерминированные поля — точно.

## 2. Текущее положение и риск ложной «готовности»

- У всех 514 живых входящих опкодов выбранного ядра есть ветка в клиенте; `src/generated/protocol-data/dead-opcodes.md` относит ещё 147 к неиспользуемым в этой сборке. Ветка — не эффект: учёт 01.10 (5.29, `src/world/IgnoredOpcodes.ts`, сверяется `tests/opcode-coverage.test.mjs` с заголовком `OpcodeBacklog.ts`) — 484 с эффектом, 18 без эффекта по замыслу, 1 запланирован (пункт плана), 11 без пункта плана (02.10: SPELLLOGEXECUTE и ENCHANTMENTLOG ушли в журнал боя, 3.01; пять обработчиков 5.22 получили реакцию Wow.exe, SERVER_FIRST_ACHIEVEMENT — по замыслу: только строка чата); в работе их считает `webclientIgnoredOpcodes()`. `tests/opcode-coverage.test.mjs` считает наличие `OPCODES.NAME` в исходниках и запрещает ветки «разобрать и вернуть true» вне реестра. Имя в коде не подтверждает корректный разбор, состояние, UI и исход действия. `src/world/WorldClient.ts` записывает ошибки обработки и продолжает сессию. Покрытие опкодов проверять живыми сценариями и `webclientUnhandledOpcodes()` вместе с ошибками пакетов.
- Мир уже имеет terrain, WMO, M2, воду, освещение, погоду, эффекты и потоковую загрузку. Сначала измерять конкретные пропуски и различия кадра; лимиты допуска в `src/browser/WorldRenderer3D.ts` могут скрывать объекты даже при наличии ресурса.
- Входные GlueXML экраны используются по умолчанию. Штатный **мировой** FrameXML включается настройкой «Оригинальный интерфейс WoW» (`originalFrameXml` в `src/browser/ui/SettingsModel.ts`, по умолчанию выключена); параметр `?framexml=1` / `?framexml=0` лишь переопределяет её для диагностики (`frameXmlFlagEnabled` в `src/browser/framexml/FrameXmlWorldPolicy.ts`). Без настройки HUD — собственный DOM. FrameXML загружает ограниченную часть штатного TOC и местами использует смешанный UI (`FrameXmlCorpus.ts`, `FrameXmlWorldMount.ts`).
- Известные незавершённые пользовательские пути на момент начала работ: торговец FrameXML исключал товары с `ItemExtendedCost` (`FrameXmlMerchantMetadata.ts`); `ArenaRegistrarFrame` исключён из текущего TOC из-за отсутствующего packet seam (`FrameXmlCorpus.ts`). В текущем срезе расширенная цена и штатное подтверждение покупки проверены на mounted MPQ/canned seam; серверное списание не проверено. Покупка навыка у тренера **уже имеет** путь `BuyTrainerService` → `WorldClient.learnFromTrainer` → `CMSG_TRAINER_BUY_SPELL`; ранее записанное предположение о no-op было неверным. Живой результат обоих путей всё ещё надо проверить. Их статус в альтернативном DOM UI проверять отдельно.
- `bench/run.mjs` уже даёт воспроизводимое A/B **между версиями WebClient** при 1280×720 и фиксированных ресурсах. Его PNG-сравнение не является сравнением с оригинальным WoW. Формальный контур (`BenchmarkManifest.ts`, `FormalRenderBenchmarkRunner.ts`) ещё ждёт утверждённых replay fixtures, включая Златоземье и Штормград. Старые baseline не переносить на текущее изменённое дерево.

## 3. Единица работы и учёт прогресса

Единица работы — **сквозной игровой сценарий**, а не отдельный файл, экран или опкод. Для каждого сценария завести запись:

| Поле | Что записать |
| --- | --- |
| Среда | Ревизии, fingerprint ресурсов и dataset, персонаж, стартовое состояние, настройки |
| Действия | Точные шаги игрока в оригинале и WebClient |
| Сеть | Исходящие/входящие пакеты, обязательные поля, ошибки разбора, неожиданные и необработанные опкоды |
| Мир | Авторитетное состояние сервера до/после, объекты, предметы, ауры, валюты, позиция |
| Экран/звук/ввод | Эталонные кадры или короткая запись, реакция элементов и клавиш, ожидаемые звуки |
| Качество | Время загрузки, RAF p50/p95/p99, 1% low, кадры >50/100 мс, CPU/GPU, память |
| Итог | `не проверен` / `расходится` / `исправлен` / `принят`, ссылки на артефакты |

Сценарий принимается, когда запрос доходит до сервера, его результат соответствует правилам ядра, модель мира и экран отражают результат, повторное выполнение/закрытие/переподключение не ломает состояние, а все замеченные в этом сценарии ошибки пакетов разобраны. Для недетерминированных исходов документировать инварианты. Только успешный unit test или наличие обработчика опкода не закрывает сценарий.

### Начальный реестр сценариев

**P0 — непрерывная игра:** вход → выбор/создание персонажа → вход в мир; движение/поворот/прыжок/плавание/смена зоны/телепорт; выбор цели, автоатака, обычное и наземное заклинание, ауры/кулдауны, смерть и воскрешение; NPC → получение квеста → прогресс → сдача → награда; добыча, сумки и экипировка; выход, разрыв и повторный вход. Проверять одиночного и второго игрока там, где результат виден другим.

**P1 — обычные системы Wrath:** торговец с золотом и `ItemExtendedCost`, тренер, таланты/книга заклинаний, банк, почта, аукцион, группа, чат, обмен, гильдия, питомец, транспорт, LFG и очередь PvP. Проверять диалоги ошибок: нет денег, неверная цель, полная сумка, отмена, истёкшее приглашение.

**P2 — полное покрытие выбранного realm:** арены и хартии, профессии и крафт, достижения/календарь, макросы и аддоны TSWoW, редкие состояния боя, погоды, подземелий и транспорта. Приоритет P2 уточнять по тому, что реально предоставляет это ядро и чем пользуются игроки.

P0/P1/P2 обозначают порядок проверки, а не утверждают отсутствие реализации. Если модуль уже есть, сначала проверять его сквозным сценарием и фиксировать конкретный дефект.

Для текущего этапа «игра выглядит и ощущается как 3.3.5a» объём завершения — **все перечисленные P0 и P1**, обязательные эталонные сцены из раздела 4 и порог качества из раздела 6. P2 остаётся отдельным перечнем для расширения полноты выбранного realm. Дефект внутри этапа получает тяжесть: `S0` — действие невозможно или серверный итог неверен; `S1` — видимый обязательный объект/анимация/элемент UI отсутствует либо сценарий регулярно зависает; `S2` — локальное визуальное или удобство расхождение при рабочем сценарии. На завершении этапа требуется 0 открытых S0/S1; S2 должен иметь эталон, воспроизведение и приоритет. Внутри P0/P1 сначала исправлять S0/S1 с наибольшей частотой у игроков; оценку трудоёмкости учитывать после подтверждения дефекта.

## 4. Сравнение вида и интерфейса

Сформировать каталог эталонных сцен: вход/выбор персонажа; Златоземье и Штормград; WMO интерьер; берег и подводная камера; дождь/снег; плотная толпа; бой с несколькими эффектами; персонажи разных рас/пола, экипировки и поз. `character-lab.html` пригоден для отдельной матрицы персонажей, а игровые сцены проверяют потоковую загрузку и HUD.

Для каждой сцены зафиксировать позицию и ориентацию камеры, FOV/дистанцию, время, погоду, NPC и их состояние, разрешение, UI scale и настройки. Снимать по несколько повторов оригинала, чтобы определить естественный разброс из-за анимации и времени. Сравнивать сначала состав и расположение объектов, затем геометрию/анимацию, материалы/цвет/свет/туман, эффекты, UI и звук. Использовать парное наложение, размеченные области и метрики сходства, пороги которых фиксируются после калибровки повторов. Разница WebGL и старого рендера делает точное совпадение пикселей непригодным как единственный критерий. Для регрессии WebClient до/после побитовое сравнение в детерминированных сценах остаётся полезным.

Для парных PNG уже есть `tools/compare-parity-png.mjs`: он выдаёт наложение, тепловую карту, ошибки по областям и диапазон между повторами оригинала. Без согласованных кадров он не выставляет статус «принято»; изображения держать вне Git.

В прогретой эталонной сцене требовать **0 видимых stand-in/stale моделей, 0 терминальных ошибок ресурсов и 0 отсутствующих обязательных объектов**. Учитывать причины из `StandIn.ts` и лимиты допуска `WorldRenderer3D.ts`; лимит повышать после установления пропуска и замера цены.

Для интерфейса сравнивать не только скриншот: размер/якорь/текстуры/шрифты, hover/pressed/disabled, фокус и клавиши, drag and drop, обновление после события сервера, закрытие и повторное открытие. Перевод мирового FrameXML в обычный режим выполнять после принятия P0 UI и отсутствия перекрытий со смешанными DOM областями; заглушки C API на этих путях должны иметь конкретную проверку или реализацию.

## 5. Опкоды и механики

Не расширять список по количеству опкодов ради процента. Для каждого расхождения трассировать цепочку **действие → CMSG → ответ/обновления SMSG → `WorldState` → UI**. Сверять схему с выбранным TrinityCore и генераторами. Тестировать фикстуры пакетов, затем живой результат на том же сервере. `webclientUnhandledOpcodes()` и `onPacketError` должны быть пусты на принятых сценариях; намеренно игнорируемые сообщения иметь документированную причину и отдельный счётчик.

Игровое решение остаётся на сервере. WebClient может предсказывать движение или показывать предварительную подсветку, но окончательные здоровье, урон, лут, деньги, квесты и права действия проверяются по авторитетному состоянию. Сравнение случайного урона или лута по точным байтам заменять проверкой допустимого исхода и последующего состояния.

## 6. Производительность без потери сходства

Первое действие — снять **новый** baseline этого дерева: минимум три одинаковых живых 60-секундных прохода для движения/разворота, города и толпы, интерьера и первого боя; отдельно холодная загрузка и прогретая сцена. `O` → запись фризов и `bench/analyze-live.mjs` уже дают разбивку кадра. Для A/B использовать `bench/run.mjs` только при совпадении fingerprint кода/ресурсов/браузера/GPU/настроек и валидном флаге сравнения. Закрепить replay fixtures перед применением формального 10×90-секундного контура.

Оптимизацию выбирать по горячей фазе текущего профиля: допуск объектов, построение terrain/WMO, матрицы/скелеты, draw submission, шейдеры/текстуры, HUD или gateway. Пространственный индекс, квоты сборки и LOD уже существуют; повторно внедрять их по названию задачи не нужно. Для кандидата сохранять одинаковые видимые объекты, геометрию и эффекты, затем сравнивать p95/p99 полного кадра, 1% low, потребление памяти и визуальные эталоны. Изолированный выигрыш CPU не доказывает ускорение полной игры.

Предлагаемый первый порог для согласования с целевым ПК: в 1920×1080/DPR 1, фиксированном профиле качества и после прогрева **p95 RAF ≤16,7 мс, p99 ≤33,3 мс и 0 кадров >100 мс за 60 секунд** во всех P0 сценах; отсутствие постоянного роста резидентных текстур/геометрии на трёх повторных маршрутах. Имеющаяся в проекте цель **120 FPS** — отдельный более строгий этап: p95 ≤8,33 мс на тех же определённых сценариях без снижения обязательной визуальной полноты. Числа утвердить после фиксации оборудования и нового baseline; исторические результаты не подтверждают их достижение.

## 7. Порядок исполнения для следующих задач Codex

1. **Закрепить среду и матрицу.** Сохранить fingerprint текущего дерева и источников, выбрать тестовый realm, оформить записи P0/P1 и 6–8 эталонных сцен. Сначала получить данные оригинального клиента и свежие живые записи WebClient.
2. **Создать профиль 3.3.5a и инструменты сравнения.** Зафиксировать настройки, сделать парные кадры/видео и метаданные сцен. Довести pending replay fixtures в `BenchmarkManifest.ts` до проверенных записей.
3. **Пройти P0 по одному сценарию.** Исправлять обнаруженные ошибки формата пакета, состояния мира, ввода и отображения. После каждого исправления запускать прямой `tsc --noEmit`, узкие source tests, браузерный сценарий и, когда нужен сервер, живую проверку. Не менять сгенерированные таблицы вручную.
4. **Довести штатный UI.** Проверить P0/P1 с включённой настройкой «Оригинальный интерфейс WoW» (или `?framexml=1`), заменить заглушки по измеренному использованию, завершить смешанные области и только после зелёных критериев сделать этот HUD обычным режимом.
5. **Закрывать визуальные расхождения по классу причины.** Приоритет: отсутствующий объект/неверная модель или анимация → камера/геометрия → свет/туман/материал → эффекты → мелкие детали. После каждого класса повторять соответствующие эталонные сцены.
6. **Оптимизировать подтверждённое узкое место.** Проводить сопоставимый A/B и проверку визуальной неизменности; обновлять baseline только после принятия результата. Параллельно закрывать P1/P2 по реальному использованию.
7. **Выпускной проход.** Все P0 и P1 сценарии зелёные, все обязательные эталонные сцены без S0/S1 расхождений, браузер и живой realm проверены, текущий FPS gate пройден. Оставшиеся S2 и P2 перечислены как конкретный backlog с воспроизведением и причиной приоритета.

Это план выполнения. Первым практическим срезом должна стать матрица эталонных сценариев и новый baseline: без них нельзя честно ранжировать остальные улучшения или назвать клиент похожим на оригинал по проверяемому критерию.
