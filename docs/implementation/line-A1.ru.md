### М4 «Привязка C API»

**Назначение.** Дать стоковому Lua (FrameXML и LoD-модули) ответ на вызов C-функции клиента 3.3.5 из данных, которые уже хранит `WorldClient`/`WorldStore`, а команды — отправить методом `WorldClient`. Без привязки имя, которое сток вызывает, но не определяет, отвечает счётчик-заглушка (nil), и стоковый код ведёт себя как «ничего нет»: серые пункты меню (`HasFullControl`), пустые подписи (`GetText`), вечно горящие кнопки (`IsAutoRepeatAction`).

**Кто отвечает на имя (порядок разрешения).**
1. `_G.__index` (`FrameXmlBoot.ts`, `setmetatable(_G, …)`): имя отвечает, только если оно в `__fxApi`. `installFrameXmlStubFloor` (`FrameXmlBoot.ts`, «installStubFloor») кладёт туда: имена, которые корпус вызывает и не определяет (`FrameXmlStubPlan.ts`), все `FRAMEXML_SEAM_NAMES` и все строки `FRAMEXML_NEUTRAL_API`. Имя вне множества даёт nil-глобал, вызов которого падает («attempt to call a nil value»): так ведут себя имена, живущие только внутри LoD-модулей, пока модуль не загружен.
2. `FRAMEXML_SEAM_BINDINGS` (`FrameXmlWorldSeam.ts`, объект `frameXmlWithPetBook({...})`): `Record<string, (seam, args) => readonly unknown[]>`; `[]` (`NOTHING`) — nil; `optional(v)` — `[v]` или nil. `FrameXmlBoot` регистрирует каждое имя как `__fxSeam_<name>`, `FRAMEXML_SEAM_PRELUDE` кладёт его в `__fxNeutralImpl` (кроме четырёх CVar-имён, у них своя обёртка над нейтральным ответом), метаметод `_G` отдаёт результат стоку. **Поздний ключ затеняет ранний** (комментарии в таблице: «After the trade skill's…», «Last: the one cursor…»); дубль ключа в литерале молча затеняет без ошибки.
3. Lua-прелюдии семейств (`FRAMEXML_LFD_PRELUDE`, `FRAMEXML_INSPECT_PRELUDE`, `FRAMEXML_MECHANICS_PRELUDE`…) стоят в `FRAMEXML_SEAM_PRELUDE` **после** общего цикла, поэтому обёртка над `impl.<Имя>` видит привязку шва как `base` (пример: `UnitHasRelicSlot` в `FrameXmlInspect.ts`, блок `local base = impl.UnitHasRelicSlot`).
4. Нейтральный пол (`FRAMEXML_NEUTRAL_API`, `FrameXmlNeutralApi.ts`): константа (`values: [...]`) или Lua-модуль (`values: undefined`, реализация в `FRAMEXML_NEUTRAL_PRELUDE`). Строка с тем же именем остаётся запасным ответом для холста без шва и в отчёте переписи; при появлении привязки шва привязка выигрывает.
5. Второй владелец: `installFrameXmlChatApi` (`FrameXmlChatApi.ts`) — соц. команды поверх `WorldClient` (`InviteUnit`, `UninviteUnit`, `PromoteToLeader`, `LeaveParty`, `StartDuel`, `InitiateTrade`) с помощниками `withWorld`, `unitToken`, `unitOrName`, `UNIT_TOKEN`. Правило «одно имя — один владелец»: его `reserved` по умолчанию равен `FRAMEXML_SEAM_NAMES` (`tests/framexml-chat-api.test.mjs`, проверка пересечения). Чат вне плана; команды группы из A1 кладутся в шов, а не сюда.
6. Методы виджетов (`GameTooltip:SetX`, `ColorSelect:SetColorRGB`): не M4, а таблицы методов `glue/GlueWidgets.ts` и `FRAMEXML_PROMOTED_METHODS`/`FRAMEXML_PROMOTED_STUBS` (`FrameXmlStubPlan.ts`); пункты 3.12 и 3.21 используют их же.

**Три идиомы реализации (выбирать по задаче).**
- **(a) Необязательные члены шва + чистые функции.** Образцы: `FrameXmlPlayerStatus.ts`, `FrameXmlUnitRelations.ts`. Модуль экспортирует интерфейс `FrameXmlX` с необязательными методами, чистые функции «слова мира → ответ» (`frameXmlPlayerFlagResting(flags)`, `frameXmlRaidIndex(group, selfGuid, guid)`) и таблицу `FRAMEXML_X_BINDINGS`. `FrameXmlWorldSeam` объявляет члены строками `member?: FrameXmlX["member"]` (блок «rest of the player-status family», «Combat and the group's relations»), `LiveWorldSeam` реализует их секцией с комментарием (`// ---- player status`, `// ---- combat and the group's relations`), `CannedWorldSeam` их не реализует (тогда ответ «нет»). Подходит для производных от полей/групп без состояния.
- **(b) Модель-объект.** Образец: `FrameXmlMechanicsModel` (`FrameXmlMechanics.ts`): класс с `context: { world(), self(), spell?() }`, `attach(pump)`/`detach()`, подписки `world.events.on(...)` и `pump.fire(...)`; шов держит `readonly mechanics` (`FrameXmlWorldSeam.ts` члены шва, `LiveWorldSeam.ts` конструктор, `CannedWorldSeam.ts` `mechanics = new FrameXmlMechanicsModel({ world: () => undefined, self: () => undefined })`), таблица привязок принимает `host` (`FrameXmlMechanicsHost`). Подходит для состояния, подписок, троттлинга, кешей. Так не раздуваются горячие файлы.
- **(c) Узкий `host`.** Образец: `FrameXmlArenaApi.ts` (`FrameXmlArenaHost { arena? }`): таблица привязок знает только тип хоста, а модель живёт в своём файле. Годится, когда модель уже отдельный класс.

**Типичные ошибки.**
- Булево вместо клиентского «1/nil»: часть стока сравнивает `== 1` (`UnitIsAFK` в `BNet.lua`), часть проверяет истинность; `GetPVPDesired` сравнивают с `1` и `0` (`UnitPopup.lua`), поэтому возвращать числа.
- `[]` и `[undefined]`: nil-ответ — пустой массив; массив с одним `undefined` — один nil, но шумнее в отчёте.
- Индексы: слот арены 1..3, а команды `WorldClient` принимают teamId из поля `PLAYER_FIELD_ARENA_TEAM_INFO_1_1`; сложность в C API 1-based, на проводе 0-based; индекс `UnitInRaid` 0-based; `CR_*` 1-based.
- Имя против токена юнита: `PromoteToAssistant(fullname, 1)` получает имя, `FocusUnit(unit)` токен; помощники `unitToken`/`unitOrName` есть в `FrameXmlChatApi.ts`.
- nil в арифметике и конкатенации: `GetBattlefieldStatData` обязан вернуть число (`columnData > 0`), иконка колонки — `""`, не nil (`icon..faction`), `GetArenaTeamRosterInfo`: `played - win` без защиты.
- Чтение, которое шлёт пакет: OnUpdate стока вызывает `RequestBattlefieldScoreData` каждый кадр; троттлить в `WorldClient` (правило ядра AntiDOS: 100 пакетов на опкод в секунду, `WorldSession.cpp:1751-1755`).
- Событие, запускающее собственный запрос: `PVPQUEUE_ANYWHERE_UPDATE_AVAILABLE` давал пинг-понг списков (комментарий в `FRAMEXML_SEAM_EVENTS.battlefieldList`); каждое новое событие проверять на цикл «событие → запрос → событие».
- Утечка подписок: `attach()` вызывается повторно; без `detach()` события дублируются (`FrameXmlMechanicsModel.attach` начинает с `this.detach()`).
- Раздувание горячих файлов: члены шва — одной строкой типа `FrameXmlX["member"]`; тело — в новом модуле.

### 3.19 — CVar: сохранение всех, `CVAR_UPDATE`, `SetModifiedClick`

### 3.26 — модуль `retail-talents` заменяет окно талантов, вкладка символов пропадает
**Подход:** сохранить доступ к стоковой вкладке «Символы» и при подменённом окне талантов. Причина дефекта: `retail-talents` присваивает `ToggleTalentFrame` и `PlayerTalentFrame_Toggle` своему `UniversalTalentFrame`, `createPatchedFrameXmlTalentOwner` (`FrameXmlWorldMount.ts` ≈1688-1740) вызывает захваченную функцию, не загружая `Blizzard_TalentUI`; расширение символов (`createFrameXmlGlyphExtension`, `FrameXmlGlyphOwner.ts` ≈225) передаётся только ленивому владельцу (`createLazyFrameXmlTalentOwner`, монтаж ≈3870-3877), а `GlyphFrame` в стоке не самостоятельное окно: его обработчик `ADDON_LOADED` делает его дочерним `PlayerTalentFrame` (`Blizzard_GlyphUI.lua:324-334`), вкладка «Символы» — четвёртая вкладка стоковой рамки талантов (`Blizzard_TalentUI.lua:201-219, :371-377`). Поэтому при подмене нет ни `PlayerTalentFrame`, ни вкладки. Решение по возрастанию сложности: **(1, рекомендуется)** оставить владельцем клавиши N подменённое окно, а привязки `TOGGLEINSCRIPTION`/`OpenGlyphFrame` (`ToggleGlyphFrame`, `USE_GLYPH`) направить в ленивого стокового владельца талантов, показывающего только вкладку символов: подмена окна талантов не затрагивает стоковую рамку, а `GlyphFrame_LoadUI` и хуки `FrameXmlGlyphOwner.ts` уже умеют открывать талант-рамку через контроллер (`frameXmlTalentOpen`, `toggleFrameXmlTalent` из `FrameXmlTalentController.ts`); **(2)** если `UniversalTalentFrame` уже содержит собственную вкладку символов (проверить модуль `retail-talents`, `tswow-install/modules/retail-talents/`, поиском `Glyph`), то задача сводится к тому, чтобы стоковые вызовы `GlyphFrame_*` не падали и не дублировались.
