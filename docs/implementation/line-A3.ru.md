## Общие механизмы

Линия A3 владеет тремя механизмами: **М1 «Серверное подтверждение»**, **М2 «Новый DBC-маршрут»**, **М3 «Курсор-цель»**. Все три описаны по коду, который есть сейчас; номера строк плавают, рядом всегда имя функции. Факты про ядро и стоковый Lua сверены (ссылки в тексте); чего не удалось проверить офлайн — в «Открытых вопросах» каждого механизма.

## М1 «Серверное подтверждение»

### Назначение
Сервер задаёт игроку вопрос, а ответ игрока — отдельный пакет. Оригинальный клиент показывает диалог (`StaticPopup`), сам считает «время жизни» и расстояние до NPC, а согласие уходит через C API. В WebClient уже есть отработанный образец — **призыв (`SMSG_SUMMON_REQUEST`)**: `WorldClient.summonRequest` → `FrameXmlPopupsModel.#observeSummon` → `CONFIRM_SUMMON` → `ConfirmSummon`/`CancelSummon` → `WorldClient.answerSummon` → `CMSG_SUMMON_RESPONSE`, а в native — секция «призывает вас в …» в `ui/InteractionPrompts.ts`. М1 — это тот же путь, размноженный на: `CONFIRM_BINDER` (2.03), `CONFIRM_TALENT_WIPE` (2.04), `INSTANCE_LOCK_START/STOP` (2.09), `END_REFUND` и `CONFIRM_REFUND_*` (2.10).

### Проверенные факты (общие для всех применений)
- **Два владельца одного вопроса.** Пока стоковые попапы не «опубликованы» (`FrameXmlPopupsModel.popupsOwned === false`), отвечает native (`InteractionPrompts.ts`), события стока молчат. С публикации (`popupsOwned = true` → `tick()`) показывается всё, что ещё ждёт ответа. `frameXmlPopupsPublished()` (FrameXmlPopupsController) — то, что спрашивает native, чтобы не показать второй вопрос. Ответ через C API работает **только** пока владеет сток и модель не «приглушена» (`#command`: `!#muted && #popupsOwned`).
- **Событие берёт данные не из полезной нагрузки.** `UIParent.lua` (события `CONFIRM_BINDER` 893, `CONFIRM_TALENT_WIPE` 880-892, `INSTANCE_LOCK_START/STOP` 872-878, `END_REFUND` 762-768) передаёт аргументы в `StaticPopup_Show`, а остальное диалог читает C API: `GetInstanceLockTimeRemaining()`, `GetInstanceInfo()`, `CheckBinderDist()`, `CheckTalentMasterDist()`. Значит, C API обязан отвечать по тем же данным, что и событие.
- **Диалоги стока** (`StaticPopup.lua`): `CONFIRM_BINDER` (2519: OnAccept `ConfirmBinder()`, OnUpdate скрывает по `CheckBinderDist()==false`, текст `CONFIRM_BINDER = "%s станет вашим новым домом. Согласны?"`, GlobalStrings.lua:1802); `CONFIRM_TALENT_WIPE` (2498: `hasMoneyFrame`, OnAccept `ConfirmTalentWipe()`, OnUpdate `CheckTalentMasterDist()`, OnCancel закрывает `PlayerTalentFrame`); `INSTANCE_LOCK` (2422-2496: `GetInstanceLockTimeRemaining()` возвращает **4 значения** `секунды, isPreviousInstance, encountersTotal, encountersComplete`; OnShow скрывает диалог при `<=0`; OnUpdate ведёт свой `lockTimeleft`; Accept → `RespondInstanceLock(true)`, Cancel → `RespondInstanceLock(false)`, по таймауту — тихо закрывается; тултип строк боссов — `GetInstanceLockTimeRemainingEncounter(i)` → `bossName, texture, isKilled`, `InstanceLock_OnEnter` лежит в `LFRFrame.lua:684`); `END_REFUND` (2384: `EndRefund(self.data)`).
- **События, у которых есть аргументы:** `CONFIRM_BINDER(areaName)`, `CONFIRM_TALENT_WIPE(costCopper)` (диалог вызывает `MoneyFrame_Update(dialog:GetName().."MoneyFrame", arg1)`), `END_REFUND(arg1)` → `dialog.data = arg1`; `INSTANCE_LOCK_START` без аргументов.
- **Все имена событий уже зарегистрированы `UIParent`** (`UIParent.lua:149,161-166`), поэтому гейт `frameXmlPopupsGate` (`FrameXmlPopupsOwner.ts`: `FRAMEXML_POPUPS_EVENTS.every(event => uiParent.registeredEvents.has(event))`) пропустит их.
- **Ядро.** `SMSG_BINDER_CONFIRM` = `u64 guid` (`Player::SetBindPoint` Player.cpp:9702, `BinderConfirm::Write` MiscPackets.cpp:37). `MSG_TALENT_WIPE_CONFIRM` сервер→клиент = `u64 guid, u32 cost` (`RespecWipeConfirm::Write` TalentPackets.cpp:22), клиент→сервер = `u64 guid` (`ConfirmRespecWipe::Read`); сервер шлёт тот же пакет с **guid = 0** и ценой, когда сбрасывать нечего (`HandleTalentWipeConfirmOpcode` SkillHandler.cpp:83-87). `SMSG_INSTANCE_LOCK_WARNING_QUERY` = `u32 60000, u32 encounterMask, u8 0` (`InstanceMap::Add` Map.cpp:4155-4160), ответ `CMSG_INSTANCE_LOCK_RESPONSE` = `u8 accept` (`HandleInstanceLockResponse` MiscHandler.cpp:1545: accept → `BindToInstance`, иначе `RepopAtGraveyard`; без ответа за 60 с ядро **само** привязывает, `Player::Update` Player.cpp:1313-1320).
- **Расстояние.** `INTERACTION_DISTANCE = 5.0` (ObjectDefines.h:24) плюс сумма радиусов досягаемости (`IsWithinDistInMap`) — то, что использует существующий `spiritHealerInRange` (`FrameXmlPopupsContext`). Для binder/talent-master делается то же с флагами `UNIT_NPC_FLAG_INNKEEPER=0x10000`, `UNIT_NPC_FLAG_TRAINER=0x10` (UnitDefines.h:253,241).

### Форма (типы и функции)
1. **`WorldClient`** (`src/world/WorldClient.ts`): поле-ожидание, как `summonRequest`; парсер в `*Protocol.ts` (не в горячем файле); событие в `EventBus.ts` (для native и тестов); метод-ответ; сброс в `close()` и при `SMSG_NEW_WORLD`; истечение в `expireInteractionRequests()`.
   - `binderConfirm?: { guid: bigint; areaName?: string; receivedAt: number }`, `confirmBinder()`/`declineBinder()`;
   - `talentWipeConfirm?: { guid: bigint; cost: number; receivedAt: number }`, `answerTalentWipe(accept)` (`confirmTalentWipe(guid)` остаётся низкоуровневой отправкой);
   - `instanceLock?: { expiresAt: number; encounterMask: number; previouslySaved: boolean; mapId: number; difficulty: number }`, `respondInstanceLock(accept)`;
   - `refundInfo: Map<bigint, RefundInfo>` и `requestRefundInfo(guid)`/`refundItem(guid)` (2.10).
2. **Билдеры** (`world/InstanceProtocol.ts`, `CharacterProgressProtocol.ts`, `ItemProtocol.ts`): `buildBinderActivate(guid)` = `u64`; `buildInstanceLockResponse(accept)` = `u8`; `buildItemRefund(guid)` = `u64`.
3. **Модель стока** (`framexml/FrameXmlPopups.ts`): слот `#binder = pending<…>()` / `#talentWipe` / `#instanceLock`; `#observeX(world, now)` = `#track(slot, world.x, now, hide?)` + `#show(slot, now, "EVENT", args)`; методы C API; строки в `FRAMEXML_POPUPS_BINDINGS` (`ConfirmBinder`, `CheckBinderDist`, `ConfirmTalentWipe`, `CheckTalentMasterDist`, `GetInstanceLockTimeRemaining`, `GetInstanceLockTimeRemainingEncounter`, `RespondInstanceLock`, `EndRefund`); имена событий в `FRAMEXML_POPUPS_EVENTS`; имена диалогов в `FRAMEXML_POPUPS_DIALOGS` (`FrameXmlPopupsOwner.ts`, гейт требует, чтобы каждый существовал в `StaticPopupDialogs`).
4. **Интерфейс мира** `FrameXmlPopupsWorld` (тот же файл) — расширить полями; `WorldClient` удовлетворяет ему структурно. **Двойник для тестов** — `FrameXmlCannedPopupsWorld` (`FrameXmlPopupsCanned.ts`): методы `binder()`, `talentWipe(cost)`, `instanceLock(ms)`, журнал `calls`.
5. **Native** (`ui/InteractionPrompts.ts`): секция в `showInteractionPrompts` — `section(...)` + `button(row, label, state, current, run)`; обязательно добавить новое поле в `requestsUnchanged` и в условие «нечего показывать», иначе панель не перерисуется/не скроется; обратный отсчёт — `countdown(row, deadline)`.
6. **Дистанция и таймаут в C API:** `CheckBinderDist`/`CheckTalentMasterDist` = `NPC жив и в поле зрения && расстояние <= 5 + reach`; при `false` сток скроет диалог, а `WorldClient` должен **сам** снять ожидание (иначе `#track` никогда не увидит «исчезновения» и на следующем NPC будет повторный показ).

### Пошаговый способ применения (чек-лист)
1. Сверить пакет с ядром (`file:line`) и с стоковым Lua (какие C API вызывает диалог, сколько значений они возвращают).
2. Парсер + билдер + тест байтов (`tests/*-protocol.test.mjs`).
3. `WorldClient`: ожидание, событие, ответ, сброс (`close`, `NEW_WORLD`, дистанция/таймаут).
4. `FrameXmlPopups.ts`: слот, `#observe`, привязки, события, диалоги; `FrameXmlPopupsCanned.ts`.
5. Native-секция в `InteractionPrompts.ts` (+ `requestsUnchanged`).
6. Тест на `FrameXmlPopupsModel` (сценарий «до публикации — тишина, публикация показывает один раз, ответ уходит один раз, второй ответ ничего не находит, скрытие по событию») и на реальном `WorldClient` через фальшивое соединение (образец — `tests/framexml-popups-seam.test.mjs`).
7. MPQ vertical: диалог реально строится в стоковой вертикали (`FRAMEXML_POPUPS_DIALOGS` в гейте).

### Типичные ошибки
- **`TalentFrame_LoadUI()` в обработчике `CONFIRM_TALENT_WIPE`** (`UIParent.lua:886`) вызывает `UIParentLoadAddOn("Blizzard_TalentUI")` → `LoadAddOn` отвечает `NOT_READY`, а `UIParentLoadAddOn` показывает `message(...)` (`UIParent.lua:234-243`). Нужно либо загрузить ленивый владелец талантов (`createLazyFrameXmlTalentOwner`) до `fire`, либо подменить `TalentFrame_LoadUI` в прологе.
- **guid = 0 в `MSG_TALENT_WIPE_CONFIRM`** — «сбрасывать нечего»; диалог показывать нельзя (`CheckTalentMasterDist` мгновенно скрыл бы его).
- **Идентичность объекта.** `#track` сравнивает ссылки; новый объект-ожидание на каждый пакет заставит показать диалог повторно. Заменять объект только при новом пакете.
- **Ответ дважды.** Сервер ждёт один ответ (`CMSG_INSTANCE_LOCK_RESPONSE` без ожидания = запись в лог `tried to bind himself…`); сначала снять ожидание, потом слать.
- **Таймер `INSTANCE_LOCK`.** Стоковая OnUpdate ведёт свой обратный отсчёт от `GetInstanceLockTimeRemaining()`; отдавать нужно **остаток**, а не 60 с, иначе после `/reload` таймер начнётся заново.
- **Gate-проба.** Пробы гейта не должны вызывать `ConfirmTalentWipe` и др.: `muted()` уже гасит ответы, но не добавляйте новые диалоги в Lua-пробу без нужды.

### Открытые вопросы
- Что оригинальный клиент передаёт в `CONFIRM_BINDER` первым аргументом. Стоковый текст `%s станет вашим новым домом` — название места, а пакет несёт только guid. Решение по умолчанию: название подзоны игрока в точке привязки (ядро привязывает по позиции игрока, `Spell::EffectBind`, SpellEffects.cpp:5876; ID зоны придёт в `SMSG_PLAYER_BOUND`). Как проверить: живой заход у трактирщика (14.xx).
- Сколько живёт запрос `CONFIRM_BINDER` в оригинале: сток закрывает его только по дистанции и Esc. Решение: держать до ответа/дистанции/смены карты.

## М2 «Новый DBC-маршрут»

### Назначение
Данные клиента (DBC датасета) недоступны браузеру напрямую; gateway читает таблицу, строит компактный JSON и отдаёт `GET /dbc/<имя>?v=<версия формы>`, браузерный клиент забирает его один раз. Образец — `CharTitleMetadata.ts` (gateway) + `CharTitleClient.ts` (browser) + маршрут `/dbc/char-titles` в `Gateway.ts`.

### Проверенные факты
- **Маршрут** (`Gateway.ts`, блок `pathname === "/dbc/char-titles"`, ~28 строк): `originAllowed` (403) → `?v=` совпадает с константой формы (400) → `indexes.charTitles ??= loadCharTitles(dir).then(JSON.stringify)` → `200`, `cache-control: no-store`, `content-type: application/json` → при ошибке индекс сбрасывается, ответ 500. Индексы живут в `class DatasetIndexes` (`Gateway.ts` ~658); `reset()` обнуляет **все** поля, поэтому `DatasetFingerprint` (пересборка датасета) сам сбрасывает и новые. Новое поле-промис = одна строка в классе.
- **Раскладка.** `src/generated/dbcLayouts.ts` (79 таблиц, генератор `tools/generate-dbc-layouts.mjs` из `tools/dbd/*.dbd`, список `tools/dbd-tables.mjs`; `npm run build` падает при дрейфе) **не содержит** `AreaTrigger`, `DurabilityCosts`, `DurabilityQuality`, `CharTitles`, `SpellDispelType`, `GMSurvey*`. Таблица `Spell` в нём есть: поле `DispelType` (индекс 2), `Targets` (16), `AttributesExD` (8), `ImplicitTargetA` и т.д.
- **Два способа добавить таблицу.** (а) `.dbd` в `tools/dbd/`, строка в `DBD_TABLES`, `npm run dbc:generate`, затем `openDbcFile(dir, "Таблица")` (`gateway/Dbc.ts`, `.int(row, "Поле", i)`, `.locstring`). Тяжело: правка сгенерированного файла и лицензионная запись. (б) Фиксированная раскладка по `DBCfmt.h` с проверкой заголовка — как `CharTitleMetadata.readFixed`: сверяет `fieldCount`, `recordSize`, конец блока строк и падает с `DbcError` при несовпадении. **Рекомендация для малых таблиц A3 — (б)**, с выносом `readFixed` в `gateway/DbcFixed.ts` (сейчас функция приватна в `CharTitleMetadata.ts`; вынос — механический, тест `tests/framexml-titles.test.mjs` должен остаться зелёным).
- **Формат TC для наших таблиц** (`shared/DataStores/DBCfmt.h`, `DBCStructure.h`): `AreaTriggerEntryfmt = "niffffffff"` — `ID, ContinentID, X, Y, Z, Radius, BoxLength, BoxWidth, BoxHeight, BoxYaw` (10 полей, 40 байт; в датасете 1220 записей, файл побайтно равен `dbc_source`); `DurabilityCostsfmt = "niiiiiiiiiiiiiiiiiiiiiiiiiiiii"` — `ID, WeaponSubClassCost[21], ArmorSubClassCost[8]` (30 полей, 120 байт; в датасете файл 35,2 КБ); `DurabilityQualityfmt = "nf"` — `ID, Data` (8 байт).
- **Браузерный клиент** `CharTitleClient`: константа пути с `?v=`, валидатор ответа (`charTitleRows`), `load()` с мемоизацией промиса, `onLoaded`. **Дефект образца:** «неудачный запрос не повторяется» (комментарий в файле) — та же болезнь у `FactionClient.ts:41-44`, `TalentClient.ts:55-59` (пункт 5.16). Для новых клиентов повтор обязателен: устаревший процесс gateway отвечает 404 на новый маршрут, а сбой сети не должен отключать механику до перезагрузки страницы.

### Форма
1. **gateway:** `src/gateway/<X>Metadata.ts` — `export const <X>_VERSION = 1`, интерфейс строки, `load<X>(dbcDirectory): Promise<Catalog>` (чистая функция над буфером — тестируется без gateway); поле в `DatasetIndexes`; блок маршрута рядом с `char-titles`. Чтобы не раздувать горячий `Gateway.ts`, для **новых** маршрутов A3 добавить `gateway/CatalogRoutes.ts`: таблица `{ pathname, version, load }` и **одно** место подключения в `Gateway.ts` (`indexes.catalogs ??= new Map()`; ключ = pathname; поле сбрасывается общим `reset()`); существующие маршруты не трогать.
2. **browser:** `src/browser/CatalogClient.ts` — общий `RetryingCatalogClient<T>(origin, path, validate, options)`: `load()` (мемоизация, **не** мемоизировать провал), повтор с задержками 2 → 5 → 15 → 60 с (потолок), потолок попыток 6, затем остановка до `retry()` (при следующем монтировании мира), отдельная обработка 404 («старый gateway»: один повтор через 15 с), `onLoaded`, `state: "idle" | "loading" | "ready" | "failed"`, часы и `fetch` внедряются (для теста). Клиенты `AreaTriggerClient`, `DurabilityClient` — тонкие обёртки со своим валидатором.
3. **Версия кеша:** число в `<X>_VERSION` (gateway) и то же в браузерной константе пути; тест, «сшивающий» их (образец — `tests/framexml-titles.test.mjs`). Менять номер при любой смене формы ответа.

### Пошаговый способ
1. Найти `fmt` в `DBCfmt.h`, посчитать байты, записать в комментарий вместе с измеренным числом записей датасета.
2. `gateway/<X>Metadata.ts` + чистый тест на **реальном файле датасета** (`F:/tswowRoot/tswow-install/modules/default/datasets/dataset/dbc/<X>.dbc`, тест пропускается, если файла нет).
3. Маршрут (или строка в `CatalogRoutes.ts`) + тест маршрута (поднять обработчик на порту 0, как это делают `tests/gateway-*.test.mjs`; мутация: убрать проверку `?v=`).
4. Браузерный клиент + тест повтора (двойник `fetch`: два сбоя, затем успех → строки загружены; после потолка — `failed`, `retry()` оживляет).
5. Подключение: клиент создаётся и запускается **до** первого использования (при монтировании мира), никогда не из чтения C API.
6. Живая проверка: gateway нужно перезапустить владельцу (пункт 0.1), пока процесс старый — новый маршрут отвечает 404, клиент обязан повторить и не падать.

### Файлы
`src/gateway/<X>Metadata.ts`, `src/gateway/DbcFixed.ts` (вынос), `src/gateway/CatalogRoutes.ts`, `src/gateway/Gateway.ts` (одна точка подключения), `src/browser/CatalogClient.ts`, `src/browser/<X>Client.ts`.

### Тесты
`tests/<x>-metadata.test.mjs` (реальный DBC), `tests/catalog-client.test.mjs` (повтор), `tests/gateway-catalog-routes.test.mjs` (403/400/200/500). Мутации: неверный `fieldCount` в раскладке → `DbcError` (тест ловит); убрать сброс провала → тест «два сбоя, затем успех» падает.

### Типичные ошибки
- Считать, что «повтор есть»: у образца `load()` действительно можно вызвать снова (`#pending` сбрасывается в `finally`), но его вызывают **один раз** при монтировании мира и никто не планирует повтор — после сбоя таблица пуста до перезагрузки страницы. Повтор должен планировать сам клиент.
- Забыть сбросить индекс при ошибке чтения (следующий запрос получит тот же отклонённый промис).
- Сериализовать в JSON `bigint`/`NaN`: в AreaTrigger встречаются угловые значения вне [0, 2π] (`yaw` 10 и 90 у трёх записей) — не нормализовать, ядро считает `sin/cos` от сырого значения.
- Читать `float` через `readInt32LE`.

### Открытые вопросы
- Нужен ли gzip: JSON AreaTrigger в виде массивов ≈ 70 КБ; по существующим маршрутам сжатия нет — не вводить.

## М3 «Курсор-цель»

### Назначение
Режим, в котором «следующий клик» завершает уже начатое действие: заклинание или предмет ждёт цель — предмет в сумке/экипировке/слоте обмена, юнит, игровой объект, точку земли — либо включён режим ремонта. В оригинале это один курсор заклинания (`SpellIsTargeting`) плюс режим ремонта (`InRepairMode`); стоковый Lua лишь спрашивает и передаёт клик в C.

### Что уже есть (три отдельных «владельца» одного курсора)
1. **Земля.** `game/GroundTarget.ts`: `beginGroundTarget`, `pendingGroundTarget`, `pendingGroundTargetItem`, `cancelGroundTarget`; маршрутизаторы `requestSpellCast(spellId, send)` (заклинание) и `requestItemUse(ref, send)` (предмет) — **перехватывают использование**, если контракт цели говорит «земля» (`requiredTargetMode === 3`), и взводят курсор вместо отправки; клик в мир обрабатывает `input/Controls.ts` (`confirmGroundTargetAt`); отмена — Esc или ПКМ (`stopTargeting` в `Controls.ts`, шаг `SpellStopTargeting` меню игры).
2. **Чары рецепта.** `FrameXmlTradeSkillModel.#targeting` + `targetItem(guid)`; `SpellCanTargetItem`, `SpellIsTargeting`, `SpellStopTargeting` в `FRAMEXML_TRADESKILL_BINDINGS`; `LiveWorldSeam.useContainerItem` (~3428) и `pickupInventoryItem` (~3756) первым делом зовут `tradeSkill.targetItem(guid)`; отправка — `craft.castOnItem` → `WorldClient.castSpellOnItem`.
3. **Символ.** `FrameXmlGlyph.ts`: `glyphs.targeting`, поверх привязок торговых навыков (`FRAMEXML_GLYPH_BINDINGS.SpellIsTargeting` отвечает первым и передаёт дальше).

Итог: цепочка обёрток над одним именем C API, порядок задан позицией в `FRAMEXML_SEAM_BINDINGS` (`FrameXmlWorldSeam.ts` ~2104-2138). Ещё один слой — `FrameXmlGameMenuOwner.ts`/`Controls.ts` (`frameXmlNativeTargeting`, `runFrameXmlNativeEscape`).

### Проверенные факты (стоковый клик и ядро)
- **Слот сумки** `ContainerFrameItemButton_OnClick` (ContainerFrame.lua:693): `if SpellCanTargetItem() then UseContainerItem(bag, slot)` — клик по сумке при ожидающем заклинании идёт через **`UseContainerItem`**; иначе `PickupContainerItem`. **Слот экипировки** `PaperDollItemSlotButton_OnClick` (PaperDollFrame.lua:1232): всегда `PickupInventoryItem(slot)` — то есть **внутри C-реализации** `PickupInventoryItem` при `SpellIsTargeting()` целится предметом, а при ремонте — чинит; так же `PickupContainerItem` в режиме ремонта. Проверить сток нельзя (C-код), поэтому правило такое: **все три привязки** (`UseContainerItem`, `PickupContainerItem`, `PickupInventoryItem`) сперва спрашивают курсор.
- **Юнит.** Стоковые рамки: `SECURE_ACTIONS.target` (SecureTemplates.lua:402): `SpellIsTargeting() → SpellTargetUnit(unit)`, `CursorHasItem() → DropItemOnUnit(unit)`, иначе `TargetUnit`; ПКМ «menu» при `SpellIsTargeting()` отменяет (`SecureUnitButton_OnClick`, :562-571). После любого защищённого действия: `if SpellCanTargetItem()` и заданы `target-bag/target-slot/target-item` → `UseContainerItem`/`UseInventoryItem`/`SpellTargetItem(item)` (:536-552).
- **Слот обмена.** `TradeFrame.xml:93-99`: клик по кнопке получателя (`TradeRecipientItem<N>ItemButton`) → `ClickTargetTradeButton(id)`; клик по своей → `ClickTradeButton(id, isRightButton)`. `TRADE_ENCHANT_SLOT = MAX_TRADE_ITEMS = 7` в Lua (`TradeFrame.lua:3`), в пакете это слот **6** (`TRADE_SLOT_NONTRADED`, `SpellCastTargets::Update` Spell.cpp:455).
- **Клиентские подтверждения чар:** события `BIND_ENCHANT` (`BindEnchant()`), `REPLACE_ENCHANT(old, new)` (`ReplaceEnchant()`), `TRADE_REPLACE_ENCHANT` (`ReplaceTradeEnchant()`), `TRADE_POTENTIAL_BIND_ENCHANT` (OnCancel `ClickTradeButton(TRADE_ENCHANT_SLOT, true)`), `CURRENT_SPELL_CAST_CHANGED` скрывает все (`UIParent.lua:750-780`) — это «вопросы клиента», а не сервера: они возникают **между выбором предмета и отправкой**.
- **Пакет.** `CMSG_CAST_SPELL` = `u8 castCount, u32 spellId, u8 castFlags, SpellCastTargets` (`HandleCastSpellOpcode` SpellHandler.cpp:336); `CMSG_USE_ITEM` = `u8 bag, u8 slot, u8 castCount, u32 spellId, u64 itemGuid, u32 glyphIndex, u8 castFlags, SpellCastTargets` (:75-86). `SpellCastTargets::Read` (Spell.cpp:144): `u32 mask`; при `UNIT|UNIT_MINIPET|GAMEOBJECT|CORPSE_ENEMY|CORPSE_ALLY` — packed guid объекта; при `ITEM|TRADE_ITEM` — packed guid предмета; `SOURCE_LOCATION` — packed guid транспорта + 3 float (или 3 float); `DEST_LOCATION` то же; `STRING` — cstring. Флаги (`SpellDefines.h:177-198`): UNIT 0x2, ITEM 0x10, SOURCE 0x20, DEST 0x40, CORPSE_ENEMY 0x200, GAMEOBJECT 0x800, TRADE_ITEM 0x1000, STRING 0x2000, GAMEOBJECT_ITEM 0x4000, CORPSE_ALLY 0x8000, UNIT_MINIPET 0x10000. `TRADE_ITEM`: «guid» — это **номер слота** (`m_itemTargetGUID.GetRawValue() == TRADE_SLOT_NONTRADED`), сервер берёт `GetTraderData()->GetItem(6)`. В `Spell.dbc` датасета (72 028 строк) **флаг TRADE_ITEM не встречается ни разу** (0 строк): его ставит клиент по месту предмета; флаг `ITEM` — у 768 строк.
- **Контракт целей уже посчитан на gateway.** `SpellMetadata` (gateway) несёт `requiredTargetMode` (`Unit=1, Item=2, Ground=3, Unknown=0`), `explicitTargetMask`, `clientSelectionMask` (`ExplicitSpellTargetContract.ts`: биты Item, GameObject, Corpse, Destination), `supportsExplicitTarget`. Сейчас `Ground` использует `GroundTarget.ts`, а `Item` никто не читает. Не поддержаны контрактом: `GameObjectItem` (взлом замка), слоты обмена, строки, символы.
- **Зачем разделение на классы** (замеры `A3/probe-item-targets.out.txt`): эффекты среди 768 строк с `ITEM`: `ENCHANT_ITEM` 601, `ENCHANT_ITEM_TEMPORARY` 154 (яды «Смертельный яд» 2823…, точила «Заточка клинка» 2828, масла, приманки), `PRISMATIC` 5, `FEED_PET` 2 (6991), `DISENCHANT` 2 (13262), `PROSPECTING` 2 (31252), `MILLING` 2 (51005), прочие 27; 19 строк `OPEN_LOCK` с `ImplicitTargetA = 26` (Взлом замка 1804, отмычки Кадгара 491/857/10165/10166, ключи 19646…); 203 строки с `GAMEOBJECT_ITEM 0x4000`.

### Форма (единый владелец)
Новый DOM-free модуль **`src/browser/game/SpellCursor.ts`** — «хаб курсора»:
```
type CursorKind = "ground" | "item-spell" | "item-use" | "recipe" | "glyph" | "unit-spell" | "repair" | "wrap";
interface SpellCursorState { kind; spellId?: number; source?: ItemRef; wrap?: ItemRef; armedAt: number; world: object }
interface SpellCursorProvider {           // тот, кто умеет «принять клик»
  active(): boolean; canTargetItem(): boolean; canTargetUnit(unit): boolean;
  targetItem(target: ItemTarget): "consumed" | "refused" | "ignored";   // предмет из сумки/экипировки/обмена
  targetUnit(guid: bigint): "consumed" | "refused" | "ignored";
  cancel(): boolean;
}
```
- Провайдеры в порядке ответа: `glyph`, `recipe` (обёртка над `FrameXmlTradeSkillModel`), `item-spell` (**новый**), `ground` (обёртка над `GroundTarget.ts`), `repair` (**новый**). Хаб один раз строит `SpellIsTargeting`, `SpellCanTargetItem`, `SpellCanTargetUnit`, `SpellTargetItem`, `SpellTargetUnit`, `SpellStopTargeting`, `InRepairMode`, `ShowRepairCursor`, `HideRepairCursor`, `ClickTargetTradeButton`; **цепочка обёрток** `FRAMEXML_GLYPH_BINDINGS`/`FRAMEXML_TRADESKILL_BINDINGS` для этих имён заменяется одной привязкой хаба, помещённой в таблицу привязок после них (иначе двое отвечают на одно имя).
- **Вход в режим — только через два существующих маршрутизатора**, которые уже перехватывают использование: `requestSpellCast` (`GroundTarget.ts`) и `requestItemUse`. Их решение расширяется: контракт `clientSelectionMask & Item` (или `requiredTargetMode === Item`) → `armItemSpell(spellId, source?)`; предмет-обёртка (`ITEM_FLAG_IS_WRAPPER`, ItemTemplate.flags & 0x200) → `armWrap(item)`; `GameObjectItem` (Взлом замка) → `armItemSpell` с признаком «предмет или объект».
- **Завершение** — в `LiveWorldSeam` три метода (`useContainerItem`, `pickupContainerItem`, `pickupInventoryItem`) и `clickTargetTradeButton` первым делом вызывают `cursor.targetItem(...)`; в native — обработчики кликов `ui/Bags.ts`, `ui/ItemSlots.ts`, слоты экипировки `ui/CharacterSheet.ts`, окно обмена `ui/Social.ts` (там же, где сейчас клик поднимает предмет); юнит — `input/Controls.ts` (клик по миру) и рамки `ui/UnitFrames.ts`.
- **Отправка:** `buildCastSpell` уже умеет юнит/землю, `buildCastSpellOnItem`/`buildCastSpellOnGameObject`/`buildCastSpellOnUnit` есть в `SpellProtocol.ts`; **не хватает** `buildUseItem` с целью-предметом/юнитом (`ItemProtocol.ts:155` пишет только «без цели» и «земля») и `TARGET_FLAG_TRADE_ITEM` с номером слота. Общий помощник `writeSpellTargets({ unit?, gameObject?, item?, tradeSlot?, destination?, string? })` в `SpellProtocol.ts` — единственное место, где пишется хвост `SpellCastTargets`; `buildUseItem`/`buildCastSpell*` его используют.
- **Курсор-картинка** (5.17): состояние хаба публикует `cursorKind` для `input/Controls.ts` (`Controls.ts:385-510`); отдельной работой не считается.
- **Отмена:** ПКМ по миру, Esc (шаг «SpellStopTargeting» в `FrameXmlGameMenuOwner`), смена карты (`onWorldChanged`), смерть, `CURRENT_SPELL_CAST_CHANGED` (скрывает `BIND_ENCHANT`/`REPLACE_ENCHANT`), новое использование другого предмета. **Пакета отмены нет**: до клика на сервер ничего не ушло.

### Пошаговый способ применения
1. Вынести существующие «ожидания» (`recipe`, `glyph`, `ground`) за интерфейс провайдера **без смены поведения** — существующие тесты (`framexml-tradeskill*`, `glyph*`, `ground-target*`) остаются зелёными. Это отдельный срез.
2. Ввести хаб и переключить привязки C API на него.
3. Добавить провайдеры `item-spell` (предметы/заклинания с целью-предметом) и `repair`.
4. Расширить `requestSpellCast`/`requestItemUse`; добавить билдеры хвоста целей.
5. Подключить клики (стоковые методы шва + native).
6. Клиентские подтверждения чар (`BIND_ENCHANT`, `REPLACE_ENCHANT`) — после выбора цели, до отправки (событие + `BindEnchant()`/`ReplaceEnchant()` продолжают отправку).

### Типичные ошибки
- Потерять клик: провайдер должен вернуть «consumed» **даже при отказе** (как `tradeSkill.targetItem`: неподходящий предмет — ошибка `SPELL_FAILED_BAD_TARGETS`, курсор остаётся).
- Двойная отправка (клик по слоту и `UseContainerItem` от рамки макроса).
- `TARGET_FLAG_TRADE_ITEM` без номера слота 6 или с guid предмета — ядро молча отклонит.
- Курсор земли и курсор предмета одновременно: новый взвод обязан снять прежний (`beginGroundTarget` уже обнуляет `groundTargetItem`, повторить для остальных).
- Смешать «использование предмета» (`buildUseItem`) и «заклинание из книги» (`buildCastSpell`): предмет с собственной целью — `CMSG_USE_ITEM` (иначе ядро не спишет заряд и не привяжет предмет), заклинание рецепта/книги — `CMSG_CAST_SPELL`.

### Открытые вопросы
- Как оригинал выбирает между `ITEM` и `TRADE_ITEM` — по расположению предмета (слот получателя в окне обмена). Решение: клик по кнопке получателя (`ClickTargetTradeButton(7)`) даёт `TRADE_ITEM` со слотом 6; остальные клики — `ITEM`. Проверка — живая (14.xx) с двумя клиентами.
- Порядок действий C-функций при ремонте (`PickupInventoryItem` в режиме ремонта) выведен из стокового Lua (в нём ветки ремонта нет); подтвердить можно только в игре.

### 2.01 — Area triggers (`CMSG_AREATRIGGER`)
- **Подход.** Клиент читает `AreaTrigger.dbc` через маршрут gateway (М2), каждый кадр после физики проверяет, лежит ли позиция персонажа внутри объёма на текущей карте, и на **переходе «снаружи → внутри»** шлёт `CMSG_AREATRIGGER(u32 id)` один раз. Всё, что делает вход (телепорт, таверна, исследование, флаг, скрипты модулей), решает сервер; из клиентской части нужны только отправитель и уже существующие ответы (`SMSG_NEW_WORLD`, `SMSG_TRANSFER_ABORTED`, `SMSG_AREA_TRIGGER_MESSAGE`, `SMSG_RAID_GROUP_ONLY`, `SMSG_CORPSE_NOT_IN_INSTANCE`, флаг отдыха `PLAYER_FLAGS_RESTING` → `IsResting`). Дефект подтверждён: `OPCODES.CMSG_AREATRIGGER` есть только в `generated/protocol-data/opcodes.ts`, сборщика и вызова нет.
- **Сверено.**
  - Ядро принимает пакет так (`HandleAreaTriggerOpcode`, MiscHandler.cpp:725-888): игнор при `IsInFlight()`; неизвестный id — игнор; `Player::IsInAreaTriggerRadius` (Player.cpp:2370): другая карта — отказ; **сфера** при `Radius > 0`: `GetDistance(x,y,z) - GetCombatReach() <= Radius` (Object.cpp:1187, досягаемость игрока `1.5 * scale`, `ObjectDefines.h:40`), **коробка** иначе: `IsWithinBox(center{X,Y,Z, yaw=BoxYaw}, L/2, W/2, H/2)` (Position.cpp:86): вращение `2π − yaw`, затем `|dx'| ≤ L/2`, `|dy'| ≤ W/2`, `|dz| ≤ H/2`, без запаса. Локальные оси: `lx = dx·cos(yaw) + dy·sin(yaw)`, `ly = −dx·sin(yaw) + dy·cos(yaw)`, `lz = dz` (координаты сервера X/Y, как в пакетах движения и `WorldPosition` клиента — менять оси местами, как в wowee, **не нужно**).
  - Далее сервер: скрипт TSWoW `AreaTrigger.OnTrigger` (может отменить), условия, квест «исследовать», таверна (`REST_FLAG_IN_TAVERN`), BG/OutdoorPvP (`BattlegroundWS.cpp:695-703` — сдача флага), телепорт по `areatrigger_teleport` (`PlayerCannotEnter`, ветки `reviveAtTrigger` для призрака: `ResurrectPlayer(0.5)` при входе в подземелье, где лежит тело; для группы ЛФГ `TeleportToBGEntryPoint`).
  - Данные датасета (`probe-areatrigger.out.txt`, `probe-areatrigger2.out.txt`): **1220 записей** (файл побайтно равен `dbc_source`; 40 байт, 10 полей), **687 сфер** (`radius > 0`; медиана 11,7 ярда, макс. 150), **533 коробки** (327 с `yaw ≠ 0`; медианные размеры 16,6 × 20,6 × 20; три «пустые» коробки 5048/5049/5626 с нулевыми размерами — недостижимы), 97 карт, максимум на одной карте 182 (карта 1), 178 (571), 175 (0), 154 (530). Континенты (0, 1, 530, 571) — 689 записей, остальные карты (подземелья, поля боя) — 531. **131 сфера** несёт ещё и ненулевые поля коробки (например 3646: радиус 5, «коробка» 0,33) — при `radius > 0` поля коробки **игнорируются**. Три записи с `yaw` вне [0, 2π]: 4872 (yaw 10), 5326 и 5343 (yaw 90) — использовать сырое число, как ядро. 59 триггеров с горизонтальным размахом < 3 ярдов, 16 коробок ниже 2 ярдов — по ним важен шаг проверки.
  - Стоковый пример реализации клиента: wowee `MovementHandler::checkAreaTriggers` (`movement_handler.cpp:3166-3420`): опрос раз в 0,25 с, набор «внутри», подавление при первом кадре после переноса и кулдаун 10 с (для Deeprun Tram, где точка прибытия лежит внутри обратного триггера). Мы берём набор «внутри» и подавление, но не таймеры и не таблицу Deeprun.
  - `MOVEMENT_HEARTBEAT_INTERVAL = 200` мс (`input/Movement.ts`): сервер видит позицию с запаздыванием до 200 мс × скорость (1,4 ярда бегом, 2,8 верхом); у сферы запас 1,5, у коробки **нет**.
- **Алгоритм (что и когда).**
  1. Индекс: `Map<mapId, Trigger[]>`; у каждой записи заранее `cx, cy, extent` (сфера: `radius`; коробка: `hypot(L/2, W/2)`), для коробки — `cos/sin(yaw)`. Записи без объёма (3 нулевые коробки) отбрасываются.
  2. Проверка — раз за кадр в `Loop.ts` **после** `advancePhysics` (внутри блока `world && player?.position && !worldPanel.hidden`), только если `worldPhysicsReady()`, не идёт загрузка (`game.worldLoading`), `world.movementReady`, позиция изменилась от прошлой проверки (порог 0,01 ярда) и персонаж не под управлением сервера (`serverControlsMovement(self)` — такси/сплайн; ядро в полёте такси всё равно игнорирует). Мёртвый и призрак **проверяются** (вход призрака в портал — штатный путь к телу).
  3. Отбор кандидатов: круг `(cx, cy, extent + 2)`; затем точный тест сферы (по `distance ≤ radius`, без запаса ядра — клиент не должен слать раньше, чем игрок реально внутри) или коробки (формула выше, **без** запаса).
  4. Вход — переход «предыдущий кадр: снаружи, этот: внутри» по конкретному id; множество `inside` хранит id, содержащие текущую позицию. Выход из объёма убирает id. Повторной отправки нет, пока игрок не вышел и не вошёл снова.
  5. **Пропуск тоннелирования:** между позицией прошлого и текущего кадра берутся промежуточные точки с шагом ≤ 0,5 ярда (не более 16; при скачке > 50 ярдов промежуточные точки не берутся). Если объём задет только промежуточной точкой, а концы снаружи — отправить один раз, **не** записывая id в `inside`, не чаще раза в 1,5 с на триггер.
  6. **Порядок отправки:** сначала `sendMovement(OPCODES.MSG_MOVE_HEARTBEAT)` (текущая позиция — так ядро видит игрока внутри объёма), затем `WorldClient.enterAreaTrigger(id)`. Пакеты одной сессии обрабатываются по очереди, гонки нет.
  7. **Перенос:** `world.onWorldChanged` (`app/EnterWorld.ts`, вызывается и после `SMSG_NEW_WORLD`, и после `MSG_MOVE_TELEPORT_ACK` на той же карте) вызывает `areaTriggers.reset(mapId, position)`: `inside` = все объёмы, содержащие точку прибытия, **без** отправки (точка входа в подземелье/трамвай лежит рядом с обратным триггером; игрок должен выйти и войти). Пока `position` неизвестна (`undefined` для транспорта) проверка молчит.
  8. **Подземелья:** `ContinentID` записей равен id карты подземелья; у карты подземелья своя выборка. **Транспорт:** координаты мира; клиент пока не бывает «на транспорте» (аудит, пункт 7), а после задачи A9 (М7) брать нужно **мировую** позицию, а не локальную палубную.
  9. Ответ сервера на отказ (`SMSG_TRANSFER_ABORTED`, `SMSG_AREA_TRIGGER_MESSAGE`) уже показывается (`WorldClient.ts` ~1621, ~4721); «`SMSG_RAID_GROUP_ONLY`» и «`SMSG_CORPSE_NOT_IN_INSTANCE`» — тоже (~4861, ~4891).

### 2.02 — Ремонт (`CMSG_REPAIR_ITEM`)
- **Подход.** Три части. (1) **Данные и формула:** таблицы `DurabilityCosts`/`DurabilityQuality` через маршрут gateway (М2) и чистая функция стоимости, повторяющая ядро. (2) **Отправка:** сборщик `CMSG_REPAIR_ITEM` и методы `WorldClient`. (3) **Интерфейс:** ответы шва (`CanMerchantRepair`, `GetRepairAllCost`, `CanGuildBankRepair`, `InRepairMode`), новые привязки `RepairAllItems`/`ShowRepairCursor`/`HideRepairCursor` и режим «курсор ремонта» из М3 (клик по слоту сумки/экипировки чинит предмет), кнопки в native-окне торговца. Ядро — единственный авторитет: показанная цена — оценка клиента, списание и отказы решает сервер.
- **Сверено.**
  - Пакет: `CMSG_REPAIR_ITEM` = `u64 npcGuid, u64 itemGuid, u8 guildBank` (`HandleRepairItemOpcode`, NPCHandler.cpp:758-794): NPC берётся через `GetNPCIfCanInteractWith(npc, UNIT_NPC_FLAG_REPAIR)` (флаг **0x1000**, UnitDefines.h:249; дистанция `INTERACTION_DISTANCE = 5` + досягаемости); `itemGuid ≠ 0` → `DurabilityRepair(pos, true, discount)`, `itemGuid = 0` → `DurabilityRepairAll(true, discount, guildBank != 0)`.
  - Формула (`Item::CalculateDurabilityRepairCost`, Item.cpp:753-798): `lost = max − cur` (0 → предмет не чинится; `max == 0` → нет прочности); строка `DurabilityCosts` с `ID = ItemLevel` (нет строки → цена 0, предмет пропускается), `DurabilityQuality` с `ID = (Quality + 1) * 2`, множитель = `WeaponSubClassCost[SubClass]` при `Class = 2`, `ArmorSubClassCost[SubClass]` при `Class = 4`, иначе 0; `cost = round(lost · множитель · Data)`, затем `uint32(cost · discount · RATE_REPAIRCOST)`, и **`cost == 0 → 1`**.
  - Чинятся (`DurabilityRepairAll`, Player.cpp:4998-5095): слоты 0-18 экипировки, рюкзак (23-38) и содержимое сумок 19-22; банк, выкуп и ключи — нет. Для гильдейского банка предметы упорядочиваются по цене (от дешёвых), пока хватает `GetMemberAvailableMoneyForRepairItems`; для своих денег при нехватке — **тихий возврат** (комментарий ядра: «клиент показывает ошибку сам и не шлёт опкод»). ### 5.25 — Прочие исходящие (S2 · S; девять подпунктов — по каждому решение «делать / не делать» с доказательством)

Мутация: слать и при выключенной опции — падает.
2. **`CMSG_BUSY_TRADE` — не делать.** `HandleBusyTradeOpcode` (:74) = `TradeCancel(true, TRADE_STATUS_BUSY)` — отменяет **текущий** обмен игрока; ядро само отвечает «занят» инициатору, пока игрок торгует (`HandleInitiateTradeOpcode`), поэтому безопасного клиентского повода нет (отправка при открытом окне отменила бы законный обмен). Сборщик держать только как `buildBusyTrade()` для модулей; в учёт намеренно игнорируемых (5.29) с причиной.
3. **`CMSG_MOVE_TIME_SKIPPED` — по умолчанию не отправлять.** Формат: `packed guid (двигатель), u32 timeSkipped` (`HandleMoveTimeSkippedOpcode`, MovementHandler.cpp:902: `mover->m_movementInfo.time += timeSkipped` и ретрансляция `MSG_MOVE_TIME_SKIPPED` наблюдателям); требует `IsRightUnitBeingMoved(guid)`. **Наши метки времени — настенные часы** (`Math.trunc(performance.now()) >>> 0`, `WorldClient.ts` ~1689), а не накопленное время кадров, поэтому простой фоновой вкладки уже отражён в `time`; отправка «пропущенного» двойным счётом сдвинула бы таймлайн у наблюдателей. Реализовать (по `visibilitychange`, разрыв ≥ 1 с, только если персонаж — активный двигатель) **только** после воспроизведения проблемы: второй игрок видит рывок после возврата вкладки. До тех пор — в учёт 5.29. **Проверка решения:** живой сравнительный тест с двумя клиентами (14.03).
4. **`CMSG_QUESTLOG_SWAP_QUEST` — не подключать.** Формат `u8 slot1, u8 slot2` (0…24, `HandleQuestLogSwapQuest` QuestHandler.cpp:433), но ни в стоковом Lua 3.3.5 (`QuestLogFrame.lua`, `WatchFrame.lua` — нет `SwapQuestLog`), ни в native-журнале перестановки нет: вызывающего нет. Сборщик — только для модулей; в учёт 5.29.
5. **`CMSG_GROUP_UNINVITE` по имени — делать.** `cstring name` (`HandleGroupUninviteOpcode`, GroupHandler.cpp:330: нормализует имя, отвергает себя, `CanUninviteFromGroup()`, затем исключает участника **или отменяет ожидающее приглашение** `GetInvited(name)`). Сейчас `UninviteUnit` (`FrameXmlChatApi.ts:411`) ищет только среди `world.group.members` и иначе пишет «нет в вашей группе», а `WorldClient.removeFromGroup(guid)` шлёт вариант по guid (`CMSG_GROUP_UNINVITE_GUID`, `WorldClient.ts:2748`). **Как:** `world.removeFromGroupByName(name)` = `buildGroupUninviteByName(name)`; `UninviteUnit` — сначала guid участника (как сейчас), при неизвестном имени, похожем на имя игрока (2–12 букв), — по имени (отмена приглашения). **Тест:** байты (`cstring`), поведение при известном/неизвестном имени; мутация — слать по имени даже для участника: тест «известный → guid» падает.
6. **`CMSG_CANCEL_CHANNELLING` — не делать.** `CancelChannelling::Read` = `u32 spellId` (SpellPackets.cpp:40; `HandleCancelChanneling` SpellHandler.cpp:532 прерывает канал). Уже работает `CMSG_CANCEL_CAST(u8 castCount, u32 spellId)` (`WorldClient.ts` ~1957): `HandleCancelCastOpcode` вызывает `InterruptNonMeleeSpells(false, spellId, false)`, а он прерывает и потоковое с совпавшим id. Заменять — только ради верности оригиналу; дефект не подтверждён.
7. **`CMSG_CANCEL_GROWTH_AURA` — не подключать:** пустой пакет, снимает положительные ауры `MOD_SCALE` (`HandleCancelGrowthAuraOpcode`, SpellHandler.cpp:507); стоковый `CancelUnitBuff` (`BuffFrame.lua`, `SecureTemplates.lua`) идёт через обычный `CMSG_CANCEL_AURA`. Учёт 5.29.
8. **Методы без вызовов — решение по каждому:**

   - `setTutorialSeen(index)` (`WorldClient.ts` ~3775, `CMSG_TUTORIAL_FLAG(u32 index)`; ядро: бит `index % 32` слова `index / 32`, `HandleTutorialFlag`) — **делать привязкой**: стоковый `TutorialFrame.lua` (в вертикали: `FrameXmlCorpus.ts:496`) зовёт `FlagTutorial(currentTutorial)` (:650) и `IsTutorialFlagged(id)` (:816); ни то, ни другое в шве не привязано (`grep` по `src`: 0). `FlagTutorial(index)` → `setTutorialSeen`, `IsTutorialFlagged(index)` → бит из `tutorialFlags` (`SMSG_TUTORIAL_FLAGS`, 8 слов, `parseTutorialFlags` ~7280) с локальным учётом отправленных. ### 8.17 — Поддержка: `CMSG_GM_REPORT_LAG`, `CMSG_BUG`, `CMSG_COMPLAIN` (почта), `CMSG_GMSURVEY_SUBMIT` (S2 · S по пакетам, опрос — L)
(Жалоба на чат — часть чата, вне плана; отброшено. Здесь только отчёты об ошибках и обращения в GM.)
- **Подход.** Владелец поддержки в клиенте — **native-окно** `ui/GmTickets.ts`: стоковый `HelpFrame` не входит в вертикаль (`FrameXmlWorldMount.ts:3447`: «the native GM ticket window is the help owner»), а перенос всего `HelpFrame.xml` (38,8 КБ) ради четырёх пакетов не оправдан. Значит: сборщики пакетов в `world/TicketProtocol.ts`, методы `WorldClient`, секции в native-окне, плюс два привязанных имени стокового C API для аддонов и почтового окна (`GMReportLag`, `ComplainInboxItem`). Порядок срезов: лаг → жалоба на письмо → ошибка/предложение → опрос.
- **Сверено.**
  - **Лаг:** `CMSG_GM_REPORT_LAG` = `u32 lagType, u32 mapId, f32 x, f32 y, f32 z` (`HandleReportLag`, TicketHandler.cpp:248; сохраняется в `lag_reports` вместе с задержкой сессии). `LagReportType` (TicketMgr.h:73): **1 добыча, 2 аукцион, 3 почта, 4 чат, 5 движение, 6 заклинания**.   - **Ошибка/предложение:** `CMSG_BUG` = `u32 suggestion (0 ошибка / 1 предложение), u32 contentLen, cstring content, u32 typeLen, cstring type` (`HandleBugOpcode`, MiscHandler.cpp:631; ядро читает строки, длины игнорирует; писать `длина + 1`, как оригинал; сохраняет `type` и `content` в `bugreports`). Стокового вызывающего в `FrameXML` 3.3.5 нет (`SubmitBug`/`SubmitSuggestion` не встречаются) — форма есть только как решение владельца.
  - **Жалоба на письмо:** `CMSG_COMPLAIN` = `u8 spamType (0 — почта), u64 spammerGuid`, для почты далее `u32 0, u32 mailId, u32 0` (`HandleComplainOpcode`, MiscHandler.cpp:1190; тип 1 — чат, вне плана); ядро отвечает `SMSG_COMPLAIN_RESULT(u8 0)`. Стоковое окно почты зовёт `CanComplainInboxItem(index)`/`ComplainInboxItem(index)` (`StaticPopup.lua:871`), в шве они заглушены (`FrameXmlMail.ts:927-928`: `false`/ничего).
  - **Опрос:** `CMSG_GMSURVEY_SUBMIT` = `u32 mainSurvey`, затем до 10 троек `(u32 subSurveyId, u8 rank, cstring comment)` — цикл **обрывается на первом `subSurveyId == 0`**, поэтому при меньшем числе вопросов обязателен терминатор `u32 0`; в конце `cstring общий комментарий` (`HandleGMSurveySubmit`, TicketHandler.cpp:194-236). Комментарии проходят `ValidateHyperlinksAndMaybeKick` — **ссылка (`|H…|h`) с неверным содержимым выкидывает игрока с сервера**, поэтому клиент шлёт только очищенный текст. Триггер: `SMSG_GMRESPONSE_STATUS_UPDATE(u8 getSurvey)` (ядро после `CMSG_GM_RESPONSE_RESOLVE`, шанс `CONFIG_CHANCE_OF_GM_SURVEY`) → `WorldClient.ticketSurveyPending` (`WorldClient.ts` ~7446, читает `GmTickets.ts:126`). Таблицы датасета (заголовки замерены; раскладки **выведены**, TC их не читает и `tools/dbd` не содержит): `GMSurveyCurrentSurvey` 9 строк × 2 поля (`ID, SurveyID` — все 9), `GMSurveySurveys` 2 × 11 (`ID` и до 10 id вопросов: 9 → 35…41, 6 → 28…32), `GMSurveyQuestions` 13 × 18 (`ID` + локализованная строка), `GMSurveyAnswers` 45 × 20 (`ID, порядок, вопрос`, локализованная строка). Оценки — `GMSURVEYRATING1…5` («Плохое» … «Отличная», GlobalStrings.lua:3810-3814); заголовок — `GMSURVEY_TITLE`.
