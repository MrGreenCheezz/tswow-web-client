# Этап 14. Живая приёмка

> Часть [плана реализации](../IMPLEMENTATION_PLAN.ru.md). Пункты этапа — в [плане работ](../WORK_PLAN.ru.md).

**Как проводится живая сессия.**
- **Разрешение.** Живая проверка идёт на realm владельца (auth/world/MySQL — его процессы). Агент проводит её только с явного разрешения владельца на эту сессию, не запускает и не перезапускает его серверы, не использует чужие учётки. Для P1 со вторым игроком нужен второй одновременный сеанс.
- **Подготовка.**
  - Сборка: либо локальный Electron (`electron\build.bat`: Vite не держит 5173), либо Vite dev — одно из двух.
  - Если в вехе менялся `src/gateway/**`, gateway перезапущен (0.1).
  - Тестовые персонажи известны: «Тестовый», класс 13 HERO, 80 ур.; для классовых проверок нужен стандартный класс и, по возможности, DK.
  - Начальное состояние снято read-only SELECT: инвентарь, деньги, квесты, место возвращения. Учётные данные в отчёты не пишутся.
- **Во время сессии.**
  - Для каждого пункта: шаги, ожидаемый результат, фактический результат, доказательства — скриншот, пакеты из диагностики «Пакеты», состояние сервера SELECT до и после.
  - Для замеров — запись v2 (`webclientRecordFreezes()`).
- **В конце сессии.**
  - `webclientUnhandledOpcodes()` и `webclientPacketErrors()` — пусты или с объяснением;
  - `copy(frameXmlWorld().errors)` — 0 новых;
  - `frameXmlWorld().api.filter(r => !r.neutral)` после открытия основных окон — только голос и BN.
- **Итог.** Пункт плана получает статус «принят» (или «расходится» с номером нового дефекта); запись в `docs/parity/parity-execution.ru.md`; P0/P1-строки матриц обновляются.
- **Когда.** Живая сессия — в конце каждой вехи (В1…В6), по пунктам, которые веха закрыла. Выпуск (14.26) — после В6.
