## Общие механизмы

Линия A6 владеет восемью механизмами. Общие механизмы М1–М8 других линий здесь не используются, кроме М2 («Новый DBC-маршрут», A3) в `10.08` и правила «политика кеша» из `10.12`, которой должны пользоваться новые DBC-маршруты A3.

### A6-1. «Защита сокетов и процесса gateway» (`1.03`, используют `10.01`, `10.15`)
- **Назначение.** Ни один запрос и ни один сброс соединения не могут завершить процесс gateway; отказ всегда закрывает сокет; страховка процесса отделяет «шум сокетов» от ошибок программиста.
- **Форма.** `src/gateway/UpgradeGuard.ts`: `refuseUpgrade(socket, status)`, `routeUpgrade(request, { allowedOrigins })` → `{ kind: "auth" | "world" } | { kind: "refuse", status }`; `src/gateway/ProcessGuard.ts`: `installProcessGuard({ target, log, shutdown, now, burst })`, `isSocketNoise(error)`.
- **Применение по шагам.** (1) `socket.on("error", () => socket.destroy())` первой строкой обработчика `upgrade`; (2) любая ветка отказа — только через `refuseUpgrade` (пишет ответ и `destroy` в колбэке `end`); (3) разбор URL — внутри `routeUpgrade` (`try`), результат — данные, не исключение; (4) всё тело обработчика в `try/catch` → `refuseUpgrade(socket, 500)` + журнал; (5) `server.on("error")` после `listen`; (6) `installProcessGuard` в `main.ts` **после** `startGateway`.
- **Файлы.** `Gateway.ts` (только блок `upgrade` и `startGateway`), `main.ts`, два новых модуля.
- **Тесты.** `tests/gateway-upgrade-hardening.test.mjs`, `tests/gateway-process-guard.test.mjs` (механизм A6-2).
- **Типичные ошибки.** Проверять обработчик, у которого уже стоит `ProcessGuard` (тест будет зелёным на сломанном обработчике); считать отказ «закрытым» после `socket.end()` без `destroy` (полуоткрытые сокеты копятся: 200 из 200 в модели `A6/upgrade-model.out.txt`); заглушать `ERR_INVALID_URL` как «шум» вместо исправления источника; включать `ProcessGuard` до `startGateway` (падение при старте должно оставаться аварийным выходом ≠ 0 для супервизора).

### A6-2. «Тест gateway в дочернем процессе» (`1.03`, `10.14`, `10.01`)
- **Назначение.** Ловить дефекты класса «процесс упал», которые внутри `node:test` выглядят как случайный сбой соседнего теста.
- **Форма.** Фикстура `tests/fixtures/gateway-child.mjs`: запускает настоящий `startGateway({ host: "127.0.0.1", port: 0, auth/world: TCP-заглушки, allowedOrigins, datasetPollMs: 0 })`, шлёт `process.send({ port })`, на IPC `sockets` отвечает `process.getActiveResourcesInfo().filter(x => x === "TCPSocketWrap").length`; родитель открывает сырые `net.connect({ allowHalfOpen: true })`, пишет запросы, делает `resetAndDestroy()`.
- **Применение.** `child.exitCode === null` после серии атак, `fetch("/health")` → 200, счёт сокетов.
- **Файлы.** `tests/fixtures/gateway-child.mjs`, тесты выше. Флаги `--import ./tools/register-test-sources.mjs` унаследовать из `process.execArgv`.
- **Типичные ошибки.** Единичный RST вместо серии (гонка RST против `end()`: в модели `rst-404`/`rst-503` выжили, `rst-403` и цикл из 50 — нет; нужны серии по 50); забыть `allowHalfOpen` у клиента (без него Node закрывает сокет за сервер и утечка не видна); брать порт 8090.

### A6-3. «Адрес клиента, лимиты и адрес для ядра» (`10.01`, зависимость `10.02`)
- **Назначение.** Считать игрока по реальному адресу, а не по адресу прокси; ограничивать попытки входа; при желании владельца показать ядру уникальный адрес игрока.
- **Форма.** `src/gateway/ClientAddress.ts` (`clientAddress(request, { trustedProxies, peer })`), `AuthAttemptLimiter.ts` (`take(address)`), `PlayerSource.ts` (`PlayerSourceAllocator`, `bridge(…, { localAddress })`). Шов для тестов — `GatewayOptions.peerAddress` (уже есть, `Gateway.ts:350`).
- **Применение.** Все счётчики (`bridgedPerAddress`, лимитер, журнал) берут `clientAddress(request, …)`; `X-Forwarded-For` читается только от адреса из `GATEWAY_TRUSTED_PROXIES`; отказ лимитера — закрытие WebSocket с кодом `4290`.
- **Файлы.** три новых модуля, `Gateway.ts` (блок `upgrade`, `track`, `bridge`), `GatewayConfiguration.ts`.
- **Тесты.** `tests/gateway-auth-limit.test.mjs`, `tests/gateway-player-source.test.mjs`. Проба возможности: `A6/loopback-source.mjs`.
- **Типичные ошибки.** Доверять `X-Forwarded-For` от любого адреса (подделка); ограничивать loopback (разработка упрётся в собственный лимит); хранить таблицу «игрок → 127.x» только в памяти (после перезапуска привязка учётки и баны теряют смысл).

### A6-4. «Коды ответов и тексты glue» (`1.19`; используют `2.07`, `2.08`, `10.05`, `10.06`, `10.10`)
- **Назначение.** Одно место, где числовой код ответа ядра превращается в ключ строки корпуса и в готовый текст диалога.
- **Форма.** Генератор `tools/generate-protocol.mjs` пишет `src/generated/protocol-data/responseCodes.ts` (`RESPONSE_CODES`, `RESPONSE_CODE_NAMES`) и `authResults.ts` из `shared/SharedDefines.h` и `authserver/Authentication/AuthCodes.h`; фасады `src/generated/responseCodes.ts`, `authResults.ts`; `src/browser/glue/GlueMessages.ts`: `responseKey(code, context)`, `authKey(code)`, `messageFor(key, glueString, fallback)`, `describeFailure(error, context)`.
- **Применение.** Взять код → `responseKey` → `glueString(ключ)` (глобал корпуса) → `OPEN_STATUS_DIALOG("OKAY" | "OKAY_HTML", текст)`; для `FORCE_RENAME_CHARACTER` и `FORCE_DECLINE_CHARACTER` в событие передаётся **ключ**, текст берёт сам стоковый Lua (`_G[message]`).
- **Файлы.** генератор, фасады, `GlueMessages.ts`, потребители в `glue/`.
- **Тесты.** `tests/glue-messages.test.mjs` (таблицы, вертикаль `withClient`), расширение теста генератора.
- **Как проверена таблица.** `A6/exe-response-table.mjs` нашла в `F:/Circle/Wow.exe.clean` 104 указателя (смещение `0x6d71f0`), индекс = значение `ResponseCodes`; вывод — `A6/exe-response-table.out.txt`. Для авторизации клиентская таблица `LOGIN_*` — внутренний enum, соответствие проводному `AuthResult` — по имени (`A6/exe-login-table.out.txt`).
- **Типичные ошибки.** Подставлять коды вручную (так появились неверные 42-44 в `GlueCreation.ts:71-75`); забывать, что коды 62-69 в корпусе называются `CHAR_FACTION_CHANGE_*`; выводить ключ, которого нет в `GlueStrings.lua` (`CHAR_NAME_CONSECUTIVE_SPACES`) — нужен запасной; показывать HTML-строку (`LOGIN_BANNED`) обычным диалогом.

### A6-5. «Стадии подключения и диалог статуса» (`10.05`; используют `10.06`, `2.07`, `2.08`)
- **Назначение.** Любая долгая операция экрана входа показывает штатный `GlueDialog` и может быть отменена.
- **Форма.** `GlueWorldConnector(realm, auth, progress?)`, `progress({ stage: "connecting" | "authenticating" | "queued" | "loading", position? })`; события `OPEN_STATUS_DIALOG(type, text)` → `UPDATE_STATUS_DIALOG(text)` → `CLOSE_STATUS_DIALOG`; отмена — `StatusDialogClick`/`CancelLogin` → `session.cancelPending()` (поколение `#generation`, закрытие потока).
- **Применение.** Запрос, у которого нет ответа сразу (переименование, смена внешности), открывает `OPEN_STATUS_DIALOG("CANCEL", …)`; ответ закрывает диалог и показывает результат.
- **Файлы.** `GlueSession.ts`, `GlueApi.ts`, `GlueCharacterApi.ts`, `FrontDoorHost.ts`, `Bootstrap.ts`.
- **Типичные ошибки.** Забыть, что `installConstantStubs()` вызывается последним и перекрывает настоящие функции с тем же именем (проверять, что имя убрано из `CONSTANT_STUBS`); не отбрасывать поздний ответ после отмены; `RenameCharacter` должен вернуть **истину** при отправленном запросе (стоковый Lua скрывает диалог по возвращаемому значению).

### A6-6. «Услуги персонажа на экране выбора» (`2.07`, `2.08`, `10.09`)
- **Назначение.** Пакеты и слой C API для переименования, смены внешности/фракции/расы, склонений.
- **Форма.** Чистые построители и разборщики в `world/CharacterProtocol.ts` (`buildRenameCharacter`, `buildCustomizeCharacter`, `buildFactionOrRaceChange`, `buildDeclinedNames`, `parse*Result`); по два-три строки методов в `WorldClient.ts` рядом с `createCharacter`; методы `GlueSession`; режим услуги в `GlueCreation` (`beginPaidService`); C API в `GlueCharacterApi`/`GlueCreateApi`.
- **Порядок байтов.** `CMSG_CHAR_CUSTOMIZE`/`FACTION`/`RACE`: guid, имя, пол, **skin, hairColor, hairStyle, facialHair, face** (+ раса); `CMSG_CHAR_CREATE`: skin, **face, hairStyle, hairColor**, facialHair — разные; ответ `SMSG_CHAR_CUSTOMIZE`: пол, skin, face, hairStyle, hairColor, facialHair.
- **Тесты.** `tests/glue-character-services.test.mjs` (байты), `tests/glue-rename.test.mjs`, `tests/glue-paid-service.test.mjs`, вертикали `*-vertical.test.mjs` (`withClient`).
- **Типичные ошибки.** Индекс кнопки расы вместо id в `race`; пересчёт внешности через `refreshProfile(true)` при загрузке существующего персонажа (сбрасывает вид); проверять внешность при смене пола (ядро сравнивает со старым полом — `CharacterHandler.cpp:1433`).

### A6-7. «Конфигурация публичной раздачи» (`10.02`; используют `10.13`, `10.17`, `10.01`)
- **Назначение.** Вынести из `tools/start-server.mjs` всё, что можно проверить без запуска серверов.

### A6-8. «Чистые модули Electron» (`1.29`, `10.11`, `10.17`)
- **Назначение.** Логику оболочки (разбор конфигурации, восстановление после падения, сравнение версий, свежесть сборки) держать в `electron/*.cjs` без зависимости от `electron`, чтобы `node --test` мог `require` её.

## Порядок срезов линии A6 (вход, gateway, безопасность, Electron)

### 1.02 — Вход в мир по http из обычного браузера (HMAC-SHA1 без Web Crypto)
- **Подход.** Заменить единственную зависимость входа от `crypto.subtle` — `hmacSha1` в `world/WorldCrypt.ts` — обычным RFC 2104 поверх уже имеющегося `auth/Sha1.ts`. Рекомендую **один путь без ветвления** (всегда чистый TS), а не «subtle, а если нет — запасной»: ветка, которую тесты в Node никогда не проходят (в Node `subtle` есть), — это ровно тот класс дефекта, что оставил вход по http сломанным. Стоимость: два HMAC от 40 байт на подключение к миру — микросекунды. Запасной вариант («subtle при наличии») допустим, но тогда тест обязан прогнать `WorldCrypt.create` под подменённым `globalThis.crypto` (см. тесты).

### 1.03 — Gateway падает от одного запроса (безопасность)
- **Модель угрозы.**
  - *Локальный запуск* (`GATEWAY_HOST=127.0.0.1`, `web/start-dev.bat`): достучаться до порта могут только процессы этой машины; чужая страница в браузере владельца шлёт свой `Origin` и упирается в ветку 403 до разбора URL. Уровень низкий.
  - *`online/start-server.bat`* (`tools/start-server.mjs`: `GATEWAY_HOST=0.0.0.0`): любой хост из интернета открывает TCP 8090 и одним запросом `GET //[::1 HTTP/1.1` с известным `Origin` страницы (он публичен: `http://<PUBLIC_HOST>:8091`) роняет процесс; либо шлёт любой upgrade с чужим `Origin` и сбрасывает соединение (RST). Падает и gateway, и страница игроков (`start-server.mjs` держит `serveStatic` в том же процессе), а супервизор при падении работающего gateway завершается (`tools/gateway-supervisor.mjs:291-293`, «restarting a crash in a loop would hide it»). Повторяется после каждого ручного запуска. Уровень высокий.
  - *Приложение игрока*: клиент не влияет; угроза — третьи лица, как выше.
  - *Что закрывает правка:* аварийное завершение от кривой строки запроса и от сброса соединения на любой ветке отказа, зависшие полуоткрытые сокеты после отказа, аварию при ошибке `accept` (EMFILE). *Чего не закрывает:* объёмный флуд и любую «аутентификацию» — `Origin` пишет клиент (комментарий `Gateway.ts:3418-3421` это и говорит); лимит 8 сокетов на адрес считает адрес прокси, если перед gateway стоит прокси (см. `10.01.md`, `10.02.md`).
  - *Проверка без gateway владельца:* `A6/upgrade-model.mjs` (вывод `A6/upgrade-model.out.txt`) и новый тест на настоящем `startGateway` с портом 0 в дочернем процессе.
- **Подход.** Три слоя. (1) Обработчик `upgrade` не может бросить: `error`-слушатель на сокет первым делом, разбор URL в `try`, один помощник отказа, который пишет ответ **и закрывает** сокет. (2) Сервер после `listen` слушает свой `error`. (3) Страховка процесса в `main.ts`: журнал и штатное завершение вместо мгновенного падения, шум сокетов не убивает процесс. Логику выносим в два маленьких модуля, а не раздуваем `Gateway.ts` (горячий файл).
- **Сверено.**
  - `src/gateway/Gateway.ts`, `startGateway` → `server.on("upgrade", …)` (стр. 3440-3459): `new URL(request.url ?? "/", "http://gateway.local")` вне `try` (3447); `socket.end("HTTP/1.1 403|404|503 …")` без `socket.on("error")` (3443, 3450, 3455); после `listen` слушателя `error` у `server` нет (`server.off("error", reject)`, 3465). HTTP-путь (`handle`, стр. 873-3393) уже закрыт `.catch` (3385-3393) — `GET //[::1` без upgrade даёт 500, а не аварию.
  - Node снимает свой `socketOnError` с сокета в момент передачи в `upgrade` (`_http_server.js`, `onParserExecuteCommon`), поэтому после этого сокет — на совести обработчика. `ws.handleUpgrade` вешает свой `error`-слушатель сам — защищена только ветка успешного рукопожатия.
  - Модель (`A6/upgrade-model.mjs`, настоящий `ws`, порт 0, дочерний процесс): текущий код — `GET //[::1` → выход с кодом 1 (`ERR_INVALID_URL`); чужой `Origin` + RST → выход с кодом 1 (`Unhandled 'error' event`), 50 повторов — то же; `rst-404` и `rst-503` на одном запуске выжили (гонка RST против `end()`: ветка та же, воспроизведение нестабильно — в тесте нужны серии); 200 отказов с клиентами `allowHalfOpen` — на сервере остаётся **200** открытых сокетов (у исправленной модели 0); `server.emit("error")` без слушателя бросает, с слушателем — нет. Все исправленные варианты выжили и ответили 200 на `/`.
  - Остальные источники `error` в `src/gateway` покрыты: `DatasetFingerprint.ts:428` (watcher), `AssetWorker.ts:142`, `GatewayConfiguration.ts:316/364/411`, `PatchStatus.ts:266` (дочерние процессы), `Gateway.ts:639/644` (мост), `LocalAssetStdio.ts:132-133`, `SupervisedGateway.ts:54` (отправка IPC с пустым колбэком).
  - **Полный перечень мест, где исключение или `error` роняет процесс:** (а) `new URL` в `upgrade`; (б) сокет на ветках 403/404/503 без слушателя; (в) `error` у `http.Server` после `listen` (accept EMFILE); (г) весь остальной код — `unhandledRejection`/`uncaughtException` без глобального обработчика (в `main.ts` их нет). Мост `bridge()` и `handle()` безопасны: `webSocket.send/ping/close` под проверкой `readyState`, причины закрытия короче 123 байт.
- **Изменения.**

### 10.01 — Все игроки для TrinityCore приходят с 127.0.0.1 (безопасность)
- **Модель угрозы.**
  - *Локально* (владелец играет сам): не проявляется, привязка к IP и баны для одного человека безвредны.
  - *`online/start-server.bat`, чужие игроки*: authserver и worldserver видят адрес gateway, а не игрока. Следствия (все проверены по ядру): (1) `WrongPass.BanType = 0` (по умолчанию) банит `GetRemoteIpAddress()` на `WrongPass.BanTime` секунд (`authserver/Server/AuthSession.cpp:565-611`) — то есть 127.0.0.1, то есть всех игроков сразу; при `WrongPass.MaxCount = 0` (по умолчанию, `authserver.conf.dist:108`) перебор пароля вообще не ограничен; (2) `.ban ip` и `ip_banned` бьют по всем или ни по кому (`AuthSession.cpp:186-209`); (3) привязка учётки к IP (`account.locked`, сравнение `LastIP` в `AuthSession.cpp:334-343`; такое же сравнение и проверка бана по IP на мире: `game/Server/WorldSocket.cpp:49-72`, `:541-558`) либо всегда пропускает, либо ломает всех, потому что `LOGIN_UPD_LOGONPROOF` пишет `last_ip` = адрес gateway (`:512-520`); (4) блокировка по стране (`lock_country`) не работает — у loopback нет записи в базе адресов. TrinityCore **не понимает PROXY-протокол** (Grep по `src/server`: ни одного вхождения), передать реальный адрес нельзя.

### 10.02 — TLS или обратный прокси для публичной раздачи; предупреждение при публичном запуске (безопасность)
- **Модель угрозы.**
  - *Локально* (`web/start-dev.bat`, `start-gateway.bat`, loopback): защищённый контекст и так есть, TLS не нужен.
  - *`online/start-server.bat`* (страница `http://<PUBLIC_HOST>:8091/`, gateway `ws://…:8090`): посредник на пути (публичный Wi-Fi, провайдер) может подменить `index-*.js` и снять пароль до того, как он уйдёт в SRP6 (SRP защищает канал логина, но не страницу, которая его вводит); заголовки мира шифруются RC4, содержимое (включая то, что вне плана) — нет. Браузер по http без TLS не получает `crypto.subtle` (`1.02`) и `crossOriginIsolated` (`10.18`). `http`-origin приложения игрока Electron помечает безопасным (`electron/main.cjs:105-114`) — проблема скрыта, но подмена страницы по пути к игроку остаётся.
  - *Приложение игрока*: та же подмена страницы; при TLS приложение защищено, потому что открывает `https://…` (`build.mjs:playerUrl`).
  - *Что закрывает:* подмену страницы и перехват пароля/пакетов на пути; вместе с ним снимает две поломки http-игроков. *Чего не закрывает:* злоупотребление самим открытым gateway (см. `1.03`, `10.01`) и раздачу файлов клиента всем, кто открыл ссылку (`docs/DISTRIBUTION_PLAN.ru.md:118-122`, решение владельца).
- **Подход.** Три способа, выбирает владелец (WORK_PLAN 0.4f); код поддерживает 1 и 2, документация описывает 3.
  1. *TLS в самом процессе раздачи:* `PUBLIC_TLS_CERT`/`PUBLIC_TLS_KEY` — оба listener'а (страница и gateway) поднимаются через `node:https`; адрес игрока `https://<PUBLIC_HOST>:8091/`, gateway `wss://…:8090` — страница сама переходит на `wss://` (`Environment.ts:30`, `gatewayOrigin` берёт протокол страницы). Сертификату нужны домен (или IP-сертификат, если его выдаёт выбранный центр).
  2. *Закрепление сертификата в приложении игрока* (когда домена нет и сертификат самоподписанный): в `server.json` — `certSha256`; `main.cjs` разрешает ошибку сертификата только для хоста сервера и только при совпадении отпечатка. Веб-игроки при этом получают предупреждение браузера — для них способ не годится.
  3. *Обратный прокси на этой машине* (Caddy: автоматический HTTPS, два имени `wow.<домен>` → 127.0.0.1:8091 и `gw.<домен>` → 127.0.0.1:8090; порт 8090 наружу закрыт), `VITE_GATEWAY_ORIGIN=https://gw.<домен>` при сборке, `GATEWAY_TRUSTED_PROXIES=127.0.0.1` (`10.01`), `MODULE_UI_WRITE=0` (см. `10.04`). Один origin для страницы и gateway не годится (`DISTRIBUTION_PLAN.ru.md:105-109`).
- **Сверено.**
  - Предупреждение сейчас только одно: `src/gateway/GatewayConfiguration.ts:76-81` — при `host` вне loopback **и** `ALLOWED_ORIGINS=*`. Публичный запуск `start-server.mjs` (`GATEWAY_HOST=0.0.0.0`, конкретные origin'ы) не предупреждает ни о чём. Комментарии `Gateway.ts:330` («says so at start-up») и `Gateway.ts:1688-1689` («`main.ts:34-39`») указывают на предупреждение, которого в `main.ts` (35 строк) нет — оно переехало в `GatewayConfiguration.ts`; в `1685` строки такого предупреждения тоже нет.
  - `tools/start-server.mjs` выставляет `GATEWAY_HOST=bind`, `ALLOWED_ORIGINS` (публичный origin страницы и loopback-двойники, стр. 46-49), `MODULE_UI_WRITE=0`; поднимает `serveStatic(webRoot, { host, port })` из `electron/static-server.cjs` в том же процессе, что и gateway.

### 10.04 — `ALLOWED_ORIGINS=*` вместе с `MODULE_UI_WRITE=1` (безопасность)
- **Модель угрозы.**
  - *Локально* (владелец включил `MODULE_UI_WRITE=1` для окна-построителя `ui/WindowBuilder.ts`, а `ALLOWED_ORIGINS=*` оставил «на время»): любая страница, открытая в браузере владельца, шлёт `fetch("http://127.0.0.1:8090/modules/ui/<мод>/<файл>.json", { method: "PUT", body })`. ### 10.10 — TOTP/2FA в GlueXML (S0 латентно)
- **Модель угрозы/эффект.** Не безопасность, а работоспособность: учётка с включённым TOTP сейчас войти не может — `buildLogonProof` бросает «This account requires a six-digit authenticator token», игрок видит текст ошибки. Проявится, как только владелец включит `account.totp_secret` (в audit: «таких учёток нет»).
- **Подход.** Провести штатный поток клиента: авторизационный вызов при `securityFlags & 0x04` поднимает событие `PLAYER_ENTER_TOKEN`, стоковый Lua показывает `TokenEnterDialog`, `TokenEntered(token)` возвращает код в ожидающий вход, `CancelLogin()` его прерывает; `GetUsesToken/SetUsesToken` запоминают, что учётка требует токен (чтобы поле `AccountLoginTokenEdit` показывалось заранее).
- **Сверено.**
  - Ядро: `AuthSession::LogonChallengeCallback` (`authserver/Server/AuthSession.cpp:383-400, 437-438`): если у учётки `totp_secret` — `securityFlags = 4`, в ответ на challenge добавляется байт `1`; `HandleLogonProof` (`:473-496`): при `securityFlags & 4` в конце proof идёт `u8 size` + строка токена, `atoi` и `TOTP::ValidateToken`; неверный токен → тот же код `WOW_FAIL_UNKNOWN_ACCOUNT` (0x04), что и неверный пароль, и с тем же `_status = STATUS_CLOSED` (повтор — новое соединение).
  - Клиентский протокол уже готов: `src/auth/AuthProtocol.ts` — `AUTH_SECURITY_TOKEN = 4`, `challengeSecurityExtraLength`, `parseLogonChallenge` (читает байт при флаге), `buildLogonProof(proof, flags, token)` (проверяет `^\d{6}$`, пишет длину и байты, стр. 108-130); `auth/login.ts` `LoginCredentials.token?` — но токен должен быть **известен заранее**, а игрок вводит его *после* challenge. `GlueApi.login` (`GlueApi.ts:590-643`) токен не передаёт; `TokenEntered`, `PINEntered`, `GetUsesToken [false]`, `SetUsesToken [], ` — константные заглушки (`GlueApi.ts:216-217`).

События `PLAYER_ENTER_TOKEN`, `PLAYER_ENTER_PIN`, `PLAYER_ENTER_MATRIX` есть в словаре событий клиента (`A6/exe-response-table.out.txt`). PIN и матрица (`securityFlags & 1, 2`) — не поддерживаются ядром 3.3.5 TC вообще (`AuthSession.cpp:422-435` отправляет нули), оставить отказ.
- **Изменения.**
  1. `src/auth/login.ts` — `LoginCredentials.token` становится `string | (() => Promise<string>)` (или отдельный `onTokenRequired?: () => Promise<string>`, вызываемый **после** `parseLogonChallenge`, только если `challenge.securityFlags & AUTH_SECURITY_TOKEN`): SRP-вычисления идут параллельно ожиданию, `buildLogonProof(proof, flags, token)` вызывается после ответа. ### 10.12 — HTTP-кеш: поколение в URL или ревалидация (S2, M)

### 10.14 — `bufferedAmount > 4 МБ`: пауза чтения TCP вместо разрыва сессии [гип.] (Риск)
- **Модель угрозы/эффект.** *Локально:* сеть — loopback, буфер не растёт. *Раздача (`online/start-server.bat`, приложение игрока):* игрок с медленной или дёргающейся сетью в момент всплеска трафика мира (вход в мир, крупный `SMSG_UPDATE_OBJECT`/`COMPRESSED_UPDATE_OBJECT` — сотни КБ) может превысить 4 МБ в очереди отправки WebSocket и потерять сессию; не безопасность, а надёжность. Тег [гип.]: превышение на живой сети **не измерено**. Раз в этой работе числа снимают, а не оценивают — сначала измерение, потом правка.
- **Подход.** (1) Срез-измерение: счётчик пика `webSocket.bufferedAmount` и число пауз на сессию, вывод в журнал при закрытии (`GATEWAY_LOG_BACKPRESSURE=1`). (2) Если пик приближается к порогу — включить паузу чтения TCP по верхней/нижней отметке; разрыв оставить только как последний предел.
- **Сверено.** `src/gateway/Gateway.ts`, `bridge()` (стр. 583-647): `tcp.on("data")` при `webSocket.bufferedAmount > MAX_BUFFERED_BYTES` (4 МиБ, стр. 63) вызывает `fail("Client is too slow")` — `tcp.destroy()` и `webSocket.close(1011)`; обратное направление: `tcp.write(payload)`, при `tcp.writableLength > MAX_BUFFERED_BYTES` — `fail("Backend is too slow")` (стр. 627-628). `ws` даёт `bufferedAmount` и обратный вызов у `send(data, options, cb)` (срабатывает, когда данные ушли в сокет); отдельного `drain` у `WebSocket` нет; `tcp.pause()/resume()` есть у `net.Socket`, а при паузе чтения worldserver копит исходящие данные у себя (предел очереди `Socket::_writeQueue` в этом ядре **не проверялся** — открытый вопрос), поэтому пауза не бесконечна: предел по времени `PAUSE_LIMIT_MS`.
- **Изменения.**
  1. `bridge()`: `let paused = false; const HIGH = 1 MiB, LOW = 256 KiB`; в `tcp.on("data")` после `send(data, { binary: true }, () => resume())` — при `bufferedAmount > HIGH` → `tcp.pause(); paused = true`; в колбэке `send` при `paused && bufferedAmount < LOW` → `tcp.resume()`. Разрыв — только если пауза длится > 30 с (`PAUSE_LIMIT_MS`) или `bufferedAmount > 16 МиБ` (запас против ошибки).
  2. Обратное направление: при `tcp.writableLength > HIGH` вызывать `webSocket.pause()` (есть в `ws` 8.x) до `tcp.once("drain")`, вместо немедленного `fail`.
  3. Счётчики и журнал (шаг 1) — общий помощник `src/gateway/BridgeStats.ts` (новый): `peak`, `pauses`, `pausedMs` на мост; строка в журнал при закрытии (только при `GATEWAY_LOG_BACKPRESSURE=1`).
- **Тесты.** `tests/gateway-backpressure.test.mjs` (новый; `startGateway` порт 0, бэкенд — TCP-заглушка, шлющая 20 МБ, клиент — `ws` с `socket.pause()`): при медленном клиенте соединение **не рвётся**, память gateway ограничена (пик `bufferedAmount` ≤ `HIGH` + размер одного чанка), после `resume()` клиент получает все 20 МБ байт в порядке (контрольная сумма); при клиенте, не читающем дольше `PAUSE_LIMIT_MS` (поддельные часы) — разрыв с причиной. Мутации: убрать `tcp.resume()` — тест виснет (таймаут теста); вернуть немедленный `fail` — первый тест падает.
- **Офлайн-проверка.** тест выше; отдельного стенда не требуется.
- **Живая проверка.** → 14.08 (разрыв/повторный вход) с включённым журналом на тестовой раздаче и искусственным ограничением канала (Chrome DevTools → Network throttling «Slow 3G» на входе в мир): пики и паузы видны, сессия жива.
- **Зависимости.** Перезапуск gateway владельцем; тот же блок кода `bridge()` правит `10.01` (`localAddress`) — вести последовательно.
- **Риски и открытые вопросы.** (1) Пауза чтения замедляет ответы на пинги игры — `CMSG_PING` идёт в обратном направлении и не блокируется, но `SMSG_PONG` встаёт в очередь: латентность растёт, порог `MAX_OVERSPEED_PINGS` ядра считает интервалы клиента, не задержку. (2) Открытый вопрос: реальный пик — снять шагом (1) на живой раздаче до выбора порогов `HIGH/LOW`.
- **Размер и файлы.** S; `src/gateway/Gateway.ts` (только `bridge`), `src/gateway/BridgeStats.ts` (новый), `tests/gateway-backpressure.test.mjs` (новый).

### 10.15 — Сторож gateway (перезапуск при падении); поведение 409 после сборки TSWoW при подключённых игроках (Долг)
- **Подход.** Два независимых среза: (А) супервизор перезапускает упавший gateway с нарастающей паузой и предельным числом падений; (Б) после «осевшей» сборки TSWoW игрок не остаётся в 409 бессрочно: срок ожидания, объявление в баннере и принудительный перезапуск по истечении срока (по решению владельца).
- **Сверено.**

Комментарий: «restarting a crash in a loop would hide it». Следствие для `tools/start-server.mjs`: страница игроков живёт **в процессе супервизора** (`serveStatic` до `import("./start-gateway.mjs")`, стр. 54-64), поэтому падение gateway убивает и страницу.

  - Решение о перезапуске после сборки: `restartDecision` (стр. 55-70) — ждёт «тихой» сборки (`quietMs 5 с`), маркера `last-client-build.json` или `buildTimeoutMs 120 с`, и **нулевого числа игроков** (`clients.auth + clients.world > 0` → `wait/players`); дочерний процесс отказывает на `shutdown` с `declined`, если игрок подключился (`SupervisedGateway.ts:106-116`). Пока игрок в мире, gateway отвечает 409 `client_patch_chain_changed` на все маршруты клиентских медиа (`Gateway.ts:910-919`, перечень `isClientVisualProfileRoute`, стр. ~134-147), а баннер (`PatchChainChanged.ts`) предлагает «Обновить страницу», которая до перезапуска ничего не даёт (поколение то же).
- **Изменения.**
  1. (А) `gateway-supervisor.mjs`: в `#onExit` для фазы `running` — перезапуск, если падений за последние 10 мин ≤ `crashLimit` (5): пауза `crashDelaysMs [1, 2, 5, 15, 60] с`, строка в журнал `gateway exited (code/signal); restarting in N s`; при превышении — `#finish(code)` как сейчас (постоянный сбой нельзя прятать). Опции в `SUPERVISOR_DEFAULTS`. Для тестов `deps.now` уже инжектируется.
  2. (А) `tools/start-gateway.mjs`: супервизор включать и без `GATEWAY_RESTART_ON_PATCH`, когда задан `GATEWAY_SUPERVISE=1` (публичный запуск ставит его сам); при `0` — прежнее поведение.
  3. (Б) `restartDecision`: параметр `playerDeadlineMs` (по умолчанию `0` = ждать бессрочно, как сейчас; владелец задаёт `GATEWAY_RESTART_DEADLINE_MIN`, например 15): после срока с момента «осевшей» сборки `players` больше не блокируют; `shutdown` дочернему — `{ reason: "restart", force: true }`; `superviseGateway` при `force` закрывает мосты кодом `4001` с причиной `gateway-restart` вместо `declined`. Каждое объявление за 60 секунд: gateway в `/client/patch-status?summary=1` добавляет `restartAt` (для баннера: «Сервер обновится через N мин»).
  4. (Б) `PatchChainChanged.ts` `describePatchState`: строка с временем до перезапуска, если `restartAt` есть; иначе текст как сейчас. Игрок получает код 4001 → `10.06` показывает «Сервер перезапускается», возврат на экран входа.
- **Тесты.** `tests/gateway-supervisor.test.mjs` (расширить; там уже поддельный `fork` и ручные часы): падение `running` — второй `spawn` после паузы 1 с; шестое падение за 10 мин — `exit` с кодом; падения реже окна не накапливаются; `stop()` во время паузы — без нового `fork`; `restartDecision`: при `playerDeadlineMs` и `now - settledAt >= deadline` возвращает `restart` с `force`, до срока — `wait/players`; `superviseGateway` (файл `SupervisedGateway.ts`): `shutdown { force: true }` закрывает мосты с 4001 и выходит, `restart` без `force` при игроках — `declined` (регресс). ### 10.18 — Игроки по http без `crossOriginIsolated` не получают воркер поз (Риск, S)
- **Вывод.** Заголовки COOP/COEP этот случай **не лечат**: изоляция от других источников включается только в защищённом контексте, а `http://<публичный адрес>` таковым не является — это прямо сказано в коде владельца (`electron/main.cjs:105-114`: «…the crowd pose worker needs cross-origin isolation; both exist only in a secure context, which plain http on a public address is not»; тот же довод в `online/README.md:85-89`: «в браузере по http нет Web Crypto … и нет cross-origin isolation, поэтому позы толпы считаются в основном потоке»). Сервер уже шлёт `Cross-Origin-Opener-Policy: same-origin` и `Cross-Origin-Embedder-Policy: credentialless` (`vite.config.mjs`, `CROSS_ORIGIN_ISOLATION_HEADERS`, стр. ~148-151; `electron/static-server.cjs:33-36`) — на не-loopback http браузер их игнорирует. Приложение игрока изоляцию получает только потому, что `main.cjs` помечает origin безопасным (`unsafely-treat-insecure-origin-as-secure`).
- **Подход.** Настоящее решение — TLS (`10.02`): на `https://…` `crossOriginIsolated` становится `true` без правок кода. Запасной путь без `SharedArrayBuffer` (воркер с передачей буферов сообщениями и удвоенной буферизацией палитр) — подсистема XL с выигрышем только для веб-игроков по http, поэтому **не строить** без явного решения владельца; вместо него — видимость и документация.
- **Сверено.** `src/browser/PoseEngine.ts:570-584`, `pagePoseEngine()`: `crossOriginIsolated !== true || typeof Worker === "undefined"` → `undefined` молча; `?poseworker=0` отключает; `PoseEngine.create` возвращает `undefined` без `SharedArrayBuffer`/`Atomics` (стр. 197-206); цифра «−17…21 % FPS на стенде» взята из текста пункта плана (10.18), в этой работе не перемерялась; отчёты по производительности — в `docs/`. После `1.02` первая половина комментария `main.cjs:109` про Web Crypto устарела (вход по http уже работает) — обновить.
- **Изменения.**
  1. `src/browser/PoseEngine.ts` `pagePoseEngine()` (стр. 570-584): при отказе один раз `console.info("[pose] воркер поз выключен: " + причина)`, причина — `"страница не изолирована (crossOriginIsolated=false: http вне loopback или нет COOP/COEP)"`, `"нет SharedArrayBuffer"`, `"?poseworker=0"`; экспортировать `poseEngineStatus(): { state, reason }` для панели производительности (`RenderStats`/`PerformanceCapture` — файлы другой линии, только подключение).
  2. `electron/main.cjs:105-114`: комментарий привести в соответствие (только изоляция; Web Crypto уже не нужна); для `https`-страницы переключатель не добавляется (`10.02`).
  3. `online/README.md` («Ограничения») и `docs/DISTRIBUTION_PLAN.ru.md`: пояснить, что COOP/COEP по http не работают, единственный путь — TLS или приложение игрока.
- **Тесты.** `tests/pose-engine-status.test.mjs` (новый, чистые функции; `pagePoseEngine` кэширует состояние модуля — тест выносит решение в `poseEngineAvailability(scope)`): `crossOriginIsolated: false` → `{ state: "off", reason: …isolated… }`; `true` без `SharedArrayBuffer` → `no-sab`; `?poseworker=0` → `query`; `true` + `SharedArrayBuffer` + `Worker` → `on`. Мутация: возвращать `on` при `crossOriginIsolated: false`. Регресс: существующие `tests/pose-engine*.test.mjs` (Grep по `PoseEngine` в `tests/`) без правок.
- **Офлайн-проверка.** тест выше; `.runtime/ui-audit` не нужен.
- **Живая проверка.** → 14.24/14.26 (FPS gate): на тестовой раздаче открыть по `http://172.30.240.1:8091/` (`PUBLIC_BIND=172.30.240.1`) — в консоли строка о причине; то же по `https://` (после `10.02`) — воркер запущен, кадры в толпе быстрее (замер по методике `bench/`, не оценка).
- **Зависимости.** `10.02` (TLS решает по существу), `1.02`. Владельцу: нужен ли запасной путь без SAB (XL) — иначе закрыто документацией и TLS.
- **Риски и открытые вопросы.** Веб-игроки по http без TLS остаются на главном потоке — это оценочное «−17…21 %» относится к стенду владельца (толпа Штормграда), у игрока на слабом железе может быть иначе; замерить на реальном не-isolated клиенте при возможности.
