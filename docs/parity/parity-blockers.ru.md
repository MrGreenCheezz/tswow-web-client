# Незавершённые проверки совместимости

## P0: штатное окно выдачи и сдачи квестов в мировом FrameXML

- Для штатного мирового FrameXML (настройка «Оригинальный интерфейс WoW», `originalFrameXml`; `?framexml=1` лишь переопределяет её) добавлен отдельный владелец `QuestFrame`: при успешном структурном gate он направляет новые серверные страницы в `QUEST_GREETING/DETAIL/PROGRESS/COMPLETE`, завершение — в `QUEST_FINISHED`, а появление метаданных предметов/заклинаний — в `QUEST_ITEM_UPDATE`. Native диалог остаётся fallback при неподдерживаемой странице или ошибке штатного Lua. Обычный DOM-режим сохраняет native окно. Живой Маршал Дугхан открыл именно stock QuestFrame; native `.quest-window` был скрыт. Принятие задания сервером подтверждено ростом счётчика журнала с 1 до 2. Сдача, платная награда и парное сравнение с оригиналом ещё не проверены.
- Пакетно подтверждённые C API для приветствия, деталей, прогресса, награды и команд уже привязаны к `LiveWorldSeam` через отдельный адаптер. Индекс выбора награды Lua 1-based переводится в 0-based для пакета; недопустимая или устаревшая страница не отправляет команду. Это ещё не проверка stock окна: подтверждение платной сдачи остаётся ответственностью его `StaticPopup`.
- Изолированный `UnitExists/UnitName("questnpc")` seam берёт только активный GUID квеста и загруженный объект типа unit/player; при неизвестном типе и gameobject возвращает false/nil. `SetPortraitTexture(QuestFramePortrait, "questnpc")` берёт этот GUID только при положительном серверном `UNIT_FIELD_DISPLAYID`, отдаёт его существующему 3D рендереру портретов и оставляет под canvas штатную иконку книги. Отсутствующий/нулевой display не заменяется выдуманной моделью. Живой портрет NPC ещё не проверен.
- Чистый `FrameXmlQuestLifecycle` сопоставляет новые страницы `questList/questDialog` с `QUEST_GREETING/DETAIL/PROGRESS/COMPLETE` и закрытие с `QUEST_FINISHED`; повторная перерисовка и сообщение об ошибке не создают лишних событий. Для `QUEST_ITEM_UPDATE` используется отдельный результат асинхронного кеширования, без синтеза этого события из обычной перерисовки. Mounted MPQ-тест прошёл GREETING → DETAIL → PROGRESS → COMPLETE и обновление метаданных.
- Из выбранных пакетов выведены и проверены таблицы меню, текста/прогресса, предметов/награды и флагов; 35 имён C API зарегистрированы в общем seam. По доступному снимку журнала `GetActiveTitle` различает complete/incomplete; тривиальность задания остаётся nil без подтверждённого правила `GetQuestGreenRange`. Неизвестные имя или иконка награды остаются nil до кеширования, строка титула по `titleId` не выводится из пакета. `GetFactionInfoByID` использует асинхронно загруженный `/dbc/reputation?v=1` и полный снимок репутации, включая строки под свёрнутым заголовком. Именованный `PlaySound` подключён к SoundEntries.dbc. Mounted тест выбранного MPQ проверил X/Escape с одним `CMSG_CANCEL`, принудительное закрытие и серверный FINISHED без лишнего CANCEL, локализованную ошибку выбора награды и сообщения об отказе. Узкие 35/35, TypeScript, production-сборка и полный source suite до последующих правок прошли. Живая выдача подтверждена, награда и авторитетный итог сдачи не проверены.

## Графика: лимит наружных M2 в плотной сцене

> **04.10: раздел устарел, ниже — история.** С 26.09 у наружных M2 своя квота `ENVIRONMENT_SCENERY_BUDGET = 1024` с дальностью по размеру модели и настройкой «Дальность прорисовки объектов» ([STREAMING_OPTIMIZATION](../STREAMING_OPTIMIZATION.ru.md), «Дальность прорисовки деревьев»). Числа 320 (`ENVIRONMENT_BUDGET`) и 48 (`ENVIRONMENT_FAR_BUDGET`) в `src/browser/WorldRenderer3D.ts` теперь — квоты ближних наружных WMO и дальних оболочек WMO. Блокер Chrome `0xC0000022` снят: стенд `bench/run.mjs` с 23.09 снова работает на аппаратном GPU, валидные серии 26–28.09 — шаги 16–21 в [PERF_STATUS](../PERF_STATUS.md). Остаётся открытым только парный кадр оригинала; полнота сцены вживую не мерена.

- **Подтверждено на данных выбранного оригинала:** в направлении контрольной камеры Златоземья центр 617 наружных M2 одного тайла находится внутри frustum; текущий ближний лимит допуска равен 320. Это анализ размещений и алгоритма, а не парный кадр оригинала.
- **Исправлено частично:** visual tile v4 публикует консервативный радиус безопасных статичных M2 из исходных вершин. На тайле Златоземья это 1260 размещений; старый холодный отбор тратил места на объекты позади камеры, а регрессия с видимым деревом id 12096 теперь проходит. Анимированные, с эффектами и некорректные модели остаются fail-open.
- **Не подтверждено:** число пропущенных объектов в игровом кадре после прогрева, их визуальная важность и цена большего лимита в p95/p99 RAF/GPU. Аппаратный browser benchmark завершался `0xC0000022` у GPU-процесса; отдельный профиль и кэш Chrome внутри workspace дали тот же результат до создания страницы. Синхронного кадра оригинала нет. Не повышать лимит только по количеству размещений: сначала снять парные сцены и текущий FPS-профиль, затем проверить изменение видимых объектов и полный кадр.
- **Проверена граница без изменения лимита:** у трёх размещений растительности исходные сферы пересекают дальность 600 ярдов, хотя центры лежат дальше. Пробный допуск каждого кандидата оставил дальнюю квоту 48 заполненной и итог 673 объекта: простой перенос проверки расстояния на радиус не возвращает эти модели в кадр. Отбор 320 ближних и 48 дальних требует парного кадра и аппаратного профиля перед изменением порядка или размера квоты. Изменений рендера по этой гипотезе нет.

## P1: подтверждение покупки за ItemExtendedCost в stock MerchantFrame

- **Подтверждено:** ItemExtendedCost.dbc имеет 16 полей по активному TrinityCore (DBCStructure.h, DBCfmt.h); gateway выдаёт каталог; GetMerchantItemInfo передаёт extendedCost=true, GetMerchantItemCostInfo — честь, очки арены и число предметов, GetMerchantItemCostItem — текстуру и количество. В canned stock MerchantFrame после MERCHANT_SHOW видны строка и AltCurrencyFrame, денежный фрейм скрыт при цене 0. Узкие source-тесты и typecheck проходят.
- **Исправлен узкий разрыв:** штатный `MerchantFrame_ConfirmExtendedItemCost` запрашивает через `GetItemInfo(link)` качество требуемого предмета. Добавлен cache-only префикс `GetItemInfo` (имя, ссылка, качество); неизвестный предмет возвращает nil. Изолированный тест исполняет фрагменты `MerchantFrame.lua` и `StaticPopup.lua` непосредственно из выбранных MPQ: редкий жетон открывает `CONFIRM_PURCHASE_TOKEN_ITEM`, а принятие вызывает ровно один `BuyMerchantItem(1,1)`. Остальные поля полного native `GetItemInfo` этим срезом не реализованы.
- **Исправлен полный mounted stock путь:** новая дочерняя проба локализовала скрытую `Bridge.Click` ошибку: `StaticPopup.lua:3151` обращался к отсутствующему `StaticPopup1MoneyInputFrame`. В вертикальном TOC не хватало исходных `MoneyInputFrame.lua` и `.xml`, хотя `StaticPopup.xml` наследует их шаблон. Они загружаются в штатном порядке. Ограниченный 30 секундами тест MPQ/виджета теперь проверяет правый клик, видимый `CONFIRM_PURCHASE_TOKEN_ITEM`, отмену без покупки, повторный клик и принятие с одной записью `{slot:9,count:1}`; Lua-ошибок нет. Старый TODO снят. Это проверка canned seam, а не серверного списания.
- **Закрыта опасная ветка:** пока запись ItemExtendedCost отсутствует или запрос каталога не удался, GetMerchantItemInfo сообщает isUsable=false, а LiveWorldSeam.buyMerchantItem отклоняет прямую попытку купить товар с неизвестной стоимостью. Это проверено отдельно для ожидания, повторной неудачи и восстановления после загрузки DBC; покупка за обычные деньги остаётся доступной.
- **Следующий критерий:** с настоящим `WorldClient` согласие отправляет ровно один `CMSG_BUY_ITEM` с исходным vendor slot; живой realm возвращает авторитетный успех либо отказ при нехватке стоимости. Отдельно требуется браузерный кадр и взаимодействие смонтированного окна.
- **Найденный изолированный сценарий:** соседний `F:\tswowRoot\tswow-tests\datascripts\items\currency.ts` задаёт торговцу `TEST_ITEM_VENDOR` покупку за пять единиц специальной валюты; рядом есть обычные и ограниченные позиции в `items/item-vendor.ts` и `npc/vendor.ts`. Сейчас в выбранном `tswow-install/modules` есть только `default`, поэтому эта фикстура не является живой частью realm. Её можно использовать лишь после установки в отдельном согласованном тестовом окружении; рабочие данные и патчи не изменялись. Независимая C++ реализация в `CPPClientExample/wowee/src/addons/lua_inventory_api.cpp` полезна как вторичная проверка C API, но формат и права покупки подтверждаются выбранным TrinityCore.

## P1: сквозной stock Trainer с живым WorldClient

- **Подтверждено:** `BuyTrainerService` уже проходит через `LiveWorldSeam.buyTrainerService` и `WorldClient.learnFromTrainer` к `CMSG_TRAINER_BUY_SPELL` (GUID uint64 + spell ID int32 по активному TrinityCore). Имеющийся MPQ-тест нажатия штатной кнопки с canned seam проходит. Новый узкий тест проверяет живой seam, фильтр видимых строк и точное 12-байтовое тело отправленного пакета; ответы success/failure покрыты тестами WorldClient.
- **Не получилось подтвердить:** единый MPQ-тест, который одновременно открывает stock Trainer поверх настоящего `WorldClient` и нажимает кнопку. Две проверки зависали при открытии окна после `owner.show`, до нажатия, без результата теста. Этот экспериментальный тест удалён; рабочий MPQ-тест не изменён. На живом realm открыта Мишель Белль (`trainer.Type=2`): она по текущему подтверждённому контракту остаётся в native UI, не в stock TrainerFrame. Первоначально список был пуст из-за отсутствия предварительной загрузки spell metadata в native ветке; код исправлен, 20 узких тестов и TypeScript прошли. Живое повторное открытие и обучение, а также stock тренер класса не проверены.
- **Остаток по UI:** `CollapseTrainerSkillLine` и `ExpandTrainerSkillLine` сейчас только обновляют окно. Текущая проекция не содержит строк `header`; `GetTrainerServiceInfo` возвращает только известные spell-строки. Группировку из `requiredSkillLine` не выводили: это поле пакета задаёт требование к навыку и не подтверждает заголовок группы. Нужен источник группировки и отдельный критерий раскрытия строк.
- **Повторная проверка источника:** выбранный `Blizzard_TrainerUI.lua` только сворачивает уже готовые строки с `serviceType="header"`; алгоритма создания групп в Lua нет. `NPCPackets.cpp::TrainerList::Write` не передаёт заголовок или категорию, а `ReqSkillLine` из `Trainer.cpp` служит требованием к навыку. Даже `SkillLineAbility.dbc` не даёт однозначной категории: 65 spell ID принадлежат нескольким линиям. Автоматически создавать заголовки из `ReqSkillLine` нельзя. Для реализации нужен наблюдаемый список услуг и состояние сворачивания оригинального 3.3.5a либо подтверждённый клиентский алгоритм; код не менялся.
