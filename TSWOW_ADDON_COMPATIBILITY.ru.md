# Собственные аддоны TSWoW в WebClient

Цель: писать клиентский код в `modules/<creator-module>/addon`, использовать обычные
`shared`-контракты TSWoW и выполнять полученный Lua в WebClient. Совместимость произвольных
сторонних WoW-аддонов не является критерием готовности этой работы.

## Регрессия спутников после сборки, 2026-09-04

В активном `survival/livescripts/survival.ts` оставался временный глобальный
`CustomPacket.OnReceive` для диагностики флуда. В текущем ядре общий Lua-обработчик
выполняется раньше обработчика конкретного опкода, а следующий `CustomPacketBase::Reset`
обнуляет размер сообщения. Поэтому запрос OP64 с версией 3 читался как 0, OP66 терял ID,
а OP95 — токен рабочих мест. Журнал оригинального клиента подтвердил ответы OP65/OP96;
воспроизведение legacy-ответа показало испорченное имя/ID второго спутника и ложную экспедицию.

Диагностика удалена из исходника модуля; survival сохраняет только подписку OP60.
Проверка `node --test tests/tswow-survival-packet-routing.test.mjs` воспроизвела потерю
версии `3 → 0` до исправления и проходит после него. По прямому указанию пользователя
«пересобери» выполнена штатная команда `build scripts default.dataset --no-inline`:
все девять серверных модулей собраны, код завершения 0. В установленном Lua survival
проверены отсутствие диагностики и единственная подписка OP60; три целевых теста прошли.
Сервер в момент сборки не был запущен: исправленный Lua загрузится при следующем запуске.

Сценарий `custom-companions` в `tswow-addons:check` теперь проверяет две записи OP91,
имена, ответ рабочих мест OP99, призыв каждого ID через OP66 и выбор creature entry
для обоих предпросмотров. Это проверка с тестовыми ответами сервера; реальный призыв
и отображение всех моделей нужно повторить в игровой сессии после перезапуска сервера.

В WebClient исправлена отдельная потеря кликов: кнопки `StoreStyle` регистрируют
`AnyUp`/`AnyDown`, а DOM-обработчик учитывал только конкретные кнопки мыши. Теперь
оба режима вызывают исходный Lua `OnClick` на нужной фазе, без повторного вызова
от DOM `click`; отключённые кнопки остаются неактивными. Регрессионный тест в
`framexml-dom.test.mjs` падал до исправления и проходит после него.

Первоначальная проверка: компиляция WebClient через `tsc -p tsconfig.json` и `vite build`,
50 целевых тестов и 8/9 сценариев аддонов. Повторный прогон текущего патча проходит 9/9,
включая `simple-button-addon`. В браузере на настоящем
gateway и `LiveWorldSeam` с тестовыми ответами сервера видны обе карточки; реальные
нажатия «Призвать» отправили OP66 с ID 101 и 202, предпросмотр отрисовал модель волка.
Веб-страницу после изменения нужно перезагрузить; окно открывается командой `/companions`.

Обычный вход запускает Lua наших аддонов поверх нативного интерфейса. `?framexml=1`
дополнительно выбирает диагностическую замену stock HUD. Проверки ниже используют активный
патч и тестовый транспорт; полный gameplay с настоящим сервером не подтверждён.

## Что реализовано

### Загрузка и надписи кнопок, 2026-09-04

Обычный вход на `localhost:5173` загружает аддоны асинхронно. В браузерном стенде с настоящим
`EnterWorld`, рендерингом мира и HTTP-файлами gateway монтаж занял около 14 секунд; это
измерение стенда, а не обещание времени загрузки. Чат теперь показывает «Загрузка аддонов…»,
затем результат. Ранний вызов `/companions` объясняет, что аддоны ещё загружаются. Обычный
чат и уже зарегистрированные команды продолжают работать. Завершение или ошибка снимает
статус только у своей попытки загрузки; результат старого входа не попадает в новую сессию.

Исправлены три причины неверного расположения текста:

- Lua `SetFont(file, height, flags)` раньше терял файл/флаги, а renderer игнорировал заданную
  высоту. Теперь используются настройки конкретного виджета; `SetFontObject` возвращает
  наследуемый шрифт. Поддержаны outline-флаги; `MONOCHROME` сохраняется для `GetFont`,
  отдельная монохромная растеризация не реализована.
- `FontString.SetJustifyV` теперь выравнивает строки внутри заданной области, сохраняя
  цветные фрагменты, переносы строк и горизонтальное выравнивание.
- `<ButtonText/>` без `<Anchors>` центрируется внутри своей кнопки. Такие стандартные
  кнопки используются в окне эхо; раньше абсолютный HTML-текст оставался без координат.
  Явные привязки, включая отступ текста «Призвать» в StoreStyle, сохраняются.

Все три регрессии воспроизведены до исправления. Финальная проверка: TypeScript, Vite build,
63 целевых теста и 9/9 сценариев аддонов. В браузере измерено центрирование 17 кнопок эхо
и вертикальное выравнивание двух кнопок призыва с тестовыми ответами OP91/99. Реальные
клики по миникарте открывают спутников и эхо. Проверены ранний ответ `/companions` и
последующее «TSWoW: загружено 9/9 аддонов»; диагностический список содержит две прежние
ошибки stock FrameXML, ошибок загрузки TSWoW-модулей нет.

Результаты: `.runtime/addon-text-qa.json`, `.runtime/echo-buttons-centered.png`,
`.runtime/companion-buttons-centered.png`. Это проверка интерфейса с тестовым транспортом;
живой ответ сервера на призыв в этом прогоне не проверялся. Эти изменения затрагивают
WebClient: достаточно перезагрузить страницу, новая TSWoW-сборка не требуется.

Изменены `src/browser/glue/GlueWidgets.ts`,
`src/browser/ui/framexml_compat/FrameXmlDomRenderer.ts`, `FrameXmlRuntime.ts`,
`src/browser/ui/Chat.ts`, `src/browser/app/EnterWorld.ts`; регрессии добавлены в
`tests/framexml-dom.test.mjs` и `tests/framexml-world-mount-lifecycle.test.mjs`.

### Возможности runtime

- Общие библиотеки и модули берутся из generated-блоков активного `FrameXML.toc`, в порядке
  сборщика, через ту же MPQ-цепочку, что использует gateway. Список имён в загрузчике не нужен.
- `IsAddOnLoaded` становится истинным после выполнения файлов. Отсутствующий Include/Script,
  ошибка Lua, обработанная ошибка OnLoad или ошибка общей библиотеки не дают успешного статуса.
  Отдельные результаты доступны в `FrameXmlBoot.tsAddonResults` и диагностике `tsAddons`.
- При монтаже FrameXML команды из `SLASH_*` / `SlashCmdList`, определённые TSWoW-модулями,
  регистрируются в браузерном чате. Стандартные команды и каналы сохраняют приоритет.
  Обработчики получают текст аргумента как Lua-значение, без подстановки в исходный код.
- Добавленные из Lua кнопки `GameMenuFrame` получают действия в браузерном меню.
  Например, кнопка магазина вызывает исходный OnClick из `tswow-store`.
- Команды, пункты меню, Lua-ссылки и packet subscriptions освобождаются при снятии runtime.
- При обычном входе отрисовываются созданные TSWoW-модулями виджеты, включая окна, созданные
  позднее командой или ответом пакета. Stock-предки сохраняют только геометрию и видимость,
  их изображения и обработчики ввода не дублируют нативный HUD.
- `CharacterFrame`/`PaperDollFrame` следуют нативному окну персонажа и вкладке листа;
  `Minimap` следует нативной миникарте. Окна из `UISpecialFrames` закрываются через Escape.
- Slash-команды и custom packet callbacks публикуют изменения UI одним пакетом изменений.
  Исправлен разбор `SetPoint(point, relativeTo, x, y)`: пропущенный `relativePoint` больше
  не превращает вертикальные отступы кнопок в горизонтальные.
- Масштаб применяется к отрисовке и геометрии привязок; `GetEffectiveScale` учитывает
  предков. Уже при загрузке Lua `UIParent:GetWidth/GetHeight` возвращают логический размер
  экрана; после монтажа размеры остальных виджетов берутся из DOM. `SetClampedToScreen`
  удерживает окно в области клиента. Обычный Frame поддерживает
  `RegisterForDrag`, `SetMovable`, `StartMoving` и `StopMovingOrSizing`: исходные обработчики
  `StoreStyle` перемещают окно, захват отпускается и за его границами, положение сохраняется
  при Hide/Show в пределах сессии.
- Размер иконки при привязке берётся из заданного аддоном размера, а не из исходного файла
  картинки. Подсветка кнопок скрыта в обычном/отключённом состоянии; `SetHighlightTexture`
  использует аддитивное смешивание по умолчанию и поддерживает явный режим.
- `GameTooltip.SetOwner(..., "ANCHOR_CURSOR")` размещает подсказку у настоящего курсора,
  с учётом масштаба и границ экрана.
- `EnableMouse(true)` разрешает обычным Frame получать ввод. Карточка спутника вызывает
  исходный Lua-обработчик клика и открывает `DressUpModel`. `SetCreature` разрешает запись
  существа в display ID, загружает модель и её текстуры; `SetDisplayInfo` принимает display ID
  напрямую. Скрытые модели не создают WebGL-контекст, устаревшая асинхронная загрузка не
  заменяет новую модель, ресурсы освобождаются при снятии runtime. Навесное снаряжение
  гуманоидных моделей в этом предпросмотре пока не отрисовывается.
- `GetCursorPosition` получает настоящие координаты мыши в логических единицах UI.
  Исходный обработчик спутников вращает модель; главное окно при этом не перемещается.
  Отпускание мыши за моделью, скрытие и снятие runtime завершают исходный `OnUpdate`.
- Наведение на предмет в нативной сумке/экипировке вызывает исходные `GameTooltip`-хуки:
  `custom-stats` отправляет OP97 и добавляет строки OP98 в браузерную подсказку. Сохраняются
  цвета и кеш аддона, поддерживаются строки после восьмой, чужой запоздавший ответ не
  добавляется к новой подсказке.
- `gem-abilities` выбирает реальный предмет в экипировке/сумке и показывает исходную кнопку
  извлечения. Она отправляет OP85 и закрывает окно. Установка новых камней через cursor /
  CMSG_SOCKET_GEMS в этом окне пока не реализована.

## Как проверять новый аддон

1. Создать модуль штатным способом TSWoW. Клиентский вход — `addon/addon.ts`; общие packet-типы
   держать в `shared`, серверные обработчики — в `livescripts`. Не копировать generated Lua в WebClient.
2. Использовать поддержанные Lua/FrameXML API и `CreateCustomPacket` / `OnCustomPacket`.
   Минимальный проверенный путь: `require` общего модуля, создание Frame/Button, обработчик
   `PLAYER_ENTERING_WORLD`, slash-команда, click, ответ custom-пакета и изменение текста виджета.
   Проверка этого пути на новом имени модуля находится в `tests/framexml-tsaddon-generated.test.mjs`;
   она использует настоящие `RequireStub.lua` и `ClientNetwork.lua` установленного TSWoW.
   Это проверка формата и runtime, а не запуск компилятора TypeScriptToLua.
3. Владелец проекта выполняет нужные TSWoW-сборки: при изменении data/tags сначала `build data`,
   при изменении серверной части затем `build scripts`, для клиентского кода — `build addon`.
   В этой рабочей области они также запускают публикацию патчей; агент их не выполняет.
4. Перезапустить gateway и страницу после смены патча. При использовании `CLIENT_PACK_DIR`
   учитывать, что проверяется этот снимок, а не более новый исходный клиент.
5. Добавить в `TSWOW_ADDON_SCENARIOS` файла `tools/check-tswow-addons.mjs` сценарий с наблюдаемым
   результатом: команда/кнопка → ожидаемый пакет → ответ → изменение UI. Это тест аддона;
   runtime не требует регистрации имени нового модуля.
6. Собрать WebClient и запустить `npm run tswow-addons:check`. Новый модуль без сценария,
   отсутствующие файлы, ошибки обработчиков и неверный результат завершают проверку с кодом 1.
7. Проверить тот же сценарий в браузере с реальным сервером. Использование нового API требует
   реализации и отдельной проверки этого API; нейтральная заглушка не считается поддержкой.

`build:autonomous` использует именно этот TSWoW gate. Проверка сторонних каталогов
`Interface/AddOns` остаётся отдельной командой `client-addons:check`.

Для повторной проверки текущих исходников WebClient без TSWoW-сборок:

```powershell
.\.runtime\node\node.exe node_modules/typescript/bin/tsc -p tsconfig.json
.\.runtime\node\node.exe --test tests/framexml-tsaddon-contract.test.mjs tests/framexml-tsaddon-generated.test.mjs tests/framexml-client-network.test.mjs
.\.runtime\node\node.exe tools/check-tswow-addons.mjs
```

Последняя проверка текущего патча возвращает код 0: 9/9 сценариев.
