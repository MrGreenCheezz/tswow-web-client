# Локальный Three.js benchmark

```powershell
npm run bench
npm run bench -- --trace --label diagnosis
npm run bench -- --baseline bench/results/<baseline-timestamp>.json --label candidate
npm run bench -- --scenario world-crowd-50,world-crowd-200 --trace --diagnostic
npm run bench -- --scenario world-crowd-10,world-crowd-50,world-crowd-64,world-crowd-200 --label crowd-lod
npm run bench -- --scenario world-crowd-50 --capture-abba --label capture-abba
npm run bench -- --additive-probe
```

Нужны зависимости из lock-файла, Node ≥22.15 и Google Chrome. На этом рабочем месте
runner автоматически использует `.runtime/node/node.exe`, если системный Node старее.
`BENCH_CHROME_PATH` позволяет выбрать другой установленный Chrome.

Первый запуск автоматически готовит кеш ресурсов через локальный gateway
(`BENCH_GATEWAY_URL`, по умолчанию `http://127.0.0.1:8090`), открывая отдельные сцены.
Следующие запуски читают зафиксированные байты и проверяют SHA-256. Код, ресурсы,
версия браузера, GPU и параметры записываются в JSON. Кеш привязан к выбранному клиенту;
для другого dataset нужен отдельный baseline и новый кеш. Изменять клиент во время
сравнения нельзя. Код рендера собирается перед каждым запуском.
Анимационный Web Worker собирается отдельной точкой входа; сервер отдаёт его compiled JS
по URL, который использует клиент. Его исходники входят в общий source fingerprint замера.
Если на границе видимости обнаружен ранее неизвестный ресурс, runner считает этот
проход подготовкой и автоматически повторяет сценарий в новом Chrome (не более трёх
таких повторов). Решение не зависит от времени кадров. Ошибки не маскируются подбором
«лучшего FPS». После замораживания кеша принимается первый полный проход без новых ресурсов.

`bench/config.json`: 1280×720, pixelRatio 1, seed 12340, 5 секунд прогрева после завершения
загрузок, 20 секунд измерений. Маршрут задаётся функцией от прошедшего времени, а не
числом кадров, поэтому скорость движения не зависит от FPS. Измеряется RAF cadence
в headless Chrome с отключённым лимитом FPS; CPU submit и асинхронные GPU queries
приводятся отдельно. Это не измерение задержки физического дисплея.

На Windows `cpu-policy.ps1` выбирает самый быстрый `EfficiencyClass` через Win32
`GetSystemCpuSetInformation` и ограничивает только процессы тестового Chrome этими CPU
до прогрева. Топология, выбранные logical CPU и affinity сохраняются в JSON;
выбор CPU входит в хеш условий. Это устраняет свободную миграцию между P/E-ядрами
на гибридном процессоре. Другие процессы и общая схема питания не изменяются.
Старый baseline без фиксации CPU сохранён, но для следующих A/B-сравнений используется
`bench/baseline-pcores.json`. Смену условий нельзя считать ускорением исходного кода.
Перед запуском Chrome и вокруг каждого измерения runner снимает внешнюю CPU-нагрузку,
исключая собственные процессы. Более 2 занятых CPU-ядер делает прогон невалидным;
результат сохраняет причину и самые активные процессы. Это защита от конкурирующей
нагрузки, а не попытка автоматически подобрать лучший FPS. GPU-конкуренцию эта проверка
не исключает: тяжёлые приложения должны оставаться вне сравнительного прогона.

- `movement`: настоящий `WorldRenderer3D`, map 0, локальные terrain/splat/grass/scenery,
  10 персонажей, переход через x=-9600. В браузере прогревается только начало маршрута;
  новые тайлы и модели должны проходить обычный streaming в измеряемом участке.
- `crowd-10/50/200`: ровно столько анимированных HumanMale, реальные текстуры,
  228 костей на текущем клиенте, независимые фазы Stand/Run. Используются shipping
  `AnimatedModel`/`ModelBuild`. Это отдельная лабораторная сцена: игровой
  `WorldRenderer3D` имеет лимит 64 и не проверяет одновременно 200 моделей.
  Нет HUD, сетевой симуляции, разнородного снаряжения и поведения сервера.
- Дополнительные `world-crowd-10/50/64/200`: настоящий мир с игроком и 9/49/63/199 NPC;
  персонаж обходит квадратную толпу по кругу, admission остаётся ограничен 64.
  Подготовка проходит восемь направлений, чтобы проверить также сохранённые скрытые rigs.
  Это отдельный профиль для world/units/shadows, не замена лабораторным 200 видимым моделям.
  В серии 10/50/64/200 первые три случая показывают изменение стоимости в пределах
  лимита допуска, а 200 проверяет стоимость скрытых NPC при том же пределе 64.
`--diagnostic` разрешён только вместе с `--trace`: сохраняет данные даже при внешней
нагрузке и добавляет счётчики обновлений костей/пропусков скрытых NPC. Всегда помечается
valid=false/comparable=false; ни FPS, ни этот инструментированный код не служат A/B.

`--capture-abba` запускает четыре последовательных 20-секундных прохода
`world-crowd-50` в одном Chrome: запись world submission выключена, включена,
включена, выключена. Прочее диагностическое инструментирование не включается.
Каждый проход сохраняет FPS, CPU, GPU, пик JS heap, условия нагрузки и исходные кадры
в `captureAbbaResult.runs`; внешняя нагрузка свыше двух ядер и новые ресурсы делают
результат невалидным. Это отдельный эксперимент с накладными расходами записи,
`comparable=false` для обычного baseline рендера.

Живая запись через окно диагностики `O` → «Записать фризы (60 с)» теперь сохраняет
`events.checkpoints[].renderer.worldSubmission`. Один world pass раз в 500 ms
разделяется на `matrices`, `mainSkeletons`, `mainDraws`, `shadowSkeletons`,
`shadowDraws`, `shadowOther`, `other`. Это непересекающиеся CPU-интервалы:
их сумма равна `totalMs`; GPU и работа между callbacks сюда не входят.
`mainDraws`/`shadowDraws` в `calls` — фактические вызовы отрисовки из renderer.info,
а `ageMs` — возраст образца при checkpoint. `hookSetupRestoreMs` учитывает
установку/снятие перехватов; дополнительные вызовы таймера внутри прохода остаются
в измеренных интервалах. Такой профиль локализует расход, но не служит A/B FPS.
Без явной записи этот инструмент выключен. В `--diagnostic` те же данные находятся
в `scenarios[].worldSubmissions`; это проверка инструмента, а не запись игрового клиента.

Ту же запись запускает команда консоли DevTools `webclientRecordFreezes()` (F12 в Electron): 60 секунд
или до повторного вызова, файл сохраняется сам — так её можно сделать и с оригинальным интерфейсом
FrameXML, где клавиша `O` открывает окно друзей.

С версии 2 запись фризов содержит то, чего нет на стенде: `jsProfile` — выборки стеков JS
Self-Profiling API за всю минуту, включая работу между кадрами (обработчики пакетов, продолжения
загрузок) и шаг интерфейса FrameXML, который идёт в своём `requestAnimationFrame` и не входит в `cpuMs`;
`frameXmlSteps`/`frameXmlSyncs` — шаги и перерисовки HUD между кадрами дольше 4 мс; `packets` —
время обработчиков пакетов по опкодам и по секундам, `slowPackets` — отдельные пакеты дольше 4 мс;
`heap` в checkpoints. Профилировщику нужен заголовок страницы `Document-Policy: js-profiling`:
его ставят `vite.config.mjs` (`WEB_JS_PROFILING=0` — без него) и Electron-оболочка (`--no-js-profiling`
— без него); без заголовка запись идёт как раньше, а `entrySupport.jsProfiler` объясняет причину.
Chromium на Windows берёт выборку раз в 16 мс (фриз в 100 мс — около 6 выборок), маркеров GC нет.

`node bench/analyze-live-profile.mjs <capture.json> [--maps dist/sourcemaps] [--threshold 50] [--out report.json]`
разбирает каждый интервал между кадрами длиннее порога: функции по собственному и включающему
времени, файлы, типичные стеки, а рядом — секции игрового кадра, шаги FrameXML, медленные пакеты,
скрипты long animation frames и куча. Позиции минифицированной сборки переводятся в исходники по
картам `dist/sourcemaps` — их пишет `vite build` (`sourcemap: "hidden"`, из `dist/web` карты уносятся,
в Electron-сборку и приложение игрока не попадают). Карты должны быть от той же сборки, что писала запись.
`--js-profiling` у `bench/run.mjs` отдаёт страницу стенда с тем же заголовком (`valid=false`) —
для замера его цены.

`node bench/analyze-live.mjs <capture.json> <report.json>` сводит живую запись:
полные RAF/CPU, 1% low, >30 ms, десятисекундные участки и разбиение world submission.
`checkpointTimeline` сопоставляет те же десятисекундные участки с числом персонажей,
скелетов, вызовов рисования, ресурсов и стоимостью отдельных этапов отправки мира.
Если запись содержит `drawKindsMs`, сводка и `checkpointTimeline` показывают время
`mainSkinned`, `mainNonSkinned`, `shadowSkinned`, `shadowNonSkinned` внутри
`mainDraws`/`shadowDraws`.
Для старых записей соответствующие распределения имеют `count: 0` и `mean: null`.
В новых записях `animationLod` показывает количество персонажей по дистанциям и число
полных/пропущенных обновлений позы; в старых записях эти поля остаются пустыми.
Сводка явно отличает все кадры от выбранных медленных callbacks и от GPU rolling windows.

`node bench/live-periods.mjs <capture.json>... [--period 6.944] [--json out.json] [--vs <capture.json>...]`
считает живую запись в периодах развёртки (144 Гц: P = 6,944 мс, `k = round(интервал / P)`):
перцентили интервала в мс и периодах, долю интервалов в ±0,7 мс от кратного P (ниже 90 % —
предупреждение: дисплей не 144 Гц), гистограмму периодов, K2 — долю кадров с k ≤ 2 (цель кадра
`docs/implementation/line-P.ru.md` §3), CPU колбэка против двух периодов, скрытую цену H (CPU колбэка ≤ 2P, а интервал, в котором он идёт, —
следующей строки — ≥ 3 периодов), корзины CPU по той же паре, задержку старта колбэка от rAF, окна по 10 с, кучу (рост по checkpoint, падения ≥ 20 МБ и
интервалы > 50 мс, закончившиеся между предыдущим и этим checkpoint), предупреждения при окне не 1920×1080, сводки FrameXML, пакетов, программ и LoAF, поля телеметрии
P1-04, если они есть, и проверку цели (K2 ≥ 95 %, p99 ≤ 3 периодов, 0 интервалов > 100 мс). Несколько
файлов — проходы одной сцены: строка на файл, медианы, худший проход (цель судится по нему);
`--vs` — вторая группа и разность медиан, отмеченная, если она больше разброса проходов.

`--scenario city-arrival` — та же площадь, но толпа появляется во время замера: подготовка идёт
с одним игроком, затем каждую секунду приходят 8 юнитов (все 127 — к 16-й секунде), как при въезде в
город. Обычный `city` строит всех до замера и поэтому не видит цену первого появления юнита: сборку
шейдеров его материалов и клонов спавн-фейда, декодирование текстур, разбор анимаций из воркера.
Первый замер 27.09: 87 FPS в среднем, но 1% low 14.5 FPS и кадры 278/200/135 мс (`--trace`:
7 программ юнитов собраны в `render`).

`--scenario city` — Штормград, торговый квартал (`bench/city.json`): настоящий WMO города,
пол 93.95, 128 юнитов в радиусе (64 допускаются) из 17 разных displayId — стражники, разные
расы, ребёнок, волк; 16 ходят по кругу. 1920×919 и настройки живой записи: lightingQuality 2,
glow, god rays, трава 80/3. Камера облетает игрока на 18 ярдах. Сценарий запускается один
(у него свой viewport); блок `city` входит в configHash только его прогонов. Это ближайший
к живой толпе стенд: ~1300 draw calls, как в записи 23.09.

Опции разработки, всегда `valid=false`:
- `--allow-load` — не прерывать прогон при внешней нагрузке >2 ядер (она всё равно пишется).
- `--variant <dir>` — файлы `<dir>/<путь от src>` заменяют исходники в бандле, рабочее дерево не
  трогается; для A/B чередуйте прогоны с вариантом «до» и без него. Хеши заменённых файлов
  входят в `sourceHashes` как `variant:<путь>`. Вариант может и добавить модуль, которого нет в
  `src/` (относительный импорт, не найденный в дереве, берётся из `<dir>`; его исходный хеш —
  `variant-only`), — так перемеряется отклонённый шаг с новым файлом, не возвращая его в дерево.
- `--cpu-class slowest` — закрепить Chrome на E-ядрах вместо P-ядер. На этом i7-12700KF/Windows 10
  город стоит 22 мс CPU против 13 мс на P-ядрах (1.7×), что совпадает с живой записью.
- `--cpu-class none` — не трогать ядра Chrome: так страница работает у игрока в обычном браузере.
- `--headed` — Chrome с видимым окном вместо headless.
- `--browser electron` — та же сцена в Electron-оболочке `electron/main.cjs` (сначала `npm install` в
  `electron/`); оболочка сама применяет `--cpu-class` к своим процессам и повышенный приоритет,
  бенчмарк подключается к ней через DevTools-порт и перепроверяет маску. Сравнение «как у игрока» и
  «в оболочке»: `--browser chrome --headed --cpu-class none` против `--browser electron`.
- `--diagnostic` дополнительно пишет `sceneStats` (перепись графа сцены и вызовы отрисовки по
  веткам, материалы, двусторонние проходы) и `textureUploads` (явные `initTexture`: тип, размер, мс).
  В `worldSubmission.calls` добавлены `mainMaterialSwitches`/`mainProgramSwitches`.
- `--target <es2022|modules|список>` — уровень JavaScript бандла стенда (`bench/build.mjs`, esbuild
  `target`). По умолчанию `es2022` — тот же, что у боевой сборки с MEM-1 (`vite.config.mjs`
  `BUILD_TARGET`): `#private` и поля классов остаются родными. `modules` — прежний уровень боевой
  сборки (`es2020, edge88, firefox78, chrome87, safari14`, умолчание Vite 6.4.3): esbuild понижает
  `#private` до WeakMap-помощников (`__privateGet`/`__privateSet`/`__privateWrapper`) и поля до
  `__publicField`; список вида `es2020,chrome87` проверяется. Прогон с уровнем не `es2022` невалиден —
  это сторона A/B (`--target modules` против умолчания), не база. Уровень пишется в `bundle.target`
  результата и в `sourceHashes["bundle-options"]`; `sourceHash` покрывает только исходники, поэтому
  у сторон такой пары он совпадает. Боевую сборку на помощники проверяет
  `node tools/check-dist-target.mjs [каталог…]` (по умолчанию `dist/web`; код 1 — помощники найдены,
  2 — каталога нет).
- `--js-flags "<флаги V8>"` — Chrome/Electron с этими флагами V8, например
  `--js-flags "--allow-natives-syntax"` для проверки вида массивов (`%HasDoubleElements`) из варианта
  стенда. Проверку вида делайте до любого кода, который читает массивы разных видов в одном месте:
  такое чтение само переводит их в общий вид.

`--settings <файл>` запускает стенд с настройками игрока: объект `settings` из записи фризов (или
файл только с этими значениями) применяется к рендеру так же, как страница
(`src/browser/RendererGraphicsSettings.ts`), поверх графики сценария. Настройки входят в config, так
что сравнимы только прогоны с одинаковыми настройками.

`--heap-profile` снимает выборку выделений памяти (CDP HeapProfiler, шаг 16 КиБ) за измеряемые секунды
и пишет `<сценарий>.heapprofile` рядом с результатом; прогон несравним, как `--trace`.
`node bench/analyze-heap-profile.mjs <файл.heapprofile> [--map bench/build/harness.js.map] [--top 30]`
сводит байты по функциям через карту бандла стенда — карта перезаписывается каждым прогоном, для
старого профиля сохраняйте её копию. Это объём выделений (включая умершие молодыми), а не удержанная
память; выделения во встроенных V8 функциях приписываются внешней.

Подготовка кеша ресурсов больше не зависит от политики CPU: смена `--cpu-class` не запускает её.

Страница стенда, как и dev-сервер (`vite.config.mjs`), отдаётся с `Cross-Origin-Opener-Policy:
same-origin` и `Cross-Origin-Embedder-Policy: credentialless`: без cross-origin isolation нет
`SharedArrayBuffer`, и позы толпы не уходят в Web Worker (`src/browser/PoseEngine.ts`, шаг 17).
`--no-isolation` снимает заголовки (всегда `valid=false`) — так мерится страница без воркера поз.
Воркер поз собирается отдельной точкой входа `PoseEngine.worker.ts`, как анимационный. В результате
`scenarios[].hardware.crossOriginIsolated` и `scenarios[].poseWorker` — задания за замер и кто их
посчитал (`worker`, `stolen` — страница раньше воркера, `overridden` — страница забрала у опоздавшего
воркера, `waitMs`/`mainMs`). В игре воркер выключает `?poseworker=0`, `?poseworkers=N` задаёт 1–4 потока.

`node bench/framexml-probe.mjs [--seconds 10] [--profile] [--hover ActionButton1] [--open CharacterMicroButton] [--label name]`
— стоимость кадра оригинального интерфейса: открывает dev-страницу `framexml.html?toc=vertical`
(нужны Vite на 5173 и локальный gateway; игрового соединения нет) в headless Chrome без
ограничения FPS, собирает интервалы rAF, Long Animation Frames и время `sync`/`tick` рендера
и моста; `--profile` сохраняет `.cpuprofile`. Результаты — `bench/results/framexml/`.

`--additive-probe` — отдельная диагностика двойного прохода аддитивных материалов.
36 instances шести реальных WVM-эффектов, фиксированный seed 12340, 1280×720/DPR=1;
включены скелеты, частицы, ribbons, текстуры, туман, fade и перекрывающая геометрия.
Сравниваются те же буферы и позы до/после переключения только forceSinglePass.
36 ракурсов сравниваются по пикселям; скрытие аддитивных материалов служит отрицательным
контролем, чтобы совпадение невидимых эффектов не засчитывалось как визуальная проверка.
Считаются draw calls и обращения к customProgramCacheKey внутри getParameters;
два режима чередуются по схеме ABBA для диагностического CPU submit. Результат и PNG
сохраняются в `bench/results/<timestamp>`. Этот профиль всегда comparable=false:
он не измеряет FPS целого мира и не заменяет обязательные movement/crowd-сценарии.

Средний FPS = 1000 / средний интервал RAF; 1% low = 1000 / среднее худшего 1% интервалов;
p99 — nearest rank; >30ms — строго больше 30. Первый интервал начинается после прогрева.
Пик JS heap снимается с каждого кадра через `performance.memory` с precise-memory-info.
Потерянные/недоступные GPU samples не считаются нулевыми.

Скриншоты снимаются после замеров, на фиксированных точках и одинаковой фазе анимации.
Для дополнительных world-crowd снимки строятся в новой подготовленной сцене: история
загрузки на границах видимости во время пролёта зависит от количества кадров.
Политика снимков записывается в JSON; сравнение разных политик отклоняется.
Сравнение с `--baseline` проверяет размеры, число изменённых пикселей и дельты каналов;
для мира учитывайте недетерминированный порядок асинхронного допуска новых объектов.
Численные дельты требуют визуального разбора, а не автоматического объявления паритета.

Результаты: `bench/results/<timestamp>.json`, изображения и trace в соседнем каталоге.
Они и клиентские ресурсы исключены из Git. Сводка принятого baseline — `bench/baseline.json`.
`--smoke` сокращает только техническую проверку до 3 секунд и никогда не даёт valid baseline;
`--scenario movement,crowd-200` выбирает подмножество; `--prepare` только наполняет кеш.
Ошибки ассетов, отсутствующая высота маршрута, программный GPU и новые ассеты в измеряемом
участке делают результат невалидным. Trace/CPU profile включаются только отдельным
запуском: overhead профилировщика не смешивается с сравнением производительности.

С `--trace` сценарий дополнительно пишет: `programEvents` (новые программы по вызовам
`compile`/`render`; в первой записи — `parallelShaderCompile` и `checkShaderErrors` рендерера),
`programFirstUse` (первая отрисовка каждой новой программы: сколько она длилась — программа, ещё
не слинкованная, ждёт драйвер — и цепочка объекта), `compileCalls` (каждый вызов прогрева
`renderer.compile`: время, число материалов, мс), `benchStartMs` (`performance.now()` начала
замера: `atMs - benchStartMs` совпадает с `frames[].rafAtMs`) и `debug` — записи, которые вариант
может класть в `window.__benchDebug`. Стенд собирается без Vite-окружения, поэтому
`renderer.debug.checkShaderErrors` в нём включён (как в dev): первая отрисовка программы делает
синхронные запросы журналов, которых в production-сборке нет.

## Lookdev: стоп-кадры реального мира без сервера

`bench/lookdev.mjs` рисует тот же мир, что и стенд (настоящий `WorldRenderer3D` поверх
неизменяемого кеша ресурсов), но ничего не измеряет: выбранное время суток, камера, погода и
настройки игрока, а на выходе — PNG, чтобы сравнить освещение, тени, лучи или дождь до и после
правки. Недостающие ресурсы берутся из gateway (`BENCH_GATEWAY_URL`) и остаются в кеше.

```powershell
node bench/lookdev.mjs --scenario city --settings enhanced --out bench/results/lookdev-city `
  --frame noon=1440,0.6,-0.35,18 --frame golden=2080,1.571,-0.2,20 --frame rain=1500,0.6,-0.3,18,rain:0.9
node bench/lookdev.mjs --scenario movement --settings enhanced --frames 90 `
  --frame sunset=2100,4.712,0.08,3,@-10600/1600
```

- `--frame имя=halfMinute,yaw,pitch,orbit[,погода:сила][,@x/y]` повторяется; погода —
  `rain`, `snow`, `thunder`, `fog`, `sand`; `@x/y` ставит персонажа в эти координаты мира
  (только `movement`, мир подгружается вокруг него). `halfMinute` — полуминуты игровых суток:
  1440 полдень, 2100 закат, 840 утро.
- Yaw задаётся относительно персонажа, который стоит лицом на запад: 4.712 смотрит на запад
  (к заходящему солнцу), 1.571 — на восток. Pitch выше ~0.15 при orbit больше 3–4 ярдов опускает
  камеру под землю — в стенде нет столкновения камеры с рельефом; для вида на небо берите orbit 3.
- `--settings enhanced` — пресет «Улучшенная графика» поверх значений по умолчанию, путь —
  файл настроек как у `bench/run.mjs --settings`; `--set ключ=значение` меняет одну настройку.
  `--population` ограничивает толпу города (по умолчанию 12), `--frames` — сколько кадров
  проходит перед снимком (по умолчанию 90; дождю и пелене нужно ~240).
- Рядом с PNG пишется `lookdev.json` с конфигурацией и статистикой теневого прохода
  (`shadowStats`: вызовы отрисовки и CPU-мс каждого каскада). Кадры с дождём и грозой
  сбрасывают погоду резко перед следующим кадром, чтобы её затухание не попало в чистое небо.
