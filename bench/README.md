# Локальный Three.js benchmark

```powershell
npm run bench
npm run bench -- --trace --label diagnosis
npm run bench -- --baseline bench/results/<baseline-timestamp>.json --label candidate
```

Нужны зависимости из lock-файла, Node ≥22.15 и Google Chrome. На этом рабочем месте
runner автоматически использует `.runtime/node/node.exe`, если системный Node старее.
`BENCH_CHROME_PATH` позволяет выбрать другой установленный Chrome.

Первый запуск автоматически готовит кеш ресурсов через локальный gateway
(`BENCH_GATEWAY_URL`, по умолчанию `http://127.0.0.1:8090`), открывая отдельные сцены.
Следующие запуски читают зафиксированные байты и проверяют SHA-256. Код, ресурсы,
версия браузера, GPU и параметры записываются в JSON. Кеш привязан к выбранному клиенту;
для другого dataset нужен отдельный baseline и новый кеш. Изменять клиент во время
сравнения нельзя. Код рендера собирается перед каждым запуском.
Если на границе видимости обнаружен ранее неизвестный ресурс, runner считает этот
проход подготовкой и автоматически повторяет сценарий в новом Chrome (не более трёх
таких повторов). Решение не зависит от времени кадров. Ошибки не маскируются подбором
«лучшего FPS». После замораживания кеша принимается первый полный проход без новых ресурсов.

`bench/config.json`: 1280×720, pixelRatio 1, seed 12340, 5 секунд прогрева после завершения
загрузок, 20 секунд измерений. Маршрут задаётся функцией от прошедшего времени, а не
числом кадров, поэтому скорость движения не зависит от FPS. Измеряется RAF cadence
в headless Chrome с отключённым лимитом FPS; CPU submit и асинхронные GPU queries
приводятся отдельно. Это не измерение задержки физического дисплея.

- `movement`: настоящий `WorldRenderer3D`, map 0, локальные terrain/splat/grass/scenery,
  10 персонажей, переход через x=-9600. В браузере прогревается только начало маршрута;
  новые тайлы и модели должны проходить обычный streaming в измеряемом участке.
- `crowd-10/50/200`: ровно столько анимированных HumanMale, реальные текстуры,
  228 костей на текущем клиенте, независимые фазы Stand/Run. Используются shipping
  `AnimatedModel`/`ModelBuild`. Это отдельная лабораторная сцена: игровой
  `WorldRenderer3D` имеет лимит 64 и не проверяет одновременно 200 моделей.
  Нет HUD, сетевой симуляции, разнородного снаряжения и поведения сервера.

Средний FPS = 1000 / средний интервал RAF; 1% low = 1000 / среднее худшего 1% интервалов;
p99 — nearest rank; >30ms — строго больше 30. Первый интервал начинается после прогрева.
Пик JS heap снимается с каждого кадра через `performance.memory` с precise-memory-info.
Потерянные/недоступные GPU samples не считаются нулевыми.

Скриншоты снимаются после замеров, на фиксированных точках и одинаковой фазе анимации.
Сравнение с `--baseline` проверяет размеры, число изменённых пикселей и дельты каналов;
для мира учитывайте недетерминированный порядок асинхронного допуска новых объектов.
Численные дельты требуют визуального разбора, а не автоматического объявления паритета.

Результаты: `bench/results/<timestamp>.json`, изображения и trace в соседнем каталоге.
Они и клиентские ресурсы исключены из Git. Сводка принятого baseline — `bench/baseline.json`.
`--smoke` сокращает только техническую проверку до 3 секунд и никогда не даёт valid baseline;
`--scenario movement,crowd-200` выбирает подмножество; `--prepare` только наполняет кеш.
Ошибки ассетов, отсутствующая высота маршрута, программный GPU и новые ассеты в измеряемом
участке делают результат невалидным. Trace/CPU profile включаются только отдельным
запуском: overhead профилировщика не смешивается с сравнением производительности.
