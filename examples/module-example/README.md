# Пример модуля: схема сообщения, лайвскрипт к ней и окно

Схема сообщения — [`messages/example.json`](./messages/example.json), в том виде, в каком её
читает веб-клиент. Скопируйте её в `modules/<ваш-модуль>/content/messages/example.json` (или,
пока это черновик, в `data/ui/<ваш-модуль>/messages/example.json`), и клиент подхватит его при входе
в мир: шлюз перечислит файл на `GET /modules/index`, клиент заберёт его с
`GET /modules/messages/<модуль>/example.json`, проверит и зарегистрирует.

Рядом лежит [`ui/example.json`](./ui/example.json) — окно, которое клиент уже рисует; о нём ниже,
в разделе «Окно». Клиент загружает обе схемы, рисует окно и выполняет действия кнопок.

## Куда класть файл

| каталог | когда |
|---|---|
| `modules/<mod>/content/messages/*.json` | боевой вариант: там же, где студия владельца пишет `content/ui/*.json` |
| `data/ui/<mod>/messages/*.json` | черновик рядом с клиентом, ничей билд его не трогает |

Черновик перекрывает файл модуля с тем же именем — ради этого каталог и существует: правку пробуют
до того, как она попадёт в модуль. Перекрытие **пофайловое**: остальные файлы модуля продолжают
грузиться, а индекс говорит про каждый файл, откуда он взят (`"source": "draft"` или `"module"`), и
это же видно в диагностике — так забытый черновик заметен, а не загадочен.

## Как устроена схема

Файл — либо `{"messages": [...]}`, либо голый массив сообщений. У сообщения четыре поля:

* `name` — уникально на весь клиент, с точкой в стиле `модуль.Сообщение`;
* `opcode` — `uint16`, который вы выбираете сами. **Дубликат отклоняется с именами обоих модулей**.
  Студия владельца пишет в генерируемый Lua то же правило: «Опкоды должны быть уникальны на весь
  сервер»;
* `direction` — `"in"` (только приём), `"out"` (только отправка) или `"both"` (по умолчанию);
* `fields` — список полей **в том же порядке**, в каком их пишет лайвскрипт.

### Типы полей

| тип | на проводе | чем пишется в лайвскрипте |
|---|---|---|
| `u8` `i8` `u16` `i16` `u32` `i32` | 1–4 байта LE | `WriteUInt8` … `WriteInt32` |
| `u64` `i64` | 8 байт LE, в клиенте `bigint` | `WriteUInt64` / `WriteInt64` |
| `f32` `f64` | 4 и 8 байт | `WriteFloat` / `WriteDouble` |
| `string` | `u32` длины и байты **без NUL** | `WriteString` |
| `cstring` | байты и один `0` | `WriteStringNullTerm` (только C++) |
| `fixedString`, `size` | `u8` длины и ровно `size` байт | старый `@MsgString(n)` |
| `array`, `capacity`, `of` | `u8` счётчика и ровно `capacity` слотов | старый `@MsgPrimitiveArray(n)` |
| `nested`, `fields` | поля подряд, без обёртки | старый `@MsgClass` |

Декораторы `@Message`/`@MsgClass`/`@MsgPrimitive`/`@MsgString` в этой сборке объявлены в
`global.d.ts`, но не реализованы. Поэтому схема — JSON, а `fixedString` и `array` существуют ровно
затем, чтобы старую раскладку всё ещё можно было выразить.

## Три ловушки, которые стоит знать до того, как писать схему

* **`CreateCustomPacket(op, size)`: `size` — это предвыделение, которое становится нагрузкой.**
  `CreateCustomPacket(op, 100)` плюс одно `WriteUInt32` отправит 100 байт, 96 из них —
  неинициализированная куча (`CustomPacketBase.cpp:25-52`, `:151-182`). Пишите `CreateCustomPacket(op, 0)`.
  Клиент читает объявленное и терпит хвост, а размер хвоста показывает в диагностике.
* **`u64` не переживает Lua tswow.** `ClientNetwork.lua:73-74` для обоих 64-битных читателей зовёт
  `READ_UINT32`, а `TSPacketRead::ReadUInt64` возвращает `double(Read(def))`. Восемь байт всё равно
  едут — их пишет C++, — но на той стороне ждите округления. В веб-клиенте это `bigint`, и в окне
  диагностики он показан с суффиксом `n` именно поэтому.
* **Пустое сообщение отправить нельзя.** Кадр из одного шестибайтового заголовка сервер читает как
  `NO_HEADER` и отвечает `KickPlayer` (`CustomPacketBuffer.cpp:24-27`). Схема с `"fields": []` и
  направлением `"out"`/`"both"` отклоняется при загрузке. «Игрок нажал Закрыть» — это поле `u8`,
  которое лайвскрипт игнорирует.

Верхний предел на отправку — **10 229 байт** тела: `IsValidSize` это `size < 10240` вместе с
четырьмя байтами опкода (`WorldSocket.cpp:708-712`), а кадр больше закрывает сокет. Фрагментировать
нельзя: нефинальный фрагмент должен быть не меньше 25 000 байт, иначе `TOO_SMALL_FRAGMENT` и кик.
На приём этот предел не действует — там работает квота сборщика в 8 000 000 байт.

## Лайвскрипт к этому файлу

`modules/<mod>/livescripts/<что-нибудь>.ts`. Опкоды — те же числа, что в JSON:

```ts
export const OP_EXAMPLE_REQUEST = 4001; // клиент → сервер
export const OP_EXAMPLE_STATE   = 4002; // сервер → клиент

export function Main(events: TSEvents) {
    events.CustomPacket.OnReceive(OP_EXAMPLE_REQUEST, (opcode, packet, player) => {
        const value = packet.ReadDouble();

        // Ноль — это предвыделение, а не «пусто»: писатель растёт сам.
        const reply = CreateCustomPacket(OP_EXAMPLE_STATE, 0);
        reply.WriteUInt32(1234);                  // gold
        reply.WriteString("Лавка");               // title
        // guid: u64. `GetGUID()` возвращает `TSGUID` — объект с методами, а не число, — и `BigInt`
        // в лайвскриптах не объявлен вовсе (`global.d.ts`, ни одного упоминания). На провод кладут
        // младшую половину: `GetGUIDLow()` — это `TSNumber<uint32>` (`global.d.ts:5884`), а
        // `WriteUInt64` берёт `uint64`, который в этих объявлениях тот же `number` (`:27`, `:10054`).
        reply.WriteUInt64(player.GetGUIDLow());   // guid
        // tag: fixedString(12) — длина в байтах, потом ровно 12 байт
        WriteFixedString(reply, "shop", 12);
        // prices: array(8, u32) — счётчик, потом ровно 8 слотов
        reply.WriteUInt8(3);
        reply.WriteUInt32(10); reply.WriteUInt32(20); reply.WriteUInt32(30);
        for (let i = 3; i < 8; i++) reply.WriteUInt32(0);
        // seller: nested — просто поля подряд
        reply.WriteUInt32(60001);
        reply.WriteUInt8(1);

        reply.SendToPlayer(player);
    });
}

// Только ASCII, и это не придирка: клиент читает `fixedString` как UTF-8 по объявленному числу
// байт, а помощник пишет по одному обрезанному байту на кодовую единицу UTF-16 и кладёт в длину
// `value.length`. Для «Лавка» это 5 при десяти настоящих байтах UTF-8; прогнано через
// `decodeCustom` — обратно приезжает `1b 30 32 3a 30`, то есть ESC и «02:0». Для кириллицы
// берите тип `string`: его пишет `WriteString`, и там уже UTF-8 с длиной в байтах.
function WriteFixedString(packet: TSPacketWrite, value: string, size: uint32): void {
    packet.WriteUInt8(value.length);
    for (let i = 0; i < size; i++) packet.WriteUInt8(i < value.length ? value.charCodeAt(i) : 0);
}
```

`CustomPacket.OnReceive` — это `TSEvents.h:861-864`, `CreateCustomPacket` и `SendToPlayer` —
`TSCustomPacket.h:52`, `:104`. Ничего другого на серверной стороне для кастомного пакета нет.

## Что получается, если это померить

Проверено через `parseCustomMessages` и клиентский кодек:

* `example.Request` — фиксированные **8 байт** тела; кадр вместе с шестибайтовым заголовком —
  **14 байт**: `00 00 01 00 a1 0f` (fragmentId 0, totalFrags 1, опкод `0x0FA1` = 4001) и `f64`.
* `example.State` фиксированного размера не имеет — в нём `string`. Ответ из примера выше
  (`gold` 1234, `title` «Лавка», `guid`, `tag` «shop», три цены из восьми, `seller`) — **77 байт**,
  и он декодируется обратно ровно в то же значение, с нулевым хвостом.

## Что видно в клиенте

Диагностика (клавиша `O`), вкладка **«Пакеты»**:

* строка на каждый файл схемы: модуль, файл, сколько сообщений живо, откуда взят (`module` или
  `draft`), первые восемь знаков sha1;
* строка на каждое **загруженное** сообщение, даже если по нему ещё ничего не ходило: имя, модуль,
  опкод и «тишина» вместо счётчиков. Это ответ на первый вопрос — «клиент вообще взял мой файл, и
  под каким номером»;
* строка на каждый опкод: имя сообщения и модуль, счётчики принято/отправлено/разобрано/ошибок,
  размер хвоста и **последнее декодированное значение**;
* опкод, которого нет ни в одной схеме, показан как «схемы нет» и с сырыми байтами в hex — это
  ровно то, что видно, если лайвскрипт уже шлёт, а JSON ещё не написан;
* внизу — предупреждения транспорта (многофрагментное сообщение, брошенный хвост) и ошибки
  декодирования с именем поля, на котором две стороны разошлись.

Вкладка обновляется сама, пока открыта: счётчики идут за пакетами, окно закрывать и открывать не
нужно. Закрытая вкладка не стоит ничего — кадр сравнивает четыре числа и выходит.

## Окно: `ui/example.json`

Рядом с `messages/` лежит [`ui/example.json`](./ui/example.json) — определение окна в том же
формате, в каком его пишет студия владельца (`modules/<мод>/content/ui/*.json`): корневой `Frame`,
якоря `SetPoint` с `y` вверх, `strata`, `backdrop`, `closeButton`, `escClose`, локализованный
заголовок. Ничего своего веб-клиент не придумал — файл студии читается как есть, а его собственные
добавки (`bind: "{выражение}"`, `repeat`, `state`, `css`) необязательны.

В этом примере: полоса на привязке `playerHealth`, подпись на `playerName`, подпись-шаблон
«Уровень {player.level} · {world.subzone or world.zone} · {world.clock}», вторая полоса на
`targetHealth` с условием `noTarget → hide` и подписью «Цели нет» под тем же условием наоборот,
надпись «В бою» с условием `outOfCombat → hide`, и кнопка с действием `chat`.

Рядом же — [`ui/proverochnyy-ekran.json`](./ui/proverochnyy-ekran.json), побайтная копия живого
экрана владельца из `modules/test/content/ui/`, чтобы рендер можно было проверить на настоящем
файле, а не только на придуманном.

**Действия кнопок поддерживаются.** Девять глаголов: открыть окно, показать или спрятать виджет,
записать в состояние окна, послать строку в чат, выполнить макрос, вызвать одну из тридцати двух
именованных команд клиента, отправить объявленное сообщение или сырое, сыграть звук интерфейса и
ветвиться по выражению. Файлы забираются через `GET /modules/ui/<модуль>/<файл>.json`, окна
регистрируются на входе в мир, а вкладка «Окна» пишет, сколько нажатий было и сколько выполнено.

## Правка встроенного окна: `ui/target-extras.json`

Второй вид файла в том же каталоге `content/ui/` — **правка** (`"kind": "patch"`). Она не рисует
своё окно, а меняет окно, которое написал сам клиент, и только там, где клиент это разрешил:

```json
{
  "kind": "patch",
  "id": "target-extras",
  "target": "target-frame",
  "hide": ["target-frame/details"],
  "add": [{ "slot": "target-frame/actions", "widget": { "id": "identify", "type": "Button", ... } }],
  "class": { "target-frame": "example-skin" },
  "css": ".example-skin { outline: 1px solid #d8b25a; }"
}
```

`widget` — тот же виджет, из которых состоит окно: тот же разборщик, тот же рендер, тот же проход
привязок раз в кадр и тот же список действий. После загрузки `messages/example.json` кнопка в рамке
цели шлёт кастомный пакет ровно так же, как кнопка в окне модуля. Встроенный диагностический preview
без установленного модуля проверяет только окно и правку: реестр сообщений он не загружает.

### Куда можно дотянуться

| слот | где | параметры |
|---|---|---|
| `character-window/stats` | под характеристиками персонажа | — |
| `character-window/footer` | внизу окна персонажа | — |
| `target-frame/actions` | ряд кнопок рамки цели | — |
| `bag-window/footer` | внизу каждой из четырёх сумок | `slot.bag` = 1…4 |
| `quest-log/entry-actions` | в каждой карточке журнала заданий | `slot.questId` |
| `minimap/buttons` | ряд кнопок миникарты | — |
| `spellbook/tabs` | строка вкладок книги заклинаний | — |
| `target-frame/details` | подвид · тип · уровень цели | только `hide` |
| `player-frame/experience` | полоса опыта под рамкой игрока | только `hide` |
| `minimap/clock` | часы над миникартой | только `hide` |

Скрыть можно любой из десяти, а **поставить виджет — только в первые семь**, и это проверка, а не
уговор: в последние три клиент пишет свой собственный `textContent` (подвид цели, часы), а этот
сеттер заменяет всех детей — виджет модуля смело бы с экрана без единого слова. Правка с `add` в
такой слот отказывается целиком, и в сообщении перечислены те семь, которые виджет принимают.
`class` вешается на `player-frame`, `target-frame`, `character-window`, `inventory-window`,
`spellbook-window`, `bag-window`, `quest-log` и `minimap`. Слот есть только там, где встроенное окно
его объявило: до произвольного узла модер не дотягивается, и это сделано намеренно.

**Слот с несколькими местами.** `quest-log/entry-actions` объявляется на каждой карточке, а
`bag-window/footer` — на каждой сумке, так что один `add` превращается в столько копий, сколько
сейчас мест. Каждая копия получает свои привязки и свой параметр:

```json
{ "do": "command", "name": "queryQuest", "args": ["{slot.questId}"] }
```

`{slot.name}` — имя слота, остальные ключи — то, что объявила панель. Нажатие читает ту же строку,
что нарисована: кнопка на карточке задания 4213 шлёт 4213, а не то, что было в последнем кадре.

**Отказ — всему файлу.** У окна сломанный виджет выбрасывается, а окно грузится. У правки не так:
файл, который спрятал строку и не сумел поставить кнопку взамен, забрал у игрока и не дал ничего.
Поэтому неизвестное имя слота или окна — отказ всей правке, и в сообщении перечислены все десять
имён, которые есть.

**Стиль.** `css` — это текст стиля, а не имя файла (как и `params.css` у окна); отдельный файл
кладётся в `content/css/` и подхватывается сам. Каждое правило модуля получает префикс
`[data-module="<модуль>"]` — и в виде потомка, и слитно, если селектор начинается с `.`, `#`, `[`
или `:`. Слитный вид и есть то, чем `class` работает: отметка стоит на самом окне, а не над ним.
`body { display: none }` слитного вида не получает (тип обязан быть в составном селекторе первым) и
остаётся недостижимым.

**Выгрузка симметрична.** Виджеты снимаются с хостов, `hidden` возвращается к тому значению, которое
было **до** первого скрытия (а не к `false`: виджет, который клиент и так прятал, модуль не имеет
права включить), класс и отметка снимаются с окна. Проверяется побайтно — рамка цели сериализуется
до и после.

## Что видно в клиенте: вкладка «Окна»

Диагностика (клавиша `O`), вкладка **«Окна»**:

* «Показать пример» рисует `ui/example.json`, «Показать экран владельца» — `ui/proverochnyy-ekran.json`,
  «Применить правку» применяет и снимает `ui/target-extras.json`; модуль на диске для этого не нужен,
  файлы берутся прямо отсюда тем же путём, каким пойдёт загрузчик;
* строка на каждое живое окно: модуль и id, открыто или закрыто, сколько в нём виджетов, сколько
  выражений вычислил последний кадр и сколько из них изменилось (у неподвижного окна — ноль), и
  сколько было нажатий;
* строка на каждую живую правку: модуль, id и окно, которое она правит, и сколько у неё сейчас
  **мест** — «мест 0» у правки журнала заданий означает, что файл загружен, а журнал ещё не
  открывали, и это первое, о чём спрашивает автор такой правки;
* ниже — замечания разбора: всё, что `WindowSchema` записал, даже если окно при этом загрузилось.
